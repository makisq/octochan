## Что такое Octochan (ochan)?

**Octochan** (команда `ochan`) — минималистичный оркестратор для командной
строки и CI/CD: безопасная и предсказуемая автоматизация работы с
конфигурациями, серверами и базами данных.

Главная идея — **контроль человека над изменениями**. ochan отвечает на
три вопроса: *что изменится*, *кто сказал «да»* и *как вернуть, как
было*. А когда серверов много — и на четвёртый: *что можно сделать без
человека* — ровно то, на что человек дал согласие заранее, с границами,
которые видно и которые отзывают.

Версия — **0.3.0-alpha**. Код, документация и сборка — в каталоге
[`octochan/`](octochan/README.md).

---

### Ключевые возможности

* **План до выполнения.** Правка конфига, сценарий исполнителя или
  сценарий на языке алиасов сначала показывают, что изменится, — ничего не
  меняя. Конфиги сравниваются по смыслу: `8GB` и `8192MB` равны.
* **Заявки и согласование.** Критичное изменение оформляется заявкой и
  согласуется человеком. Выполняется ровно согласованный план: перед
  выполнением он строится заново и сверяется, а исполнитель обязан
  применить ровно его. Заявки выстраиваются по порядку (`--after`); упавшая
  заявка не повторяется молча, а пересобирается; одну заявку не выполнят
  дважды — ни два процесса, ни два сервера.
* **Откат.** Файлы возвращаются к прежнему содержимому, а правку, сделанную
  после операции, откат не стирает. Во внешней системе обратное действие —
  вторая согласованная заявка (`ochan compensate`).
* **Инвентарь и цели.** Серверы, группы и их переменные — в инвентаре (YAML,
  выгрузка CMDB, реестр агентов), а не в тексте сценария; `--limit`
  сужает цели.
* **Без человека — только по политике.** `ochan watch` находит новые
  серверы и выполняет сам только то, что укладывается в зарегистрированную
  политику: белые списки целей и значений, срок, отзыв. Всё прочее
  становится заявками.
* **Безопасная работа с нейросетями (MCP).** Модель читает, планирует,
  пишет сценарии и оформляет заявки, но **не может выполнить или
  согласовать изменение** — это делает человек. Задачи ставятся
  формальным промптом, и ochan проверяет детерминированно: сам промпт,
  сценарий, план — по жёстким правилам и границам слотов, отчёт модели —
  против плана. Подключаются и локальные модели, и модели поставщиков по
  HTTP.
* **Роли, аудит, песочница.** Права, запреты, области, пределы частоты,
  разделение обязанностей и журнал аудита с цепочкой хешей; системная
  политика ролей, которую держит root. Сценарии, написанные не человеком,
  выполняются в песочнице ядра Linux (Landlock, seccomp, пространства
  имён), программы — только разрешённые.
* **Сервер и отказоустойчивость.** Общий оркестратор по TLS с входом по
  ролям; пара серверов primary/standby с ручным переключением; машины-агенты,
  которые сами сообщают о себе.
* **Контур без человека (HA-AI).** master передаёт модели free — роль,
  политику и срок: модель чинит инциденты сама, но у каждого уровня
  критичности свой срок; не успела — инцидент уходит инженерной группе
  письмом с описанием, её шагами и журналами. О решённом — тоже письмо;
  статистика (что модель решила сама, что нет и почему) — отчётом на почту
  раз в настраиваемый период. Агенты пишут друг другу только формальным
  промптом, людям — на языке, который выбрал оператор.
* **Своя модель (embedded).** Заготовка под локальную LLaMA на fp: ochan сам
  ведёт генерацию, кольцо 0 и маска языка не дают модели напечатать ни
  токена ниже порога, ни утверждения вне формального языка. Говорить на
  естественном языке своя модель не может.
* **Триггеры CI и реестры пакетов.** Роль развёртывания действует только в
  окне релиза; пакеты алиасов ставятся из реестров с подписью и заявкой
  (`!!search`, `!!rin`).
* **Расширяемость.** Из коробки — файлы конфигураций и живой
  PostgreSQL/pgbouncer, исполнитель RLM ставится модулем. Linux, Ansible,
  Kubernetes, облака подключаются модулями (команды, исполнители, языки
  интерфейса по gRPC), источниками и пакетами алиасов.
* **CI/CD и интерактивная работа.** Утилита командной строки с понятными
  кодами возврата, интерактивная оболочка, интерфейс на русском и
  английском, другие языки — модулями.

### Быстрый старт

```bash
cd octochan
make install                          # ochan и ochan-mcp — в ~/.local/bin
ochan diff prod.conf test.conf        # различия по смыслу
ochan request prod.conf changes.conf  # заявка «ждёт решения»
ochan approve <id> && ochan apply --request <id>
```

Дальше — [документация](octochan/docs/README.md), [как устроен
ochan](octochan/docs/guide/concepts.md) и [кукбук](octochan/docs/cookbook/README.md)
с проверенными рецептами.

### Для кого этот проект?

Octochan предназначен для **DevOps-инженеров, системных администраторов и
разработчиков**, которым нужен надёжный инструмент автоматизации с защитой
от «человеческого фактора» и безопасными механизмами работы с
ИИ-ассистентами.

Это альфа: что в ней проверено, а что нет, — в разделе
[«Статус безопасности»](octochan/README.md#статус-безопасности).

# БАГ 11. Модуль-библиотека ставится как `.hcplugin`

## Что произошло у нас

```
plugins/nash/         package nash    ← БИБЛИОТЕКА
plugins/rlm/          package main    ← модуль
```

Собрал `nash` в плагин:

```bash
go build -o nash.hcplugin ./plugins/nash
```

**Собралось!** Размер — **651 КБ** (обычный модуль — 22 МБ, в 34 раза меньше).

При установке:

```
ошибка: модуль не загрузился и был удалён
```

**И всё.** Ни причины, ни подсказки.

## Почему `go build` не падает

Go **не требует** `main` для сборки — создаёт бинарник-заглушку:

```
package nash
func main() {}   ← фактически
```

То есть **валидный ELF**, но **не go-plugin**. `pluginhost` его запускает, тот не отвечает рукопожатием — **exit status 2**.

## Сколько это стоит

**Нашёл случайно.** Если бы не заметил размер — **искал бы долго**.

## Что нужно

### Вариант A — проверка при `!!install`

```
!!install nash.hcplugin
```

До копирования — **запустить** и проверить рукопожатие. Если не отвечает:

```
ошибка: nash.hcplugin — не модуль ochan.
  Причина: пакет «nash» — библиотека (package nash), а не main.
  Соберите модуль: package main + pluginhost.ServeCommandModule(...)
```

### Вариант B — умная диагностика

Хост **сам** определяет:

- **ELF** — Go-плагин? `.hcplugin`?
- **Запуск** — отвечает ли по gRPC?
- **stderr** — что напечатал процесс?

И говорит:

```
ошибка: процесс завершился с кодом 2
  stderr:
    This binary is a plugin. These are not meant to be executed directly.
```

**Вот это** — то, что спасло бы нас в баге 2.

# Рукопожатие: `!!install` ↔ плагин

## Что **сейчас**

```
1. !!install копирует файл в .octochan/modules/
2. Вычисляет SHA256
3. Запускает процесс
4. Ждёт gRPC-рукопожатие
5. Если fail — удаляет и говорит «модуль не загрузился»
```

**Проблема:** шаг **5** — **после** шага **1**. Файл **уже** в каталоге.

## Что **должно** быть

### Шаг 0 — **до** копирования

```
!!install nash.hcplugin

1. Проверить: ELF? Linux? Права?
2. Запустить в песочнице с таймаутом 5 с
3. Проверить рукопожатие: pluginhost.GRPCProtocol?
4. Проверить Name(), Version()
5. Проверить SHA256 (если есть .sha256)
6. Только теперь — копировать
```

**Если любой шаг упал — файл не попадает в `.octochan/modules/`.**

### Сообщения при отказе

```
!!install nash.hcplugin

ошибка: это не модуль ochan

  Файл:     nash.hcplugin
  Размер:   651 234 байт (в 34 раза меньше обычного)
  Пакет:    nash (не main)

  Причина: го собирает библиотеку как бинарник-заглушку.
  Она не отвечает по протоколу плагина.

  Что делать:
    Соберите именно модуль: package main + pluginhost.ServeCommandModule(...)
```

**Вот как надо.** Тогда баг 11 **исчезнет**.

## Ещё — **проверка при `!!reload`**

Сейчас `!!reload` перезагружает **без** проверки. Если модуль сломан — **молча** отвалится.

**Что нужно:** `!!reload` **проверяет** и, если сломан, **оставляет старую версию**:

```
!!reload

  rlm.hcplugin      v0.3.0 → загружен
  nash.hcplugin     ✗ не модуль — оставлен прежний
```

## И **атомарность** установки

```
!!install bad.hcplugin

  Проверка:  ✗
  Установка: отменена
  Прежняя версия rlm.hcplugin: не тронута
```

**Ничего не сломано.** Сейчас — **файл удалён**.

# Пожелания к 0.3.1

---

## Обязательно — это блокеры

### 1. `Required` без `Default` — не пишется в конфиг

**Симптом:** обязательная настройка **дублируется** — одна строка без `#`, вторая закомментированная.

```
  pgstat:
    cluster: ""                    ← setConfigValues
    # host: 127.0.0.1
    # имя кластера (обязательно)
    # cluster: ""                  ← insertModuleBlock, дубликат
```

**Причина:** `configEntry` **не знает** про `Required`. Два пути (`setConfigValues` и `insertModuleBlock`) пишут **одну** настройку, каждый по-своему.

**Что нужно:** единый писатель. Или `required bool` в `configEntry`.

### 2. Модуль упал — **не говорят почему**

```
plugin process exited: error="exit status 2"
```

Наш `-si` падал **молча**. Пришлось **запускать файл руками**, чтобы увидеть панику.

**Что нужно:** stderr плагина **пробрасывать** в сообщение. Хотя бы первые 20 строк.

### 3. `>|` теряет вывод на первом вызове

```
applyModuleChanges() → refreshModuleCommands() → rootCmd.SetOut(старый)
```

Подмена в `withRedirect` **слетает**. Данные **молча** теряются.

**Что нужно:** `applyModuleChanges()` **до** `withRedirect`.

---

## Очень желательно

### 4. `config show` — прочитать свой конфиг

`.octochan/` закрыт целиком. `corlm` **пишет**, а прочитать **нечем**. Говорят, будет — **подтверждаю спрос**.

**Что нужно:** `ochan config show` — **без секретов**, с маской (`cookie: "…"`), с указанием источника (`modules.rlm` / `executors.rlm` / `defaults.*`).

### 5. `Supply` командам, а не только исполнителю

`remoteRunner` отдаёт `runnerhost.Settings(ctx)` и `Token(ctx)`. **Команда** — **ничего**. Пришлось читать `tokens/` самим.

**Что нужно:** `pluginhost.Settings()` и `pluginhost.Token()` **и для команд**.

### 6. POST в `fetch`/`curl` — **осознанно**

Сейчас:

```
метод POST: сценарий только читает (GET, HEAD)
```

**Правильно.** Но нужен **путь**: `--sandbox=false` **или** явный `fetch(url, {"method": "POST", "allow_write": true})` с маркером в плане — **чтобы видел человек**.

Не «просто добавьте POST» — **добавьте с видимостью**.

### 7. Шаблон модуля

```
ochan new module mymod
```

Создал бы `main.go` с готовым скелетом, `go.mod`, `Makefile`. Сейчас — **копируешь** чужой.

## Приятно было бы

### 8. Отладка алиасов

Ошибка: `<shell>:1:11: file: … — каталог закрыт`. Хорошо. Но **нет**:
- значения переменных на момент ошибки
- трассировки вызовов
- `--trace` флага

**Что нужно:** `ochan run --trace script.ochan` — печатать **каждую** строку и результат.

### 9. `ochan inspect` показывал **требования**

```
Настройки:
  api_url = ... (обязательно)  ← есть
```

Но **не сказано**, что **будет**, если не задать. Для `Required` — пример ошибки.

### 10. Точечное закрытие `.octochan/`

Закрыт **весь** каталог. Секреты — только в `config.yaml` и `tokens/`. Логи, история, `modules/` — **безобидны**.

**Что нужно:** закрыть **точечно**.

### 11. Модуль-библиотека **не должен** собираться в `.hcplugin`

`go build` пакета без `main` даёт **заглушку 651 КБ**. Мы на это **попались**.

**Что нужно:** `!!install` **до** установки проверяет — это модуль?

---

## Чего **не** надо


**Не убирайте модель «сценарий только читает».** Это **сильная** идея. Пусть будет **видимый** способ писать, а не **молчаливый**.
