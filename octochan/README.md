# octochan

Утилита сравнения конфигураций PostgreSQL/pgbouncer и запуска сценариев RLM.

## Сборка

```
go build -o ochan .
```

Собирается под Linux, macOS и Windows.

## Устройство

```
config       движок: разбор, нормализация, сравнение, план        зависимостей нет
pluginhost   хост подключаемых модулей команд                     зависимостей нет
scenario     сценарий и реестр исполнителей      -> config
lang         язык алиасов                        -> config
pgsource     живой PostgreSQL как источник       -> config
rlm          клиент RLM как исполнитель          -> config, scenario
workspace    рабочие директории, история, заявки -> config
report       документы .docx и почта             -> config
module       встроенные модули сценариев         -> config, rlm, scenario
cmd          команды CLI                         -> всё вышеперечисленное
```

**`config` не зависит ни от чего** — ни от RLM, ни от системы плагинов, ни
от единой внешней библиотеки. Движок сравнения полезен сам по себе, и его
можно импортировать отдельно.

**`lang` знает только про `config`.** Язык алиасов не привязан к RLM: он
работает с конфигами, а откуда те берутся — дело источников.

**Новая ниша — это новый пакет.** Источник регистрирует свою схему
(`config.RegisterSourceScheme`), и ядро не меняется. `pgsource` — первый
такой пакет, не последний.

**RLM — не корень, а исполнитель.** `scenario` описывает, что нужно
сделать, и ведёт реестр тех, кто умеет это выполнять. `rlm` регистрируется
в нём наравне с любым другим. СУБД и RLM — ниши, а не фундамент.

**ИИ — тоже модуль, а не основа.** Сервер MCP лежит в `mcp/` отдельным
Go-модулем со своим `go.mod` и без внешних зависимостей. Ядро о нём не
знает, моделей в нём нет, привязки к поставщику нет. Через него модель
может читать, планировать, писать сценарии на языке алиасов и создавать
заявки, но не выполнять: см. [mcp/README.md](mcp/README.md).

## Рабочие директории

Всё живёт под `~/.octochan`:

```
~/.octochan/
  config.yaml     настройки
  .env            токен API (права 0600)
  modules/        подключаемые модули команд (*.hcplugin) и их суммы
  scenarios/      сохранённые сценарии
  aliases/        пользовательские алиасы (*.ochan)
  reports/        отчёты команды diff
  snapshots/      снапшоты расхождений
  history/        журнал выполненных операций (для rollback)
  requests/       заявки на согласование
  logs/           журнал работы
```

Путь до конфига переопределяется флагом `--config` или переменной
`OCTOCHAN_CONFIG`.

## Настройка

Адрес API не зашит в код — задайте его перед первым запуском:

```yaml
# ~/.octochan/config.yaml
defaults:
  api_url: https://rlm.example.internal/api/tasks.json
  max_parallel_tasks: 5
  http_timeout: 30s
  module_command_timeout: 10m
  auto_check_status: false
  allow_unverified_modules: false
```

Токен:

```
ochan auth                       # спросит токен, ввод скрыт
export OCTOCHAN_API_TOKEN=...    # либо через окружение
```

Токен хранится в `~/.octochan/.env` с правами `0600` и никогда не попадает
в `config.yaml`.

## Основные команды

```
ochan diff prod.conf test.conf        сравнить два конфига
ochan patch base.conf changes.conf -o out.conf
ochan validate postgresql.conf        проверить синтаксис
ochan find postgresql.conf shared_buffers
ochan stats postgresql.conf
ochan apply scenario.yaml             выполнить сценарий
ochan apply scenario.yaml --wait
ochan check сценарий.ochan            проверить сценарий, не выполняя
ochan plan сценарий.ochan             что сценарий изменил бы
ochan services                        кто какие сервисы исполняет
ochan status <task_id>
ochan logs --tail 50
ochan shell                           интерактивная оболочка
```

Команды читают stdin, если вместо файла указан `-` или файл не указан вовсе:

```
cat prod.conf | ochan validate
ochan print prod.conf | ochan diff - test.conf
```

Ненулевой код возврата означает ошибку — команды пригодны для CI.

## Сравнение значений

Значения сравниваются по смыслу, а не побуквенно:

| Равны | Не равны |
|---|---|
| `8GB` и `8192MB` | `1` и `on` |
| `1s` и `1000ms` | `8MB` и `8GB` |
| `on`, `true`, `yes` | `/var/lib/PG` и `/var/lib/pg` |

## План и история

### plan — что произойдёт, до того как произошло

```bash
ochan plan prod.conf changes.conf          # что изменит patch
ochan plan restart.yaml                    # какие задачи были бы созданы
```

```
План: restart.yaml (pangolin_restart) -> —
‼️ План прерывает обслуживание

Изменений: 2

  CI00000001
    задача     pangolin_restart — confirm=true, restart=instance
  CI00000002
    задача     pangolin_restart — confirm=true, restart=instance
```

В режиме плана изменяющие запросы запрещены на уровне API-клиента, поэтому
команда не может создать задачу даже по ошибке. Если модулю нужен ответ
внешней системы уже на этапе подготовки (так делает `psql_tuning_params_se`,
запускающий разведку), план получается неполным — и об этом говорится прямо,
а не замалчивается:

```
⚠️ модуль psql_tuning_params_se обращается к API на этапе подготовки,
   поэтому план неполный: показаны цели, но не итоговые параметры
```

### history и rollback

Каждая операция попадает в журнал `~/.octochan/history`:

```bash
ochan history              # список от новых к старым
ochan history f475         # подробности (достаточно начала идентификатора)
ochan rollback f475        # вернуть файл к состоянию до операции
```

```
• 2026-09-07 01:30:16  780cce0d6a  правка файла  prod.conf  откат операции f47595a2a8
↩ 2026-09-07 01:29:53  f47595a2a8  правка файла  prod.conf  изменено параметров: 2

• обратимо, ↩ уже отменено
```

Состояние файла до изменения хранится целиком, а не как обратный diff: конфиги
малы, а откат по diff ломается, если файл успели поправить руками между
операциями. Сам откат тоже записывается и тоже обратим.

**Что откатить нельзя.** Задачи, созданные во внешней системе, необратимы:
перезапуск уже произошёл, и отменять в октохане нечего. Для таких записей
команда откажет и скажет об этом прямо, а не сделает вид, что откатила:

```
❌ запись 7c0ccd86f7 необратима (сравнение): откатывать нечего
```

Это доведённые до рабочего вида снапшоты: раньше `diff` складывал их в файлы,
которые никто не читал, потому что `LoadSnapshot` и `ApplySnapshot` не были
подключены ни к одной команде.

## Заявки, документы и почта

Во многих компаниях изменение нельзя выполнить просто потому, что оно
правильное: сначала нужна заявка, согласование и бумага. Октохан умеет
всю цепочку целиком.

```bash
ochan request restart.yaml --doc заявка.docx   # оформить заявку и выгрузить документ
ochan requests                                 # очередь
ochan requests 3ff2                            # карточка с планом
ochan approve 3ff2 --comment "окно с 02:00"    # согласовать
ochan reject 3ff2 --reason "нет окна"          # отказать (причина обязательна)
ochan apply --request 3ff2                     # выполнить согласованное
```

**Заявка хранит сам сценарий, а не путь к нему.** Между согласованием и
выполнением файл на диске могли поправить — и тогда выполнилось бы не то,
на что сказали «да». `apply --request` берёт текст из заявки.

**Решение принимается один раз.** Согласованную нельзя отклонить, а
отклонённую — согласовать: пересмотр — это новая заявка. Иначе журнал
перестаёт отвечать на вопрос, что именно было одобрено.

```
❌ заявка 3ff2670fdd уже согласована — решение принимается один раз
```

**Несогласованное не выполняется:**

```
❌ заявка 3ff2670fdd не согласована (ждёт решения): выполнять нельзя
```

### Документ

`--doc` выгружает заявку в `.docx` — обычный Word-файл с шапкой, таблицей
полей и таблицей изменений. Формат пишется напрямую (`archive/zip` +
`encoding/xml`), без внешних библиотек и без установленного Word.

### Почта

```yaml
defaults:
  smtp_host: smtp.example.internal
  smtp_port: 587
  smtp_from: octochan@example.internal
  smtp_to: [dba@example.internal, duty@example.internal]
  smtp_user: octochan
  smtp_starttls: true       # требовать шифрование, рекомендуется
  notify_always: false      # true — слать без флага --notify
```

Соединение шифруется всегда, когда сервер это умеет. `smtp_starttls: true`
делает шифрование обязательным: если сервер его не предлагает, октохан
откажется отправлять письмо и скажет об этом.

```
⚠️ не удалось отправить уведомление: не удалось отправить письмо через
   smtp.example.internal:587: сервер не предлагает STARTTLS
```

Включайте этот флаг, если в письмах бывает что-то, что не должно
путешествовать по сети в открытом виде.

```bash
export OCTOCHAN_SMTP_PASSWORD=...     # пароль только через окружение
ochan approve 3ff2 --notify
```

Пароль не хранится в `config.yaml`: конфиг лежит на диске и попадает в
резервные копии.

Ненастроенная почта — **не ошибка**: письмо просто некуда слать, и команда
делает своё дело молча. А вот сбой отправки при настроенной почте
показывается — но работу не прерывает: изменение уже сделано, и откатывать
его из-за письма неправильно.

## Источники конфигурации

Везде, где команда принимает конфиг, можно указать файл, `-` для stdin или
живой источник:

```bash
ochan diff эталон.conf postgres://dba@db1:5432/postgres
ochan stats postgres://dba@db1:5432/postgres
ochan validate postgres://dba@db1:5432/postgres
```

### Почему живой сервер, а не postgresql.conf

Для работающего PostgreSQL conf-файл не является источником правды: поверх
него действуют `ALTER SYSTEM` (postgresql.auto.conf), директивы `include`
и параметры командной строки. Два сервера могут иметь одинаковые файлы
и вести себя по-разному. Поэтому читается `pg_settings`.

Значения пересчитываются в вид, принятый в conf-файле. `pg_settings` хранит
число в единицах поля `unit`, и unit содержит множитель: для `shared_buffers`
сервер отдаёт `setting=16384` при `unit=8kB`, то есть 131072kB. Без пересчёта
сравнение живого сервера с файлом давало бы расхождение в каждой строке.

Берутся только параметры, которые действительно являются конфигурацией.
Отсекаются три вида шума:

| `source` | Что это | Почему не берём |
|---|---|---|
| `default` | ~300 параметров со значением по умолчанию | Простыня «есть только справа» рядом с обычным conf-файлом |
| `override` | `config_file`, `data_directory`, `transaction_isolation` | Факты рантайма, а не настройки |
| `client`, `session` | `application_name` и прочее от подключения | Инструмент показывал бы расхождение, которое сам же и создал |

Флаг `--all` (или `config(источник, "all")` в языке) отключает фильтр:
у тестового сервера это 18 параметров против 364.

Если у параметра стоит `pending_restart`, об этом сообщается отдельно:

```
⚠️ изменены, но требуют перезапуска: max_connections, shared_buffers
Найдены различия (1):
  shared_buffers: 256MB -> 131072kB [Modified]
```

Здесь кто-то выполнил `ALTER SYSTEM SET shared_buffers = '256MB'` и перечитал
конфиг: файл уже говорит 256MB, а сервер по-прежнему работает на 128MB.
Инструмент, читающий только postgresql.conf, сказал бы «всё совпадает».

Подключение подписывается как `application_name = octochan` — чтобы
администратор боевого сервера видел в `pg_stat_activity`, кто пришёл.

### Пароль

Пароль в строке подключения приходится percent-кодировать, поэтому лучше
его туда не писать:

```bash
export PGPASSWORD=...        # либо пропишите сервер в ~/.pgpass
ochan diff эталон.conf postgres://dba@db1:5432/postgres
```

Имя источника в отчётах, журнале и сообщениях об ошибках пароля не содержит.

### Другие источники

`core` не знает ни про PostgreSQL, ни про какую-либо другую систему: источники
регистрируют свою схему сами (см. пакет `pgsource`). Движок сравнения общий,
поэтому новая ниша — это новый пакет со схемой, а не правка ядра.

## Язык алиасов

Алиас оборачивает последовательность операций в именованный вызов
с параметрами и может вызывать другие алиасы.

```
alias синхронизировать(эталон: конфиг, цель: конфиг, адреса: словарь) {
    if diff(эталон, цель) != 0 {
        print("расходятся:", diff_list(эталон, цель))
        for сервер: строка in адреса {
            применить(цель, сервер, адреса[сервер])
        }
        return len(адреса)
    }
    return 0
}
```

```
ochan run сценарий.ochan
ochan run синхронизировать prod.conf test.conf
ochan eval "diff('prod.conf', 'test.conf')"
ochan aliases
```

Файлы алиасов лежат в `~/.octochan/aliases/*.ochan`.

### Значения

Неудачная операция — это ошибка, прерывающая сценарий, а не число.
Значение — то, что операция вычислила: `diff` возвращает количество
расхождений, поэтому условие пишется как `diff(a, b) != 0`.

Типы: целое, дробное, число, строка, логическое, список, словарь,
конфиг. Имена принимаются и латиницей (`int`, `string`, `list`, `map`,
`config`, …).

**Конфиг** разбирается один раз и живёт в переменной, а не перечитывается
на каждом обращении:

```
цель = config("test.conf")
print(цель["max_connections"], цель["server.port"])
put(цель, "max_connections", "200")
save(цель, "patched.conf")
```

Короткое имя параметра ищется среди параметров без секции, затем по всем
секциям; совпадение в нескольких — ошибка с требованием уточнить секцию.

**Словарь** держит карту вида «сервер → адрес»:

```
адреса = {"srv1": "10.0.0.11", "srv2": "10.0.0.12"}
for сервер in адреса { print(сервер, адреса[сервер]) }
```

Фигурные скобки заняты блоками, поэтому литерал словаря распознаётся
только там, где ожидается выражение. В начале инструкции `{` открывает блок.

### Типы необязательны

Без аннотаций всё работает как раньше. Написанный тип проверяется при
объявлении, при каждом последующем присваивании и при передаче аргумента —
ошибка всплывает на входе в алиас, а не в его середине.

Строка числом не считается: `порт: целое = "5432"` — ошибка. Иначе
аннотация не ловила бы ровно то, ради чего её пишут. А `x: число = 5`
проходит: расширение без потери данных.

### Ошибки и параллельность

Основной сценарий предметной области — «раскатать на полсотни серверов,
продолжить при отказе двух и отчитаться». Для него есть `try`/`catch`
и `parallel for`:

```
parallel for сервер in сервера {
    try {
        применить(конфиг, сервер)
        print(сервер, "применено")
    } catch ошибка {
        print(сервер, "ПРОПУЩЕН:", ошибка)
    }
}
```

**Вывод детерминирован.** Итерации выполняются одновременно, но их вывод
сбрасывается в порядке следования элементов, а не в порядке завершения —
иначе результат нельзя было бы сравнить с предыдущим прогоном.

**Число одновременных итераций** ограничено `defaults.max_parallel_tasks`
(по умолчанию 5), чтобы полсотни серверов не превратились в полсотни
одновременных подключений.

**Тело изолировано.** Оно видит копию внешних переменных, а его присваивания
наружу не выходят:

```
счётчик = 0
parallel for n in [1, 2, 3] { счётчик = счётчик + n }
print(счётчик)          # 0
```

Это не ограничение ради ограничения: без копии две итерации писали бы
в одну переменную одновременно, а `put()` в общий словарь давал бы гонку
на уровне Go. Накопление результата делается через вывод, а не через общую
переменную.

По той же причине `break`, `continue` и `return` внутри `parallel for`
запрещены: прерывать нечего, итерации уже идут.

Если отказ не перехвачен, цикл завершается ошибкой со списком упавших целей:

```
parallel for: неудачных итераций 2 из 4:
  srv2: недоступен
  srv4: отказ применения
```

`catch` ловит только ошибки. `break`, `continue` и `return` проходят
сквозь него насквозь — это управление, а не сбой.

### Проверка до запуска

Интерпретатор находит ошибку, только когда до неё дошло выполнение:
опечатка в ветке, которая срабатывает раз в месяц, всплывёт в бою.
`check` обходит все ветки и все алиасы и ничего не выполняет:

```
ochan check сценарий.ochan     # один сценарий
ochan check                    # вся библиотека алиасов
```

```
сценарий.ochan:4:38: неизвестная функция "diff_lst"; возможно, имелось в виду "diff_list"
сценарий.ochan:5:9: break допустим только внутри for
сценарий.ochan:9:1: переменная x: объявлен тип целое, присваивается значение типа строка
сценарий.ochan:14:7: неизвестное имя "y"
❌ сценарий.ochan: найдено ошибок: 4
```

Находится всё, что видно без запуска: неизвестные имена и функции,
переменные вне своей области (заведённая внутри `if` после него не видна —
так же, как при выполнении), число аргументов, `break`, `continue` и
`return` не на своём месте, явно неверные типы, деление на ноль. Все ошибки
сразу, а не по одной за запуск.

Ложная тревога хуже пропуска, поэтому отвергается только то, что неверно
наверняка. Тип, который станет известен лишь при выполнении (результат
алиаса, значение из конфига), проверит интерпретатор. Тесты держат обе
стороны: каждая находка — настоящая ошибка выполнения, а набор рабочих
сценариев проверку проходит.

```
  /srv/pg/prod.conf
    изменить   max_connections: 100 -> 200
    изменить   work_mem: 4MB -> 8MB

  /srv/pg/report.txt
    записать   файл — новый файл, 13 байт
```

Сценарий сначала проверяется, потом выполняется в режиме плана: `write`
и `save` ничего не пишут, а запоминаются. Дальше по сценарию записанное
видно — `read` того же файла вернёт новое содержимое, — иначе план
описывал бы не тот сценарий, что выполнится. Чтение файлов и живых
источников настоящее: без него планировать нечего; обращение к живому
серверу план называет отдельно.

`save` пишет файл целиком, поэтому план раскладывает его по параметрам и
показывает и удаления — в отличие от `patch`, который значения только
переносит. Порядок изменений — порядок выполнения, и у `parallel for` тоже:
действия итераций идут в порядке элементов.

### Песочница

Без флагов сценарий умеет всё, что умеет запустивший его человек. Для
сценария, который написал не человек, есть песочница:

```
ochan plan --sandbox --root ./configs --allow-env APP_ENV --allow-live postgres сценарий.ochan
ochan run  --sandbox --root ./configs сценарий.ochan
```

- файлы — только внутри `--root` (по умолчанию — текущий каталог);
  символические ссылки раскрываются до проверки, висячие отвергаются;
- переменные окружения — только перечисленные в `--allow-env`: среди них
  токен API и пароли;
- живые источники — только схем из `--allow-live`.

Отказ — ошибка с объяснением, а не пустое значение: сценарий, которому
вместо пароля подсунули пустую строку, сломался бы дальше и непонятно где.

### Заявка на сценарий

```
ochan request сценарий.ochan
ochan approve 3ff2
ochan apply --request 3ff2
```

В заявку попадают текст сценария, план, каталог, от которого отсчитываются
относительные пути, песочница и суммы файлов библиотеки, алиасы из которых
сценарий вызывает. В карточке (`ochan requests 3ff2`) и в документе `.docx`
есть и план, и текст сценария: согласуют не только план, но и то, что его
породило.

Перед выполнением план строится заново и сверяется с согласованным. Если
поправили файл, из которого сценарий строит конфиг, или алиас библиотеки,
выполнение отменяется с объяснением — согласовывали не это:

```
❌ план сценария изменился после согласования заявки 3ff2670fdd: выполнилось бы не то, что согласовали; оформите новую заявку.
Что изменилось:
  /srv/pg/prod.conf: будет записано не то содержимое, что согласовали (поменялись данные, из которых сценарий его строит)
```

Выполнение попадает в журнал, но откатить его через `rollback` пока нельзя:
запись произвольного текста журнал хранить не умеет.

### Конвейер

`a | f(b)` означает `f(a, b)` — левое значение подставляется первым
аргументом и сохраняет свой тип. Конвейер связывает крепче сравнения,
поэтому `a | b != 0` читается как `(a | b) != 0`.

## Модули команд

Модуль бывает двух видов: Go-плагин (`.hcplugin`), добавляющий новые
команды, и пакет алиасов (`.ochan`) — готовые сценарии поверх уже
существующих операций. Пакет доступен как `пакет.алиас`, короткое имя —
пока оно не занято; совпадение в двух пакетах даёт ошибку с требованием
уточнить, а не молчаливый выбор.

Пакет алиасов безопаснее Go-плагина: это текст, который видно глазами,
и он умеет ровно то, что дают встроенные функции.

Go-модуль — отдельный исполняемый файл, реализующий `pluginhost.CommandModule`
(см. `dwd/main.go`). Обвязка go-plugin и gRPC живёт в `pluginhost`.

```
go build -o test-module.hcplugin ./dwd
ochan '!install' ./test-module.hcplugin
ochan modules
```

При установке фиксируется SHA-256 модуля. При запуске загружаются только
модули с совпадающей суммой — файл, подменённый в `~/.octochan/modules`
после установки, выполнен не будет. Для разработки проверку можно отключить
через `defaults.allow_unverified_modules: true`.

В интерактивной оболочке изменившиеся модули перезагружаются автоматически;
после пересборки модуль нужно переустановить (`!install`), чтобы обновить
контрольную сумму.

## Тесты

```
go test ./... ./mcp/...
go test -race ./... ./mcp/...
go vet ./... ./mcp/...
```

`mcp/` — отдельный модуль, и шаблон `./...` в него не заходит: его нужно
назвать явно. `go.work` позволяет сделать это из корня одной командой.
