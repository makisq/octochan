# octochan

Минималистичный оркестратор для командной строки и CI. Он отвечает на
три вопроса: **что изменится**, **кто сказал «да»** и **как вернуть, как
было**, — и на четвёртый, когда серверов много: **что можно сделать без
человека**.

- **План до выполнения.** Правка конфига, сценарий исполнителя, сценарий
  на языке алиасов — сначала план, ничего не меняя.
- **Заявки и согласование.** Выполняется ровно согласованный план: перед
  выполнением он строится заново и сверяется, исполнитель получает его и
  обязан применить ровно его. Порядок между заявками (`--after`), конечное
  состояние «упала», заявку не выполнят дважды.
- **Откат.** Файлы возвращаются к прежнему содержимому; во внешней системе
  обратное действие — вторая согласованная заявка (`compensate`).
- **Цели из инвентаря.** Сценарий не перечисляет серверы: группы и хосты —
  в инвентаре (файл, CMDB, реестр агентов), `--limit` сужает.
- **Без человека — только по политике.** `ochan watch` находит новые
  хосты и выполняет сам только то, что укладывается в зарегистрированную,
  отзываемую политику; остальное — заявки.
- **Роли.** Права, запреты, области, пределы, журнал аудита с цепочкой
  хешей; системная политика ролей, которую держит root, а не владелец
  рабочего каталога.
- **Песочница ядра.** Сценарий, написанный не человеком, — под Landlock,
  seccomp и своими пространствами имён; программы — только
  перечисленные.
- **Сервер и пара.** Общий оркестратор по TLS, пара primary/standby с
  ручным переключением, машины-агенты.
- **Слой для нейросетей.** Сервер MCP без права выполнять и согласовывать;
  задачи — формальным промптом, который проверяется детерминированно: до
  работы, по плану, по слотам обобщений и по отчёту модели.

Из коробки ochan работает с конфигурациями — файлами и живым
PostgreSQL/pgbouncer; исполнитель RLM ставится модулем (`make rlm`). Это
ниши, а не предел: Linux, Ansible, Kubernetes или что угодно ещё
подключается источниками, модулями — с командами или исполнителями — и
пакетами алиасов. ochan собирают под себя — от пары алиасов до сложного
оркестратора.

Версия — **0.2.0-alpha**: [что в ней](CHANGELOG.md).

## Быстрый старт

```bash
cd octochan
make install          # или scripts/install.sh; на Windows — scripts\install.ps1
ochan --version
```

`ochan` и `ochan-mcp` ставятся в `~/.local/bin` (на Windows — в
`%LOCALAPPDATA%\Programs\ochan`, он добавляется в `PATH`) и дальше
вызываются по имени из любого каталога. Без `make` и без сети, в любой
каталог — [«Установка»](docs/guide/install.md).

Сравнить конфигурации по смыслу (`8GB` и `8192MB` равны):

```
$ ochan diff prod.conf test.conf
Найдены различия (2):
  max_connections: 100 -> 200 [Modified]
  log_min_duration_statement: — -> 1s [OnlyInRight]
```

Правка через заявку, с согласованием и откатом:

```
$ ochan plan prod.conf changes.conf
План: changes.conf -> prod.conf

Изменений: 1

  prod.conf
    изменить   max_connections: 100 -> 200

$ ochan request prod.conf changes.conf
Заявка 2a37aad7b2 создана (ждёт решения)
$ ochan approve 2a37
$ ochan apply --request 2a37
Заявка 2a37aad7b2 выполнена: /srv/pg/prod.conf, изменено параметров: 1
Откат: ochan rollback a5f046b9bd
```

Сценарий на языке алиасов — по серверам из инвентаря:

```yaml
# ~/.octochan/inventory.yaml
groups:
  db: {max_connections: 200}
hosts:
  db1: {groups: [db]}
  db2: {groups: [db], max_connections: 300}
  db3: {groups: [db, db_new], max_connections: 150}
```

```
# rollout.ochan — свой лимит соединений каждому серверу группы
отчёт = file("rollout.log")
parallel for сервер in inventory("group=db") {
    try {
        c = config("base.conf")
        put(c, "max_connections", str(сервер.max_connections))
        save(c, "out/" + сервер.host + ".conf")
        print(отчёт, сервер.host, "готов")
    } catch ошибка {
        print(отчёт, сервер.host, "ПРОПУЩЕН:", ошибка)
    }
}
```

```
$ ochan check rollout.ochan
rollout.ochan: ошибок не найдено
$ ochan plan rollout.ochan --limit group=db_new
План: rollout.ochan -> —

Изменений: 3

  /srv/configs/out/db3.conf
    добавить   max_connections = 150
    добавить   shared_buffers = 4GB

  /srv/configs/rollout.log
    записать   файл — новый файл, 15 байт
$ ochan request rollout.ochan --sandbox      # согласование, затем apply --request и откат
```

Без аргументов на терминале `ochan` открывает интерактивную оболочку.
Ненулевой код возврата означает ошибку — команды пригодны для CI.

## Статус безопасности

Это альфа, и на что в ней можно рассчитывать, лучше знать заранее:

- **Песочница** (`--sandbox`) — две стены. Встроенные функции проверяют
  пути, окружение, сеть и живые источники, а на Linux сценарий ещё и
  выполняется отдельным процессом под ограничениями ядра: Landlock (файлы,
  запуск программ), seccomp (системные вызовы), свои пространства имён
  (пользователь, сеть, процессы). Не поставилось ограничение — сценарий не
  выполняется. На macOS и Windows — отдельный процесс без окружения, а
  файлы и сеть держит только язык; ochan об этом предупреждает,
  `sandbox.strict: true` превращает предупреждение в отказ. `--allow-exec`
  ограничивает запуск, а не поведение программы. Модули — обычные
  исполняемые файлы, песочницей не ограничены; их защита — контрольная
  сумма.
- **Роли** без системной политики защищают от ошибки и ограничивают
  нейросеть, но не владельца рабочего каталога: кто может изменить
  `~/.octochan`, тот master. Системная политика `/etc/octochan/roles.yaml`
  закрепляет роли за пользователями ОС, но ограничивает ochan, а не
  человека: то, что нужно защитить от него, держат у сервера под
  отдельным пользователем ОС. На общем сервере роли — граница между
  людьми: области, запреты, пределы, разделение обязанностей и журнал
  аудита.
- **Пара серверов** не переключается сама и не обещает консенсуса:
  переключает человек, эпоха не даёт бывшему primary писать дальше.
- **Серверный режим, пара и MCP по HTTP** (вход, сессии, TLS, токены,
  копия состояния) независимого аудита не проходили. Не выставляйте их в
  недоверенную сеть и не используйте с боевыми паролями, пока код не
  посмотрит кто-то, кроме автора.
- **Не проверялось вживую:** модуль RLM работал только против поддельного
  API; тесты под macOS не запускались (только сборка); песочница ядра
  проверена на Linux 6.x x86-64, на arm64 — только сборка; пара серверов —
  двумя процессами на одной машине.

Единственное, на что альфа рассчитана твёрдо: нейросеть через `ochan-mcp`
не может ничего выполнить и согласовать — для этого нужен человек.
Подробнее — [«Безопасность»](docs/guide/security.md).

## Устройство

```
config  inventory  lang  fp  arbiter  rings  i18n  logs  rbac  audit  sandbox
remote  pluginhost  runnerhost  scenario  pgsource  workspace  report  cmd
mcp/ — отдельный Go-модуль        plugins/rlm — модуль RLM, ядро его не импортирует
```

`config` не зависит ни от чего; СУБД и RLM — ниши, а не фундамент; ИИ —
модуль, а не основа. Подробно — [«Как устроен ochan»](docs/guide/concepts.md).
