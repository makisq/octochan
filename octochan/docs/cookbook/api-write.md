# Запрос в API из сценария

**Задача.** Сценарий проверяет состояние и, если нужно, заводит тикет в
трекере, ставит задачу в CI, создаёт тикет в API. Это запись во внешнюю
систему. Сценарий в ochan по умолчанию только читает, а записывать должен
явно и так, чтобы запрос видел человек, который его согласует.

Здесь API — демонстрационный HTTP-сервер на `127.0.0.1:18731`. Он
принимает `POST /v1/tickets`, отвечает `201 {"id": 42}` и записывает
каждый запрос в журнал.

## 1. Сценарий

```
# Завести заявку в трекере, если диск заполнен больше чем на 90%.
let used = int(trim(read("disk.txt")))
if used > 90 {
    var r = curl("http://127.0.0.1:18731/v1/tickets",
                 {"method": "POST", "allow_write": true,
                  "body": {"title": "диск заполнен", "used": used}})
    print("ответ:", r["status"], r["body"])
}
```

- **`"allow_write": true`** — без него `POST`, `PUT`, `PATCH` и `DELETE`
  не отправляются;
- **`"body"`** — словарь или список уходят как JSON (с `Content-Type:
  application/json`), строка — как есть;
- **`fetch`** — то же, только он возвращает тело ответа, а `curl` — ответ
  целиком.

Забыли `allow_write` — сценарий остановится и скажет, как писать:

```
ошибка: bad.ochan:1:6: метод POST: сценарий только читает (GET, HEAD); запрос, который меняет внешнюю систему, — с "allow_write": true: ochan plan покажет его, а выполнит run с правом apply
```

## 2. План: запрос виден и не отправлен

```
$ echo 93 > disk.txt
$ ochan plan ticket.ochan
ответ: 0 

План: ticket.ochan -> —

Изменений: 1

  127.0.0.1:18731
    запрос     POST http://127.0.0.1:18731/v1/tickets — тело 47 байт; в плане не отправляется; не откатывается
```

План выполняет сценарий, но меняющий запрос не отправляет. `curl`
возвращает в нём `status` 0, `fetch` возвращает пустую строку. Журнал
сервера пуст. Тела в плане нет, только его размер: в теле бывают токены.

## 3. Заявка, согласование, выполнение

```
$ ochan request ticket.ochan
План: ticket.ochan -> —
…
    запрос     POST http://127.0.0.1:18731/v1/tickets — тело 47 байт; в плане не отправляется; не откатывается

Согласовать: ochan approve 8506a014b6
$ ochan approve 8506a014b6
Заявка 8506a014b6: согласована (root, роль master)
Выполнить: ochan apply --request 8506a014b6
$ ochan apply --request 8506a014b6
Заявка 8506a014b6, сценарий ticket.ochan
ответ: 201 {"id": 42}
Заявка 8506a014b6 выполнена, записано файлов: 0
```

Сервер получил ровно один запрос:

```
POST /v1/tickets {"title":"диск заполнен","used":93}
```

## 4. Данные поменялись после согласования

Заявка хранит текст сценария, а перед выполнением строит план заново и
сверяет его с согласованным: метод, адрес и тело каждого запроса. Если
`disk.txt` изменился, тело уже другое, и заявка не выполнится:

```
$ echo 95 > disk.txt
$ ochan apply --request 84dc146cb5
ошибка: план сценария изменился после согласования заявки 84dc146cb5: выполнилось бы не то, что согласовали; оформите новую заявку.
Что изменилось:
  POST http://127.0.0.1:18731/v1/tickets: тело запроса не то, что согласовали
Текущий план:
План: ticket.ochan -> —

Изменений: 1

  127.0.0.1:18731
    запрос     POST http://127.0.0.1:18731/v1/tickets — тело 47 байт; в плане не отправляется; не откатывается
```

Запрос не отправлен.

## Подводные камни

- **Откатить запрос ochan не может.** `ochan rollback` возвращает только
  файлы. Обратное действие в API пишут отдельным сценарием (`DELETE`) или
  делают исполнителем с `compensate`, см.
  [«Обратное действие»](../guide/requests.md#обратное-действие-во-внешней-системе).
- **`run` выполняет сразу**, без заявки, и требует права `apply`. Роль
  `llm` выполнить запрос не может: она получает только план и заявку.
- **В песочнице** запрос уходит только на хосты из `--allow-net`, как и
  чтение.
- **Токен — не в тексте сценария.** Сценарий читает его из окружения
  через `env()`; в песочнице переменную нужно разрешить флагом
  `--allow-env`. Заголовки в план не попадают.
- **Ответ зависит от времени.** Если тело строится из живых данных,
  согласованная заявка выполнится, только пока данные те же. Это и есть
  защита.
