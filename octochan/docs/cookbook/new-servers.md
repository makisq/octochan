# Новые серверы без человека: слежение и политика

**Задача.** В CMDB появляются новые серверы базы. Каждому нужно применить
одну и ту же настройку, и ждать человека ради этого не хочется. Но и
отдать роботу право делать что угодно тоже нельзя: без человека должно
выполняться только заранее согласованное, а всё прочее — становиться
заявками.

Исполнитель в рецепте — демонстрационный модуль `examples/runnermodule`
(сервис `demo`): он ничего не меняет, а только создаёт задачи. С модулем
RLM и его сервисами всё то же самое.

## 1. Инвентарь, сценарий, политика

```yaml
# /srv/cmdb.yaml — выгрузка CMDB
groups:
  db: {max_connections: 200}
hosts:
  db1: {groups: [db], svm_ci: CI001}
  db2: {groups: [db], svm_ci: CI002}
```

```yaml
# ~/.octochan/config.yaml
inventory:
  sources:
    cmdb: /srv/cmdb.yaml
```

```yaml
# tune.yaml — цели из инвентаря, а не списком в сценарии
service: demo
parameters: {max_connections: 300}
targets:
  - group: db
```

```yaml
# new-servers.yaml — что выполнять без человека
name: new-servers
scenario: tune.yaml
targets: [group=db_new]      # только хосты группы db_new
params:
  max_connections: 100..500  # и только с таким значением
expires: 2026-12-31          # срок обязателен
```

Существующие серверы отмечаем увиденными, чтобы слежение их не трогало, и
регистрируем политику. Регистрация — заранее данное согласование, поэтому
это право `approve`:

```
$ ochan '!!install' demo-runner.hcplugin
$ ochan inventory ack
  db1 (cmdb)
  db2 (cmdb)
Отмечены увиденными: 2

$ ochan policy add new-servers.yaml
Политика new-servers зарегистрирована.

Политика:  new-servers — действует по 2026-12-31 включительно
Сценарий:  /srv/tune.yaml (сервис demo)
Цели:      group=db_new
Параметр:  max_connections: 100..500
Добавил:   root, роль master, 2026-10-29 14:56
Файл:      /srv/new-servers.yaml (sha256 8baf2d3abc02…)

Отозвать: ochan policy revoke new-servers
```

Слежение пойдёт под отдельной ролью: она оформляет заявки и выполняет, но
не согласует и не регистрирует политики.

```
$ ochan role create robot --allow read,request,apply
Роль robot создана: read, request, apply
```

## 2. Пришли новые серверы

В CMDB добавились `db7` (группа `db_new`), `db8` (только `db`) и `web3`:

```
$ ochan inventory --new
Источник cmdb: /srv/cmdb.yaml

+ db7              db, db_new               max_connections=200 svm_ci=CI007
+ db8              db                       max_connections=200 svm_ci=CI008
+ web3             web                      svm_ci=CI103

Хостов: 3, новых: 3 (+)

$ OCTOCHAN_ROLE=robot ochan watch --source cmdb --policy new-servers
2026-10-29 14:56  cmdb: хостов 5, новых 3
  db7: заявка 6160f7c6a2 в политике new-servers — выполняется
Заявка 6160f7c6a2, сервис demo, исполнитель Demo
Создано:
  - demo-CI007: max_connections = 300
  db7: заявка 6160f7c6a2 согласована политикой new-servers и выполнена
  db8: заявка 9c20a69ffe ждёт решения — вне политики new-servers: хост не подходит под targets (group=db_new)
  web3: сценарий этот хост не выбирает — отмечен увиденным
```

- **db7** подошёл под политику целиком: заявка оформлена, согласована
  политикой и выполнена — обычным путём, со сверкой плана.
- **db8** сценарий выбирает, но политика на него не распространяется:
  заявка ждёт человека, и причина напечатана.
- **web3** сценарий не выбирает вовсе — делать нечего.

Каждый новый хост получает свою заявку на сценарий, суженный до него
(`--limit host=db7`). Кто её согласовал, видно в карточке:

```
$ ochan requests 6160
Заявка:    6160f7c6a2
Состояние: выполнена
Автор:     ochan watch (root), роль robot
Создана:   2026-10-29 14:56:19
Источник:  /srv/tune.yaml
Сервис:    demo
Цели:      --limit host=db7
Итог:      demo через Demo, операций: 1; новый хост db7 (cmdb)
Решение:   выполнена, политика new-servers (зарегистрировал root, роль master) (2026-10-29 14:56:19)
Коммент.:  хост db7 под group=db_new, параметры в пределах политики
Выполнена: 2026-10-29 14:56:19
...
```

В журнале аудита выполнение по политике — `apply` роли `robot`, с её
пределом частоты:

```
$ ochan audit --role robot
+ 2026-10-29 14:56:19  robot      root             watch --policy=new-servers --source=cmdb
+ 2026-10-29 14:56:19  robot      root             apply --policy=new-servers --source=cmdb --request 6160f7c6a2
```

Заявку на `db8` решает человек, как любую другую:

```
$ ochan approve 9c20 --comment "db8 проверил"
Заявка 9c20a69ffe: согласована (root, роль master)
Выполнить: ochan apply --request 9c20a69ffe
$ ochan apply --request 9c20
Заявка 9c20a69ffe, сервис demo, исполнитель Demo
Создано:
  - demo-CI008: max_connections = 300
```

## 3. Политика держит значения, а не только хосты

Кто-то поправил сценарий: `max_connections: 900`. Новый сервер `db9` в
группе `db_new` — но значение вне политики:

```
$ OCTOCHAN_ROLE=robot ochan watch --source cmdb --policy new-servers
2026-10-29 14:56  cmdb: хостов 6, новых 1
  db9: заявка 495888abaa ждёт решения — вне политики new-servers: параметр max_connections = 900 вне допустимого (100..500)

$ ochan reject 4958 --reason "900 соединений много" --reason-kind scope
Заявка 495888abaa: отклонена (root, роль master)
```

Политика согласует заявку, только если укладывается всё сразу: хост
подходит под `targets`, каждый параметр сценария есть в `params` и его
значение допустимо, сервис тот же, план не прерывает обслуживание, у роли
слежения есть `apply` и не исчерпан её предел, а политику регистрировала
другая роль (кроме master).

## 4. Отзыв

```
$ ochan policy revoke new-servers --reason "миграция закончилась"
Политика new-servers отозвана (root, роль master). ochan watch больше ничего не выполняет по ней сам.

$ OCTOCHAN_ROLE=robot ochan watch --source cmdb --policy new-servers
2026-10-29 14:56  cmdb: хостов 7, новых 1
  Выполнение без человека выключено: политика new-servers отозвана 2026-10-29 14:56 (root, роль master): миграция закончилась. Всё станет заявками.
  db10: заявка 709a905072 ждёт решения

$ ochan policy
new-servers      политика new-servers отозвана 2026-10-29 14:56 (root, роль master): миграция закончилась
                 цели group=db_new; параметры max_connections

$ OCTOCHAN_ROLE=robot ochan policy add new-servers.yaml
ошибка: роль robot не может выполнять policy add: нужно право approve
```

Отзыв и срок действуют со следующего прохода. Сама роль слежения
вернуть себе политику не может.

## По расписанию

Один проход — для cron:

```
*/10 * * * * OCTOCHAN_ROLE=robot ochan watch --source cmdb --policy new-servers
```

Или процесс, который проходит сам: `ochan watch … --every 10m`; политика
перечитывается на каждом проходе. Без `--policy` (`--scenario tune.yaml`)
слежение только оформляет заявки — так начинают, пока политики нет.

## Подводные камни

- **Правка файла политики — не регистрация.** Зарегистрированная
  политика хранит сумму файла; разошлись — отказ. Поменять политику —
  отозвать и зарегистрировать заново.
- **Хост, у которого не построился план, не отмечается увиденным**:
  следующий проход попробует снова.
- Политики лежат в `~/.octochan/policies` и от владельца рабочего каталога
  не защищены. Слежение, которому нельзя доверить свой каталог, держат на
  сервере под отдельным пользователем ОС.
- Источником может быть и реестр агентов (`agents://online`): тогда новый
  хост — машина, которая сама сообщила о себе
  ([«Пара серверов и агенты»](ha-pair.md)).
