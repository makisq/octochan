# Нейросети и формальный промпт

Нейросеть работает с ochan как ещё один слой абстракции, а не собеседник:
задачу ей ставят формальным промптом, она пишет сценарий и оформляет
заявку, а между каждым её шагом и исполнением стоит детерминированная
проверка. Выполняет и согласует — человек. Идея — в манифесте формального
промптирования ([formal-prompting.md](../formal-prompting.md)).

```
оператор: формальный промпт
   │
   ▼
модель ── check_prompt ──► ⊥syn ⊥ambig ⊥undef ⊥conflict?  — отказ возвращается оператору
   │
   ├── check_script ──► ошибки сценария до выполнения
   ├── plan_script (+ prompt, report) ──► план + жёсткие правила по плану
   └── request_script ──► заявка «ждёт решения»: сценарий, план, промпт, отчёт
                                   │
человек: ochan requests <id> ──► approve ──► apply --request ──► rollback при нужде
```

## Формальный промпт

Язык, на котором оператор описывает задачу модели: цель, классы, отношения,
приоритеты, обобщения со слотами, требуемое знание, скиллы, жёсткие
правила, ячейки-правки и отчёт модели. Полное описание — протокол
(`ochan fp protocol`, [fp/protocol.md](../../fp/protocol.md)); он
по-английски, потому что его читает модель. Пример —
[examples/fp/connections.fp](../../examples/fp/connections.fp).

```
# Поднять лимит соединений на prod, ничего другого не записывая.
goal: tuned

classes:
  Goal   : "tuned"
  Config : "config"

relations:
  Config --strives_to--> Goal

import @pgconf v1
  provides: Config, set_param, store
  requires_class: Config

hard forbid store(except = {prod_conf})
hard forbid write()
```

```
$ ochan fp check task.fp
task.fp: P ∈ ℒ, слова однозначны, Req(P) ⊆ K, жёсткие правила совместны
Цель γ:  Goal
K:       set_param, store
```

Проверки выполняются до модели и детерминированы — поиск по таблицам и
сравнение множеств:

| Проверка | Отказ |
|---|---|
| Текст принадлежит языку: заголовок `goal:`, известные разделы, словарь отношений, никаких приращений, вопросов и свободного текста | `⊥syn` |
| Слово означает не больше k классов, и место употребления выбирает один смысл | `⊥ambig` |
| Req(P) ⊆ K: требования, операции обобщений и действия правил есть в отношениях или скиллах | `⊥undef` |
| Жёсткие правила совместны: «никогда X» и «всегда X» вместе — противоречие (Ж3), если требование не лежит внутри исключений запрета | `⊥conflict` |
| Граф: классы объявлены, приоритеты без циклов, имена не повторяются | `⊥undef`, `⊥conflict` |
| Обобщения и частные случаи: слоты существуют, заполнены все, значения из домена | `⊥syn`, `⊥undef` |
| Ячейки: зависимости по чтению и записи, ссылки только назад | `⊥undef` или замечание |
| Отчёт: выбор из альтернатив, основание есть в промпте, заданное промптом не переопределено | `⊥conflict`, `⊥undef` |

**Отказ с подсказкой.** Отказ называет законный путь — то, что нужно
попросить у оператора, — той же детерминированной проверкой: скилл
библиотеки, в котором есть недостающая операция, похожее имя, версию,
раздел протокола.

```
$ ochan fp check задача.fp
задача.fp:10:1: ⊥undef: действие set_param неизвестно ни скиллам, ни отношениям: арбитру нечем проверить правило по плану (Ж1)
    подсказка: set_param есть в @pgconf v1.2.0 — подключите: import @pgconf v1.2.0 (протокол, «Knowledge: requirements and skills»)
```

Запрет и требование одного действия совместны, когда требование
действует только внутри исключений запрета:

```
hard forbid restart(except = {maintenance_window})
hard require restart(scope = maintenance_window)
```

**Скилл — пакет алиасов.** `import @pgconf v1` ищется среди пакетов
`~/.octochan/modules`, а операции скилла — его алиасы: проверка не верит
объявлению на слово. Версия сверяется с манифестом пакета по началу номера:
`v1` подходит под 1.2.0, `v1.3` — нет. С `--standalone` скилл даёт то,
что объявлено в его `provides:`.

**Маркер жёстких правил — `??`, а не `!`.** `!` занят командами ochan
(`!install`) и в C-подобных языках читается как отрицание. Правило пишется
`??n_действие(…)` (никогда) или `??a_действие(…)` (всегда), либо словами:
`hard forbid` и `hard require`.

Настройки — в `config.yaml`, а не в промпте:

```yaml
fp:
  max_meanings: 3         # k: сколько классов может означать слово
  consistency: strict     # strict (λ1) или reconcile (λ0)
  quiet: [fuel_policy]    # Q_off: вопросы, о которых не сообщать
```

## Жёсткие правила по плану

Промпт и отчёт модели передаются вместе со сценарием:

```
ochan plan    raise.ochan --prompt task.fp --report report.fp
ochan request raise.ochan --prompt task.fp --report report.fp
```

Промпт и отчёт проверяются до плана — как `ochan fp check`, — а жёсткие
правила проверяются **по плану**: какие файлы сценарий записал бы и какие
алиасы вызвал. Действие правила — `write`, `save` или алиас; исключения
и область сравниваются с именами целей (файл `prod.conf` — `prod_conf`,
`/srv/web-1.conf` — `web_1_conf`):

```
Отчёт модели:
  limit: double из {double, triple} — not_in_prompt

Жёсткие правила промпта:
  соблюдено  hard forbid store(except = {prod_conf})
  НАРУШЕНО   hard forbid write()
             write в /srv/pg/note.txt (note_txt)
             подсказка: write запрещено без исключений: сценарий не должен его вызывать (протокол, «Hard rules»)
ошибка: план нарушает жёсткие правила промпта: hard forbid write()
```

Подсказка у нарушения говорит, что правило допускает: цели из `except`,
цели `scope`, которые требование должно покрыть. Менять правило она не
предлагает — правило задаёт оператор.

- `hard forbid X(except = {…})` нарушает запись `X` в цель вне исключений;
  `hard forbid X()` — любая запись `X`. Если `X` — алиас, исключение
  оправдывает только то, что вызов записал: вызов, который ничего не
  записал, оправдать нечем.
- `hard require X(scope = …)` требует, чтобы `X` был в плане и покрыл
  каждую цель области: записал её или получил аргументом
  (`verify(config("prod.conf"))` покрывает `prod_conf`).
- Печать в файл — тоже `write`.

Сценарий по промпту берёт «как» только из того, что промпт подключил:
алиас пакета без `import @пакет` в промпте или операция, которой нет в
`provides:`, — отказ до плана (П5):

```
ошибка: сценарий выходит за знание промпта (П5):
  сценарий использует pgconf.set_param, pgconf.store, а промпт не подключает @pgconf
      подсказка: добавьте в промпт import @pgconf v1.2.0 — или обойдитесь операциями подключённых скиллов
```

```
ошибка: сценарий выходит за знание промпта (П5):
  сценарий вызывает pgconf.set_param, а в provides: промпта для @pgconf её нет
      подсказка: добавьте set_param в provides: import @pgconf — или обойдитесь операциями из provides:
```

План, который нарушает правило, — ошибка, и заявка на него не создаётся.
В заявку попадают промпт, отчёт и соблюдённые правила; согласующий видит
задачу и решения, которые модель приняла сама («Отчёт модели»), в
карточке и в `.docx`. Перед выполнением промпт и правила проверяются
снова: если скилл сменил версию, выполнение отменяется.

Через stdin приходит один текст, поэтому сценарий, промпт и отчёт вместе
подаются JSON-объектом с `--bundle` — так их передаёт `ochan-mcp`:

```
echo '{"script": "…", "prompt": "…", "report": "…"}' | ochan request --script --bundle -
```

## Кольца: well_True и well_False

Модель выдаёт вероятности, а арбитр отвечает «да» или «нет». Кольца —
цепочка фильтров между ними (раздел 6.2 манифеста ФПм). В ochan они
работают в **режиме протокола**: модель доступна только готовым
сценарием, и кольца судят утверждения его плана. Утверждение — то, что
написала модель: вызов операции скилла (`pgconf.store(…)`) или запись
`write`/`save` вне скиллов. Что скилл делает внутри, — реализация из
библиотеки, а не утверждение модели.

- **Кольцо 1** — интервал поддержки утверждения: надёжность его правила
  (операции скилла или `write`/`save`) по журналу решений, 95-процентный
  интервал бета-распределения.
- **Кольцо 2** — бинаризация: нижняя граница поддержки сравнивается с
  порогом `well_True`. Не дотянуло — `well_False`: утверждение отбрасывается
  целиком и в кольцо 3 не идёт даже отрицанием.
- **Кольцо 3** — булева проверка прошедших утверждений: запись, которую
  запрещает `hard forbid`, — противоречие.
- **Арбитр** — внешнее кольцо: все жёсткие правила по плану целиком.

План неделим: одно отвергнутое утверждение — и план не проходит, заявки
на него нет.

```
Кольца (режим протокола, порог well_True 0.50):
  well_True     pgconf.set_param(prod.conf, max_connections, 400)
  well_True     pgconf.store(prod.conf, prod.conf)
  well_False    pgconf.reload(prod)
                правило pgconf.reload проверено мало для порога; принять утверждение без проверки может оператор: --trust pgconf.reload
  противоречие  write /srv/pg/note.txt
                hard forbid write(): write в /srv/pg/note.txt (note_txt)
                нарушение запрета — на счёт модели и промпта: надёжность правила write не меняется

Жёсткие правила промпта:
  НАРУШЕНО   hard forbid write()
             write в /srv/pg/note.txt (note_txt)
             подсказка: write запрещено без исключений: сценарий не должен его вызывать (протокол, «Hard rules»)
ошибка: план нарушает жёсткие правила промпта: hard forbid write(); кольца отвергли утверждений: 2 из 4
```

Арбитр смотрит план и тогда, когда кольца его уже отвергли: модель
получает все причины разом, а не по одной за попытку.

**Журнал решений** (`~/.octochan/decisions`) — единственный источник
чисел. Каждый план по промпту пишется туда с решением колец и арбитра, а
потом с решением оператора. Исход ложится на правила так:

- нарушение запрета — противоречие кольца 3 или отказ арбитра по
  `hard forbid` — на счёт модели и промпта, а не правил скиллов: модель
  применила операцию там, где промпт её запретил, и это не говорит о
  ненадёжности самой операции. Соседи по плану с чужой ошибкой до суда не
  дошли;
- нарушенное `hard require`, отказ оператора (`reject`) и откат
  (`rollback`) — неудача всех утверждений плана: виновного не назвать;
- согласование (`approve`) — успех всех утверждений плана;
- отказ кольца 2 — не исход: иначе журнал подтверждал бы сам себя.

Успех засчитывает только оператор, поэтому модель не накрутит надёжность,
показывая планы. И не обрушит её: планы с нарушениями запретов, сколько
их ни показывай, на надёжность скиллов не влияют. Один и тот же план
считается один раз.

Частоту самих планов модели ограничивает предел роли `llm` —
`roles.llm.limits` в `config.yaml`, по умолчанию `plan=60/1h`
([«Пределы»](roles.md#пределы)).

Пока журнала нет, действует **условный счёт** — «как будто правило
применялось столько-то раз, и столько-то из них прошли»:
`fp.rings.prior` (по умолчанию `8/8`, это `[0,66; 1,00]`) или
`prior.<алиас>` в манифесте пакета:

```yaml
# ~/.octochan/modules/pgconf/package.yaml
version: 1.2.0
prior.set_param: 8/8
prior.reload: 1/4
```

Условный счёт — заявление автора скилла: ставя пакет, оператор ему
доверяет. `prior.` для алиаса, которого в пакете нет, — ошибка загрузки.

Оператор может принять утверждение сам: `--trust pgconf.reload` пропускает
утверждения правила через кольцо 2 (не через кольцо 3 и не мимо
арбитра). Модели флаг недоступен: роль `llm` получает отказ, а `ochan-mcp`
его не передаёт.

**Бюджет.** Модель не перебирает варианты, пока какой-нибудь не проскочит:
после `fp.rings.budget.plan` отказов подряд по одному промпту и после
второго отказа по той же причине ochan план не проверяет и зовёт
оператора. Оператор уточняет промпт — новый текст начинает новый счёт.

**Оценки скрыты.** Интервалы по умолчанию не печатаются
(`fp.rings.show_scores: false`): согласующий, который видит оценку,
согласует по ней, и его решение уже не годится для калибровки.
`ochan fp journal` показывает надёжность правил и калибровку — долю
верных планов при каждой поддержке:

```
Журнал решений: планов 2, с исходом 2, верных 1

Правило                      верных/исходов  надёжность
  pgconf.set_param                 1/1       [0.69; 1.00]
  pgconf.store                     1/1       [0.69; 1.00]
  write                            0/0       [0.66; 1.00]

Нарушения запретов — на счёт модели и промпта:
  роль llm                   планов 1, с нарушением 1
  роль master                планов 1, с нарушением 0
  промпт task.fp (9a8c885a)  планов 2, с нарушением 1

Калибровка — поддержка плана и доля верных:
  0.3–0.4  планов 1, верных 0 %
  0.4–0.5  планов 1, верных 100 %
```

Здесь оператор согласовал один план, а модель показала второй — с
записью, которую промпт запрещает. Правило `write` осталось без исхода,
нарушение записано на роль `llm` и на промпт. Для калибровки план с
нарушением — неверный план.

```yaml
fp:
  rings:
    enabled: true
    well_true:
      plan: 0.5     # порог для ochan plan
      apply: 0.6    # порог для заявки — на выполнение
    prior: "8/8"
    show_scores: false
    budget:
      plan: 3       # 0 — без предела
```

Встроенного режима (кольцо 0 — порог на вероятность токена — и выбор
между кандидатами) у ochan пока нет: для него нужна модель, распределение
которой видно. Математика для него уже в пакете `rings`.

## Сервер MCP

`ochan-mcp` даёт модели ochan через MCP: читать, планировать, писать
сценарии и оформлять заявки — и ничего не выполнять.

```json
{
  "mcpServers": {
    "octochan": {
      "command": "/usr/local/bin/ochan-mcp",
      "args": ["--root", "/srv/configs"]
    }
  }
}
```

- При подключении модель первой получает протокол — в `instructions`.
  Протокол, заголовки и описания инструментов — по-английски при любом
  `lang`; вывод инструментов — на языке оператора.
- Таблица инструментов закрыта: `apply`, `approve`, `rollback`, `run`,
  `eval`, `patch`, `!install` в неё не входят, и проверка таблицы при
  запуске не даст их добавить.
- Файлы — только внутри `--root`; живые источники и переменные окружения —
  только разрешённые (`--allow-live`, `--allow-env`). Сценарии модели
  выполняются в песочнице ochan с теми же границами.
- `ochan` под сервером работает в роли `llm`: даже ошибка в таблице не
  даст модели выполнить изменение — откажет сам `ochan`.
- У `llm` пределы — 30 заявок и 60 планов в час, а её заявку согласуют,
  только посмотрев план: подсунутая модели инструкция не завалит людей заявками и не
  рассчитает на согласование не глядя.

### Модель не на этой машине

С `--listen` сервер говорит по Streamable HTTP, и к нему подключаются
модели поставщиков: коннектор MCP в Claude API, инструмент `mcp` в OpenAI
Responses API, ChatGPT, Claude.ai, Gemini CLI и любая программа на MCP SDK.

```
ochan-mcp --root /srv/configs --listen 127.0.0.1:8765     # за прокси или туннелем с TLS
```

Каждый запрос — с токеном (`~/.config/ochan-mcp/token` создаётся при
первом запуске), на сетевом адресе — только по TLS, запросы из браузера —
только с разрешённых Origin. Инструменты и роль те же, что по stdio, а в
журнале аудита вызовы удалённой модели видны с адресом клиента. Готовые
конфиги для каждого клиента — в [mcp/clients/](../../mcp/clients/),
пошагово — рецепт [«Модель в облаке и конфиги на своей машине»](../cookbook/remote-llm.md).

Инструменты, флаги и устройство — в [mcp/README.md](../../mcp/README.md).
Пошагово — рецепт [«Нейросеть пишет сценарий по формальному промпту»](../cookbook/ai-script.md).
