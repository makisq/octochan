# Нейросети и формальный промпт

Нейросеть работает с ochan как ещё один слой абстракции, а не собеседник:
задачу ей ставят формальным промптом, она пишет сценарий и оформляет
заявку, а между каждым её шагом и исполнением стоит детерминированная
проверка. Выполняет и согласует — человек. Идея — в манифесте формального
промптирования ([md](../formal-prompting.md), [pdf](../formal-prompting.pdf)).

```
оператор: формальный промпт
   │
   ▼
модель ── check_prompt ──► ⊥syn ⊥ambig ⊥undef ⊥conflict?  — отказ возвращается оператору
   │
   ├── check_script ──► ошибки сценария до выполнения
   ├── plan_script (+ prompt, report) ──► план + жёсткие правила по плану
   └── request_script ──► заявка «ждёт решения»: сценарий, план, промпт, отчёт
                                   │
человек: ochan requests <id> ──► approve ──► apply --request ──► rollback при нужде
```

## Формальный промпт

Язык, на котором оператор описывает задачу модели: цель, классы, отношения,
приоритеты, обобщения со слотами, требуемое знание, скиллы, жёсткие
правила, ячейки-правки и отчёт модели. Полное описание — протокол
(`ochan fp protocol`, [fp/protocol.md](../../fp/protocol.md)); он
по-английски, потому что его читает модель. Пример —
[examples/fp/connections.fp](../../examples/fp/connections.fp).

```
# Поднять лимит соединений на prod, ничего другого не записывая.
goal: tuned

classes:
  Goal   : "tuned"
  Config : "config"

relations:
  Config --strives_to--> Goal

import @pgconf v1
  provides: Config, set_param, store
  requires_class: Config

hard forbid store(except = {prod_conf})
hard forbid write()
```

```
$ ochan fp check task.fp
task.fp: P ∈ ℒ, слова однозначны, Req(P) ⊆ K, жёсткие правила совместны
Цель γ:  Goal
K:       set_param, store
```

Проверки выполняются до модели и детерминированы — поиск по таблицам и
сравнение множеств:

| Проверка | Отказ |
|---|---|
| Текст принадлежит языку: заголовок `goal:`, известные разделы, словарь отношений, никаких приращений, вопросов и свободного текста | `⊥syn` |
| Слово означает не больше k классов, и место употребления выбирает один смысл | `⊥ambig` |
| Req(P) ⊆ K: требования, операции обобщений и действия правил есть в отношениях или скиллах | `⊥undef` |
| Жёсткие правила совместны: «никогда X» и «всегда X» вместе — противоречие (Ж3) | `⊥conflict` |
| Граф: классы объявлены, приоритеты без циклов, имена не повторяются | `⊥undef`, `⊥conflict` |
| Обобщения и частные случаи: слоты существуют, заполнены все, значения из домена | `⊥syn`, `⊥undef` |
| Ячейки: зависимости по чтению и записи, ссылки только назад | `⊥undef` или замечание |
| Отчёт: выбор из альтернатив, основание есть в промпте, заданное промптом не переопределено | `⊥conflict`, `⊥undef` |

**Скилл — пакет алиасов.** `import @pgconf v1` ищется среди пакетов
`~/.octochan/modules`, а операции скилла — его алиасы: проверка не верит
объявлению на слово. Версия сверяется с манифестом пакета по началу номера:
`v1` подходит под 1.2.0, `v1.3` — нет. С `--standalone` скилл даёт то,
что объявлено в его `provides:`.

**Маркер жёстких правил — `??`, а не `!`.** `!` занят командами ochan
(`!install`) и в C-подобных языках читается как отрицание. Правило пишется
`??n_действие(…)` (никогда) или `??a_действие(…)` (всегда), либо словами:
`hard forbid` и `hard require`.

Настройки — в `config.yaml`, а не в промпте:

```yaml
fp:
  max_meanings: 3         # k: сколько классов может означать слово
  consistency: strict     # strict (λ1) или reconcile (λ0)
  quiet: [fuel_policy]    # Q_off: вопросы, о которых не сообщать
```

## Жёсткие правила по плану

Промпт и отчёт модели передаются вместе со сценарием:

```
ochan plan    raise.ochan --prompt task.fp --report report.fp
ochan request raise.ochan --prompt task.fp --report report.fp
```

Промпт и отчёт проверяются до плана — как `ochan fp check`, — а жёсткие
правила проверяются **по плану**: какие файлы сценарий записал бы и какие
алиасы вызвал. Действие правила — `write`, `save` или алиас; исключения
и область сравниваются с именами целей (файл `prod.conf` — `prod_conf`,
`/srv/web-1.conf` — `web_1_conf`):

```
Отчёт модели:
  limit: double из {double, triple} — not_in_prompt

Жёсткие правила промпта:
  соблюдено  hard forbid store(except = {prod_conf})
  НАРУШЕНО   hard forbid write()
             write в /srv/pg/note.txt (note_txt)
ошибка: план нарушает жёсткие правила промпта: hard forbid write()
```

- `hard forbid X(except = {…})` нарушает запись `X` в цель вне исключений;
  `hard forbid X()` — любая запись `X`. Если `X` — алиас, исключение
  оправдывает только то, что вызов записал: вызов, который ничего не
  записал, оправдать нечем.
- `hard require X(scope = …)` требует, чтобы `X` был в плане и покрыл
  каждую цель области: записал её или получил аргументом
  (`verify(config("prod.conf"))` покрывает `prod_conf`).
- Печать в файл — тоже `write`.

План, который нарушает правило, — ошибка, и заявка на него не создаётся.
В заявку попадают промпт, отчёт и соблюдённые правила; согласующий видит
задачу и решения, которые модель приняла сама («Отчёт модели»), в
карточке и в `.docx`. Перед выполнением промпт и правила проверяются
снова: если скилл сменил версию, выполнение отменяется.

Через stdin приходит один текст, поэтому сценарий, промпт и отчёт вместе
подаются JSON-объектом с `--bundle` — так их передаёт `ochan-mcp`:

```
echo '{"script": "…", "prompt": "…", "report": "…"}' | ochan request --script --bundle -
```

## Сервер MCP

`ochan-mcp` даёт модели ochan через MCP: читать, планировать, писать
сценарии и оформлять заявки — и ничего не выполнять.

```json
{
  "mcpServers": {
    "octochan": {
      "command": "/usr/local/bin/ochan-mcp",
      "args": ["--root", "/srv/configs"]
    }
  }
}
```

- При подключении модель первой получает протокол — в `instructions`.
  Протокол, заголовки и описания инструментов — по-английски при любом
  `lang`; вывод инструментов — на языке оператора.
- Таблица инструментов закрыта: `apply`, `approve`, `rollback`, `run`,
  `eval`, `patch`, `!install` в неё не входят, и проверка таблицы при
  запуске не даст их добавить.
- Файлы — только внутри `--root`; живые источники и переменные окружения —
  только разрешённые (`--allow-live`, `--allow-env`). Сценарии модели
  выполняются в песочнице ochan с теми же границами.
- `ochan` под сервером работает в роли `llm`: даже ошибка в таблице не
  даст модели выполнить изменение — откажет сам `ochan`.

Инструменты, флаги и устройство — в [mcp/README.md](../../mcp/README.md).
Пошагово — рецепт [«Нейросеть пишет сценарий по формальному промпту»](../cookbook/ai-script.md).
