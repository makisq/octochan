# Как устроен ochan

ochan отвечает на три вопроса: **что изменится**, **кто сказал «да»** и
**как вернуть, как было**. Всё остальное — способы получить ответы на
них для разных систем.

## Путь изменения

```
источник ──► план ──► заявка ──► согласование ──► выполнение ──► журнал ──► откат
 (конфиг,     (что       (план и      (человек:          (ровно то,       (что было     (вернуть
  сценарий)   изменится)  текст)       approve/reject)    что согласовали)  до)           как было)
```

1. **Источник** — то, с чем работают: конфигурационный файл, живой
   PostgreSQL, YAML-сценарий исполнителя или сценарий на языке алиасов.
2. **План** (`ochan plan`) — что изменится, без изменений. Для сценария
   на языке алиасов это его выполнение в режиме плана: `write`, `save` и
   печать в файл ничего не пишут, а запоминаются.
3. **Заявка** (`ochan request`) фиксирует план и то, что его породило:
   текст сценария, каталог, песочницу, суммы файлов библиотеки,
   формальный промпт и отчёт модели.
4. **Согласование** (`ochan approve` / `reject`) — решение человека.
   Принимается один раз: пересмотр — новая заявка.
5. **Выполнение** (`ochan apply --request`) — ровно то, что согласовали.
   План строится заново и сверяется с согласованным; разошёлся —
   выполнение отменяется.
6. **Журнал** (`ochan history`) — каждая операция с тем, что было до неё.
7. **Откат** (`ochan rollback`) возвращает файлы к прежнему содержимому и
   удаляет созданные. Правку, сделанную после операции, без `--force` не
   стирает. Сам откат тоже обратим.

Шаги необязательны: `ochan diff` и `ochan patch` работают сразу. Но
когда изменение должно быть согласовано, цепочка проходится целиком, и на
каждом шаге видно, что именно происходит.

## Источники

Везде, где команда принимает конфиг, подходит файл, `-` (stdin) или живой
источник со своей схемой — `postgres://dba@db1:5432/postgres`. Значения
сравниваются по смыслу: `8GB` и `8192MB`, `1s` и `1000ms` равны. Новая
система — новый источник со своей схемой, ядро не меняется.
Подробнее — [«Конфигурации»](configs.md).

## Сценарии двух видов

| | YAML-сценарий исполнителя | Сценарий на языке алиасов |
|---|---|---|
| Что это | «какой сервис и над чем» — поле `service`, цели, параметры | программа: переменные, циклы, алиасы, работа с файлами и конфигами |
| Кто выполняет | исполнитель из модуля, зарегистрированный за сервисом (например, RLM) | интерпретатор ochan |
| План | исполнитель описывает задачи, не создавая их | выполнение в режиме плана |
| Откат | задачи во внешней системе необратимы | записанные файлы возвращаются |
| Подробнее | [«Сценарии исполнителей»](scenarios.md) | [«Язык алиасов»](language.md) |

## Роли

Каждая команда проверяет права текущей роли. После установки есть `master`
(всё) и `llm` (читать, планировать, оформлять заявки — потолок для
нейросетей). Остальные роли создаёт `master`. Локально роли — защита от
ошибки и граница для нейросети; границей против других людей они
становятся в [серверном режиме](server.md). Подробнее — [«Роли и права»](roles.md).

## Нейросети

Нейросеть работает с ochan через сервер MCP в роли `llm`: читает,
планирует, пишет сценарии и оформляет заявки, но не выполняет — согласует
и выполняет человек. Задачу ей ставят формальным промптом; его жёсткие
правила проверяются по плану сценария детерминированно, до выполнения.
Подробнее — [«Нейросети и формальный промпт»](ai.md).

## Расширение

ochan собирают под себя:

- **пакет алиасов** — сценарии поверх встроенных функций, текст, который
  видно глазами; с версией он становится скиллом для формального промпта;
- **модуль** — плагин по gRPC: новые команды, язык интерфейса,
  исполнители сценариев (так приходит RLM); ставится `!install`;
- **источник** — Go-пакет, регистрирующий свою схему.

Подробнее — [«Модули и пакеты»](modules.md).

## Устройство кода

```
config       движок: разбор, нормализация, сравнение, план        зависимостей нет
lang         язык алиасов: разбор, проверка, интерпретатор, план  -> config
arbiter      жёсткие правила промпта по плану сценария            -> fp, lang
fp           формальный промпт: разбор, проверки, протокол        зависимостей нет
i18n         язык интерфейса                                      зависимостей нет
logs         уровни строк журнала, перенос журнала в архив        -> i18n
rbac         роли, права, запреты, области, пределы               x/crypto
audit        журнал аудита с цепочкой хешей                       x/sys
sandbox      песочница ОС: Landlock, seccomp, пространства имён   -> i18n, x/sys
remote       серверный режим: TLS, вход, сессии, клиент           -> rbac, audit
pluginhost   хост модулей: команды, языки, исполнители (gRPC)     зависимостей в ochan нет
scenario     сценарий и реестр исполнителей                       -> config
runnerhost   исполнитель модуля как scenario.Runner (JSON)        -> pluginhost, scenario
rings        кольца формального промпта: поддержка, порог, выбор  зависимостей нет
pgsource     живой PostgreSQL как источник                        -> config
workspace    рабочие каталоги, журнал, заявки, решения            -> config, rings
report       документы .docx и почта                              -> config
cmd          команды CLI                                          -> всё вышеперечисленное
mcp/         сервер MCP — отдельный Go-модуль без зависимостей
plugins/rlm  модуль RLM: клиент API (rlm) и сервисы (module)      ядро его не импортирует
```

**`config` не зависит ни от чего.** Движок сравнения полезен сам по себе
и импортируется отдельно. **СУБД и RLM — ниши, а не фундамент:** источник
регистрирует схему, исполнитель приходит модулем, и ядро о них не знает. **ИИ —
модуль, а не основа:** сервер MCP лежит отдельно, моделей в нём нет,
привязки к поставщику нет.
