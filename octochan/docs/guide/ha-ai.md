# Контур без человека: HA-AI, free и инциденты

Обычный ochan держится на том, что решение принимает человек: модель
предлагает, человек согласует и выполняет. Есть контуры, где человека нет
физически или организационно: нет дежурного, который согласует, нет
оператора, который переключит. Для них — **контур HA-AI**: master, единственный
человек, заранее передаёт модели часть своих прав — роль, политику, срок, — а
**инцидент** ограничивает, сколько модель чинит сама, прежде чем позвать
инженеров.

| | Обычный контур | HA-AI |
|---|---|---|
| Кто согласует заявку модели | человек | политика free; вне её — ждёт master |
| Кто выполняет | человек | модель, от имени роли, которую передал master |
| Сколько модель чинит инцидент | — | срок уровня критичности, затем — инженерам |
| Кто включает | — | только master |
| Что проверяется | песочница, кольца, арбитр, сверка плана | то же самое: free меняет только то, кто сказал «да» |

## Контур

Контур — свойство узла пары: человека-оператора у этого узла нет. Объявить
его может только master:

```
$ ochan ha init --node a --role primary --ai-contour
Общий секрет пары: /home/octochan/.octochan/ha.token (права 0600) — скопируйте его на второй узел
Узел a: primary, эпоха 1 (/home/octochan/.octochan/ha.json)
Контур:    HA-AI
внимание: в этом контуре нет человека-оператора; free включает только master — ochan agents free

$ ochan ha status
Этот узел: a — primary, эпоха 1, с 2026-10-30 10:03:37 (root, роль master)
Контур:    HA-AI — человека-оператора нет; free включает только master
```

У существующего узла — `ochan ha contour ai` (или `human` — вернуть
обычный). Контур у каждого узла пары свой, ставят на обоих: после
`ha promote` free продолжает действовать на новом primary, только если и он
HA-AI.

## free

`ochan agents free <агент> --role R --for D --policy P`:

- **только master**: free не даёт прав, а делегирует уже существующие —
  master передаёт модели права роли R на выполнение;
- **только primary контура HA-AI**: на standby и в обычном контуре free не
  действует;
- **с политикой** P — той же, что у [`ochan watch`](scenarios.md#слежение-ochan-watch-и-политика):
  белые списки целей и значений параметров, обязательный срок;
- **со сроком** D: `--for 4h` гаснет сам. Кончится срок политики или её
  отзовут — free кончится вместе с ней: если master ушёл, дверь не
  останется открытой.

```
$ ochan agents free db7 --role deployer --for 4h --policy fix-db
Агент db7: isolation free (до 14:03, роль deployer, политика fix-db)
Отозвать: ochan agents free db7 --revoke

$ ochan agents
db7              на связи   10.0.0.7               db, db_new           2m44s назад, роль agent
                 isolation free (до 14:03, роль deployer, политика fix-db)

$ ochan agents free db7 --role llm --for 1h --policy fix-db
ошибка: роль llm free не передаётся: master — человек, llm — сама модель
$ OCTOCHAN_ROLE=deployer ochan agents free db7 --revoke
ошибка: роль deployer не может выполнять agents free: нужно право admin
```

Включить free при старте агента — `ochan agent run … --isolation free
--free-role deployer --free-for 4h --free-policy fix-db`: агент сразу
после регистрации просит сервер о free. Сервер пустит, только если агент
вошёл в роли master, — поэтому надёжнее выдавать free командой на сервере,
а не держать пароль master на машине агента.

### Что модель может

Заявка модели (роль `llm`, через [MCP](ai.md#сервер-mcp) или ochan) на
сценарий исполнителя проверяется против политики выдачи — сервис, каждая
цель, каждый параметр, план без перерыва обслуживания, право и предел роли
R на `apply`. Укладывается — политика её согласует, и заявка выполняется
сразу, от имени R:

```
$ ochan request raise.yaml               # роль llm
Заявка 5ce65d2552 создана (ждёт решения)
Изменений: 1
Заявка 5ce65d2552 в free агента db7 (политика fix-db) — выполняется без человека, от имени роли deployer
Заявка 5ce65d2552, сервис demo, исполнитель Demo
Создано:
  - demo-CI007: max_connections = 300
```

Не укладывается — обычная заявка, ждёт master:

```
$ ochan request wide.yaml                # max_connections: 900
Заявка c56db80d63 создана (ждёт решения)
Изменений: 1
Заявка c56db80d63 вне free: db7 (fix-db): параметр max_connections = 900 вне допустимого (200..400) — ждёт master
```

| Действие | обычный контур | free (HA-AI) |
|---|---|---|
| читать, планировать, оформлять заявки | да | да |
| согласовать и выполнить свою заявку | нет | только в политике |
| обратное действие своей заявки (`compensate`) | нет | да, пока free действует |
| вне политики | нет | обычная заявка, ждёт master |
| `set role`, `!!install`, `policy revoke`, `approve` чужого | нет | нет |

Модель с несколькими выдачами выбирает свою через `ochan-mcp --agent db7`:
тогда её заявки проверяет только free этого агента.

### Чего free не делает

- **Не отменяет песочницу**: `--allow-exec`, `--allow-net`, `--allow-env`
  действуют как всегда.
- **Не отменяет кольца, арбитра и сверку плана**: меняется только то, кто
  согласует, а не то, как проверяется.
- **Не даёт прав master**: только выполнение по политике и обратное
  действие своего.

В журнале аудита видно, что решения человека не было:

```
$ ochan audit
+ 2026-10-30 10:03:37  deployer   root   free: agent db7 free включён на a: роль deployer, политика fix-db, до 2026-10-30 14:03 (root, роль master)
+ 2026-10-30 10:03:47  deployer   root   free: agent db7 approve 5ce65d2552 (free: политика fix-db, без человека)
+ 2026-10-30 10:03:47  deployer   root   free: agent db7 apply 5ce65d2552 (free: политика fix-db, без человека)
```

Срок вышел — запись «free истёк — isolation вернулось в natural»; отзыв
и переход на новый primary после `promote` тоже пишутся в журнал.

## Инциденты

Инцидент — то, что сломалось на серверах контура: его открывает мониторинг
или сама модель, и модель идёт чинить. Чтобы она не ушла в цикл, у
инцидента есть **уровень критичности**, а у уровня — **срок**: столько
модель чинит сама. Чем критичнее, тем раньше зовут людей.

```yaml
incidents:
  levels:                       # уровень: сколько модель чинит сама
    low: 4h
    medium: 1h
    high: 30m
    critical: 15m
  engineers: [dba@corp.example]                 # инженерная группа
  notify:                                       # свои адреса уровня
    critical: [oncall@corp.example, dba@corp.example]
  notify_resolved: true                         # письмо и о решённом (по умолчанию)
  report:                                       # статистика на почту
    every: 7d
    to: [leads@corp.example, dba@corp.example]
mail:
  lang: natural                                 # письма ниже — естественным языком
```

На каком языке ochan пишет инженерам, решает режим модели
([«Почта»](mail.md)): в `llm.mode: natural` — естественным языком, иначе
формальным промптом, фактами-ячейками, а тексты мониторинга и модели
идут вложением. Письма в этом разделе — естественным языком
(`mail.lang: natural`). Формальный вариант эскалации и статистики показан
в «Почте». Своя модель (`llm.mode: embedded`) и в записях инцидента пишет
только формальным промптом ([«Своя модель»](embedded.md#только-формальный-промпт)).

Уровни — любые: например, классы систем банка.

```yaml
incidents:
  levels: {op: 4h, bo: 2h, bc: 1h, mc: 30m, "mc+": 15m}   # Office … Mission Critical+
```

### Модель чинит

```
$ ochan incident open --level critical --host db7 "PostgreSQL на db7 не принимает новые соединения"
Инцидент 88fb030508 (critical) открыт: модель чинит сама до 10:18 (15m)
Не успеет — эскалация инженерам: oncall@corp.example, dba@corp.example

$ ochan incident note 88fb "pg_stat_activity: 200 соединений из max_connections 200, держит пул приложения"
Инцидент 88fb030508: заметка записана, шагов 2
$ ochan incident attach 88fb /var/log/postgresql/postgresql.log
Инцидент 88fb030508: приложен postgresql.log, байт 261
$ ochan request raise.yaml --incident 88fb
…
Заявка 5ce65d2552 в free агента db7 (политика fix-db) — выполняется без человека, от имени роли deployer
```

Шаги инцидента — всё, что сделано: открытие, заметки модели, приложенные
журналы, заявки с `--incident` и их выполнение (под free или человеком).
Решила — `ochan incident resolve 88fb "…что сделано и как проверено"`.

### Не успела — инженерам

Срок вышел или модель сама признала, что её знаний не хватит
(`ochan incident escalate 88fb "причина не в конфиге"`), — инцидент
**эскалируется**:

```
$ ochan incident 88fb
Инцидент:  88fb030508
Состояние: эскалирован
Уровень:   critical (модель чинит сама 15m)
Открыт:    2026-10-30 10:03:46 (llm)
Итог:      время вышло: модель не решила за 15m (2026-10-30 10:18:47)
Письмо:    эскалация — oncall@corp.example, dba@corp.example
Хосты:     db7
Что:       PostgreSQL на db7 не принимает новые соединения

Шаги:
  10:03:46  llm        open: PostgreSQL на db7 не принимает новые соединения
  10:03:47  llm        note: pg_stat_activity: 200 соединений из max_connections 200, держит пул приложения
  10:03:47  llm        attach postgresql.log: журнал postgresql.log, байт 261
  10:03:47  llm        request 5ce65d2552: demo через Demo, операций: 1
  10:03:47  deployer   apply 5ce65d2552: выполнена
  10:18:47  ochan      escalate: время вышло: модель не решила за 15m
```

Инженерной группе уровня уходит письмо — заявка с описанием, всем, что
модель сделала, и журналами:

```
Subject: [ochan] Инцидент 88fb030508 (critical) эскалирован: время вышло: модель не решила за 15m
To: oncall@corp.example, dba@corp.example

Инцидент 88fb030508 — эскалация инженерам

Уровень:  critical (модель чинит сама 15m)
Открыт:   2026-10-30 10:03 (llm)
Хосты:    db7
Что:      PostgreSQL на db7 не принимает новые соединения
Причина:  время вышло: модель не решила за 15m

Что сделано:
  10:03:46  llm        open: PostgreSQL на db7 не принимает новые соединения
  …
Заявки по инциденту:
  5ce65d2552  выполнена  demo через Demo, операций: 1

Журналы (важное; целиком — во вложениях):
  postgresql.log:
    fatal  2026-10-30 14:02:03 MSK FATAL:  sorry, too many clients already
    warning  2026-10-30 14:02:09 MSK WARNING:  could not send data to client: Broken pipe

Журнал аудита за время инцидента:
  + 10:03:47 deployer   free: agent db7 apply 5ce65d2552 (free: политика fix-db, без человека)
  …
Вложения: incident-88fb030508.docx, postgresql.log
```

Важные строки журналов отбирают правила [`logs.rules`](logs.md#уровни-важности);
журналы целиком и документ `.docx` идут вложениями. Почта — та же, что у
заявок ([«Почта»](requests.md#почта)); не ушло письмо — это видно в карточке
(«Письмо: эскалация — не ушло: …»).

**После эскалации модель по инциденту не действует**: ни заметок, ни
заявок с `--incident`, ни решения, а free заявки по нему не выполняет.
Инцидент теперь у людей; закрывает его человек — `incident resolve`.

```
$ ochan incident note 88fb "попробую ещё раз"        # роль llm
ошибка: инцидент 88fb030508 эскалирован инженерам (время вышло: модель не решила за 15m): модель по нему больше не действует
```

### Решён — письмо

Решённый инцидент — письмо той же группе, которой ушла бы эскалация: кто
решил (модель или человек), за сколько, что сделано и какими шагами,
была ли эскалация. Решила модель — люди знают, что было, хотя их не звали;
решил человек после эскалации — все, кому ушла эскалация, знают, что
инцидент закрыт.

Из [рецепта](../cookbook/incident-ha-ai.md#5-инженер-решил--письмо-о-решении),
где срок `critical` — минута:

```
$ ochan incident resolve b8f8 "инженер ограничил пул приложения: pool_size 150, соединения идут"
Инцидент b8f8921ac4 решён за 1m24s: инженер ограничил пул приложения: pool_size 150, соединения идут
Письмо о решении: oncall@corp.example, dba@corp.example
```

```
Subject: [ochan] Инцидент b8f8921ac4 (critical) решён человеком (master) за 1m24s: инженер ограничил пул приложения: pool_size 150, соединения идут

Инцидент b8f8921ac4 решён человеком (master) за 1m24s

Уровень:   critical (модель чинит сама 1m)
Открыт:    2026-10-30 10:35 (llm)
Хосты:     db7
Что:       PostgreSQL на db7 не принимает новые соединения
Эскалация: 2026-10-30 10:36 (время вышло: модель не решила за 1m)
Решение:   инженер ограничил пул приложения: pool_size 150, соединения идут

Что сделано:
  …
```

Тема — «решён моделью за …» или «решён человеком (роль) за …». В карточке
— строка на каждое письмо: «Письмо: решение — адреса» или «— не ушло: …».
Не нужно — `incidents.notify_resolved: false`.

### Статистика и отчёт

ochan считает, что модель решает сама, а что — нет, по инцидентам,
открытым за период:

```
$ ochan incident stats --for 7d
Инциденты с 2026-10-23 10:37 по 2026-10-30 10:37 (7d): 3

Решены:                       2
  моделью до срока            1   в среднем 0s, медиана 0s
  человеком до эскалации      0
  людьми после эскалации      1   в среднем 23s, медиана 23s после эскалации
Не решены:                    1
  у инженеров                 1
  у модели, срок не вышел     0

Модель решила сама 1 из 3 (33%), не справилась — 2 (67%):
  срок вышел                  1
  отдала инженерам сама       1
  отдал инженерам человек     0

По уровням:
  уровень     срок  всего  модель  эскалация  не решены
  low           4h      1       1          0          0
  medium        1h      1       0          1          1
  critical      1m      1       0          1          0

Нерешённые:
  1643e8958e  medium    у инженеров  репликация db7 → db8 отстаёт на 40 минут

Отчёт: каждые 7d → leads@corp.example, dba@corp.example; следующий — 2026-11-06 10:37
```

(Вывод — из рецепта [«Модель чинит инцидент»](../cookbook/incident-ha-ai.md#6-статистика-и-отчёт),
где срок `critical` — минута, а модель «чинит» за секунды.)

- **Решены** — моделью до срока, человеком до эскалации, людьми после
  эскалации; время — от открытия (модель) и от эскалации (люди).
- **Не решены** — у инженеров (эскалирован и не закрыт) или у модели
  (срок не вышел).
- **Модель не справилась** — эскалирован: срок вышел, отдала сама
  (`incident escalate`), отдал человек. Эскалированный и потом решённый
  инцидент есть и здесь, и в «решены»: это разные вопросы.
- Период — `--for 24h`, `--for 30d`, `--for all`; без флага —
  `incidents.report.every` или 7d. Статистика считается заново из файлов
  инцидентов, поэтому дорешённый инцидент сразу виден.

**Отчёт на почту.** С `incidents.report.every` статистику с таблицей
инцидентов (`.csv`: номер, уровень, время, итог, кто эскалировал и решил,
за сколько) группе `incidents.report.to` (иначе `incidents.engineers`)
шлют сами сервер на primary и `incident check` в cron. Первая проверка
начинает расписание, дальше окна идут подряд: каждый отчёт — за время с
предыдущего; сервер стоял — один отчёт за все пропущенные окна. Не ушёл —
ошибка видна в `incident stats`, повтор через 10 минут, окно не
сдвигается. Расписание копируется на standby вместе с инцидентами: после
`ha promote` отчёт не повторится и не пропадёт. `ochan incident report
[--for 7d]` — отправить сейчас, расписание не сдвигая.

### Кто следит за сроком

- сервер (`ochan serve`) на primary — раз в 30 секунд;
- любая команда инцидентов и заявка по инциденту — по пути;
- `ochan incident check` — для cron, если сервера нет; он же шлёт отчёт по
  расписанию.

С сервером эскалация случается не позже чем через 30 секунд после срока;
без сервера — при ближайшей команде или проходе cron, поэтому на контуре
HA-AI сервер или cron обязательны. В карточке видно и срок, и момент
эскалации. Инциденты копируются на standby вместе с остальным состоянием;
сам standby сроков не проверяет и писем не шлёт — cron с `incident check`
можно ставить на оба узла, письмо уйдёт одно. После `ha promote` за сроками
и отчётом следит новый primary.

### Мониторинг

Мониторинг открывает инцидент вебхуком сервера:

```
$ ochan incident secret
Секрет вебхука мониторинга: /home/octochan/.octochan/incidents.secret (права 0600)

$ curl -X POST -H "Authorization: Bearer $(cat incidents.secret)" \
    -d '{"level": "high", "hosts": ["db7"], "summary": "нет соединений", "source": "zabbix", "log": "FATAL: too many clients"}' \
    https://orchestrator.example:7443/v1/incidents
{"deadline":"2026-10-30T10:34:00Z","id":"9c0e…","result":"инцидент 9c0e… (high) открыт: модель чинит до 10:34"}
```

`log` прикладывается к инциденту как `monitoring.log`. Вебхук принимает
только primary; standby отвечает 503 с адресом primary.

### Модель через MCP

Инструменты `incidents`, `incident_stats`, `incident_open`, `incident_note`,
`incident_attach`, `incident_resolve`, `incident_escalate` и поле `incident`
у `request_*` — [«Сервер MCP»](../../mcp/README.md#инструменты). В их
описаниях модель читает правило: не успела — не пробовать дальше, а
эскалировать.

## Права

| Действие | Право |
|---|---|
| `ha init --ai-contour`, `ha contour` | master |
| `agents free`, `agents free --revoke` | master |
| `incident`, карточка, `incident stats` | `read` |
| `incident open`, `note`, `attach`, `resolve`, `escalate`, `check`, `report` | `request` |
| `incident secret` | `admin` |

## Что не проверялось

Контур HA-AI проверен тестами и на одном узле с локальным приёмником
