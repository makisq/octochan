# Установка и настройка

## Сборка

Нужен Go 1.25 или новее. Внешних программ ochan не требует: ни Word для
документов, ни клиента PostgreSQL для живых источников. Команда — `ochan`:
её собирают и `make install`, и голый `go build` в каталоге репозитория
(модуль Go называется `ochan`).

```bash
git clone https://github.com/makisq/PACAL
cd PACAL/octochan
make install
ochan --version
```

```
ochan 0.3.0-alpha
```

`make install` собирает `ochan` и сервер MCP `ochan-mcp` и спрашивает, как
ставить:

```
Установка ochan. Как ставить?
  1 — быстрая: всё в этой папке — /srv/work/octochan
      программы, рабочий каталог (.octochan) и модули; ochan находит своё сам
  2 — ручная: каждый путь задаёте сами, Enter — путь по умолчанию
Выбор, 1 или 2:
```

- **Быстрая — всё в одной папке.** Программы, рабочий каталог и модули
  лежат в папке, из которой запущена установка; `ochan` запускают из неё
  (`./ochan`). Она для машин, где политика разрешает работать и запускать
  программы только в одной папке: ни `~/.local/bin`, ни `~/.octochan` там
  не годятся. Рядом с программой остаётся указатель `ochan.home`, и
  переменные окружения не нужны ([«Установка в одну папку»](#установка-в-одну-папку)).
- **Ручная — каждый путь отдельно:** программы, рабочий каталог, модули,
  журналы, отчёты, кеш реестров. Enter оставляет путь по умолчанию: все
  шесть Enter — обычная установка, программы в `~/.local/bin`, остальное в
  `~/.octochan`. Если каталога программ нет в `PATH`, установка скажет об
  этом; профиль оболочки она не правит.

Вопросы задаёт сам `ochan` (`ochan setup`) и читает ответы из stdin
построчно — с терминала и из конвейера одинаково; без ответа (CI,
`< /dev/null`) ставит в каталоги по умолчанию. Всё то же задаётся без
вопросов:

| | |
|---|---|
| `make install` | спросит: быстрая или ручная |
| `make install HERE=1` | быстрая: всё в этой папке |
| `make install HERE=/srv/work/ochan` | быстрая в другую папку |
| `make install BIN_DIR=… HOME_DIR=… MODULES_DIR=… LOGS_DIR=… REPORTS_DIR=… REGISTRY_CACHE_DIR=…` | ручная; незаданное — по умолчанию |
| `make install PREFIX=/usr/local` | программы в `/usr/local/bin` (копирование — через `sudo`, сборка — от вашего имени), остальное по умолчанию |
| `scripts/install.sh [--here[=папка]] [--bin=…] [--home=…] [--modules=…]` | то же без `make` |
| `printf '1\nда\n' \| scripts/install.sh` | ответы конвейером |
| `make install HERE=1 DESKTOP=1` | ещё и [значок](#значок): меню приложений и рабочий стол |
| `ochan setup` | то же готовой программой, без сборки: скачанный `ochan` ставит себя сам |
| `make uninstall` | убрать программы из `~/.local/bin` (или `PREFIX/bin`) |
| `make build` | только собрать в `bin/` каталога репозитория |
| `make build OUT=$HOME/tools` | собрать в любой каталог, куда можно писать |
| `make vendor`, `make offline` | зависимости в `vendor/` и сборка из них без сети |
| `make dist` | релиз под все платформы в `dist/` с `SHA256SUMS` |
| `make version` | какую версию соберёт `make` |

На Windows:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\install.ps1
```

Вопрос тот же. Без него: `-Here` — всё в текущей папке; `-Bin`,
`-HomeDir`, `-Modules`, `-Logs`, `-Reports`, `-RegistryCache` — пути по
одному; `-Standard` — программы в `%LOCALAPPDATA%\Programs\ochan`, каталог
добавляется в `PATH` пользователя, и в новом окне терминала `ochan` и
`ochan-mcp` вызываются по имени. Убрать — с `-Uninstall`.

### Установка в одну папку

Бывают машины, где политика разрешает работать и запускать программы
только в одной папке. `~/.octochan/modules` там не годится: модуль не
запустится (`operation not permitted`), и `!!install` откажет. Переменные
окружения (`OCTOCHAN_HOME`, `OCTOCHAN_MODULES`) это решают, но их надо
задавать в каждом окне. Быстрая установка кладёт всё в эту папку и
записывает, где что лежит:

```
$ make install HERE=1          # или: ./ochan setup --here — готовой программой
Программы:        /srv/work/octochan
Рабочий каталог:  /srv/work/octochan/.octochan
Модули:           /srv/work/octochan/.octochan/modules (в рабочем каталоге)
…
Установлено: /srv/work/octochan/ochan
Установлено: /srv/work/octochan/ochan-mcp
Указатель: /srv/work/octochan/ochan.home → .octochan (путь от папки программы: её можно переносить целиком)

Рабочий каталог      /srv/work/octochan/.octochan
                       файл ochan.home рядом с программой
…
Запуск: ./ochan из папки /srv/work/octochan
```

`ochan.home` — указатель рабочего каталога: файл рядом с программой, в нём
одна строка с путём (строки с `#` — комментарии). Путь без начала от корня
считается от папки программы, поэтому папку можно переносить и копировать
целиком. `ochan` читает указатель при каждом запуске — `export` не нужен;
переменная `OCTOCHAN_HOME` сильнее указателя. Указатель можно написать и
руками:

```bash
echo /srv/work/ochan-state > ochan.home     # рядом с ochan
```

Папка должна быть вашей: она и каталоги над ней закрыты для записи группе
и остальным, иначе `ochan` откажется работать и скажет, что закрыть
(`chmod go-w …`), — в открытую папку другой пользователь подложил бы свой
модуль.

Когда годится всё, кроме модулей, переносят только их — ручной установкой
(`make install MODULES_DIR=/opt/ochan/modules`) или строкой в `config.yaml`
(`paths.modules`, [«Пути»](#пути)).

### Значок

У `ochan` есть значок — эмблема логотипа. Установка ставит его по просьбе:
в разговоре она спрашивает «Значок в меню приложений и на рабочем столе?»,
без вопросов — `--desktop` (`make install DESKTOP=1`, `install.ps1
-Desktop`):

```
$ ochan setup --here --desktop
…
Значок: /home/ops/.local/share/applications/ochan.desktop
Значок: /home/ops/Desktop/ochan.desktop
```

| | |
|---|---|
| Linux | запись меню приложений `~/.local/share/applications/ochan.desktop`, картинка в `~/.local/share/icons/hicolor/256x256/apps/`, копия записи на рабочем столе, если он есть |
| Windows | ярлыки `ochan.lnk` в меню «Пуск» и на рабочем столе; значок встроен в сам `ochan.exe` и виден в проводнике и поиске |
| macOS | пока нет: `ochan` запускают из терминала |

Значок открывает оболочку `ochan shell` в терминале; `ochan` находится
поиском системы по имени. Для уже установленной программы — `ochan setup
--desktop=only`, убрать — `ochan setup --desktop=remove` (`make uninstall`
убирает и его).

Картинку делает `make icon` (`tools/icongen`) из `docs/assets/logo.png`:
`cmd/icon.png` несёт в себе `ochan`, а `rsrc_windows_amd64.syso` — ресурс
значка, который `go build` сам прилинковывает к `ochan.exe`. Оба файла
лежат в репозитории; после смены логотипа их пересобирают.

### go build — без make

Собрать руками, без установки, — в любой каталог:

```bash
go build -o ochan .
(cd mcp && go build -o ../ochan-mcp .)
```

Собирается под Linux, macOS и Windows, в том числе накрест:

```bash
GOOS=windows GOARCH=amd64 go build -o ochan.exe .
GOOS=darwin  GOARCH=arm64 go build -o ochan-mac .
GOOS=linux   GOARCH=arm64 go build -o ochan-arm64 .
```

Версию печатают `ochan --version` и `ochan-mcp --version`; в исходниках
записана `0.3.0-alpha`, другая задаётся при сборке:

```bash
go build -ldflags "-X ochan/cmd.Version=0.3.0-alpha" -o ochan .
(cd mcp && go build -ldflags "-X main.serverVersion=0.3.0-alpha" -o ../ochan-mcp .)
make build VERSION=0.3.0-alpha+site     # то же через make
```

Путь системной политики ролей тоже задаётся при сборке, а не окружением
([«Безопасность»](security.md#роль-которую-подтверждает-не-рабочий-каталог)):

```bash
make build SYSTEM_ROLES=/opt/octochan/roles.yaml
go build -ldflags "-X ochan/rbac.SystemPolicyPath=/opt/octochan/roles.yaml" -o ochan .
```

По умолчанию — `/etc/octochan/roles.yaml`; файла нет — политики нет.

### Закрытые системы

Там, где класть программы в `/bin`, `/usr/bin` и `/usr/local/bin` нельзя,
а сети нет, ochan собирается и работает целиком в каталогах пользователя:
ни системных путей, ни прав root ему не нужно.

1. **Без системных каталогов.** `make build OUT=$HOME/tools` или
   `go build -o $HOME/tools/ochan .` — в любой каталог, куда можно писать.
   Запуск — по полному пути (`$HOME/tools/ochan --version`) или через свой
   каталог в `PATH` (`export PATH="$HOME/tools:$PATH"` в профиле). `make
   install PREFIX=$HOME/opt` кладёт в `$HOME/opt/bin` и `sudo` не просит,
   если каталог ваш.
2. **Без сети.** На машине с сетью: `make vendor` — зависимости обоих
   модулей (ochan и ochan-mcp) ложатся в `vendor/`. Каталог `octochan`
   целиком, вместе с `vendor/`, переносится на закрытую машину, и там
   `make offline` собирает из него, не обращаясь к сети (`GOFLAGS=-mod=vendor
   GOPROXY=off`). Без make — то же руками:

   ```bash
   GOFLAGS=-mod=vendor GOPROXY=off go build -o $HOME/tools/ochan .
   (cd mcp && GOFLAGS=-mod=vendor GOPROXY=off go build -o $HOME/tools/ochan-mcp .)
   ```

3. **Без записи в домашний каталог Go.** Кеш сборки и модулей Go по
   умолчанию живёт в `~/.cache/go-build` и `~/go`; если туда нельзя или
   `/tmp` смонтирован с `noexec`, их переносят в свой каталог:

   ```bash
   export GOCACHE=$HOME/work/go-cache GOMODCACHE=$HOME/work/go-mod GOTMPDIR=$HOME/work/go-tmp
   export GOTOOLCHAIN=local      # не скачивать другую версию Go
   mkdir -p "$GOTMPDIR"
   ```

4. **Только готовый файл.** Собрать на другой машине (`make dist` или
   `GOOS=linux GOARCH=amd64 go build …`) и перенести один исполняемый файл:
   зависимостей во время работы у ochan нет. Суммы — в `dist/SHA256SUMS`.

Рабочий каталог ochan — `$HOME/.octochan`. Если домашний каталог на
закрытой машине не годится, рабочий каталог переносят целиком — установкой
в одну папку ([выше](#установка-в-одну-папку)) или
`OCTOCHAN_HOME=/srv/ochan`, — а каталог модулей, если нужно, отдельно
([«Пути»](#пути)); путь только к конфигу меняют `--config` и
`OCTOCHAN_CONFIG`.

## Первый запуск

При первом запуске ochan создаёт `~/.octochan` и `config.yaml` со
значениями по умолчанию. Всё, что ochan хранит, живёт там:

```
~/.octochan/
  config.yaml     настройки
  tokens/         токены исполнителей, файл на исполнителя (права 0600)
  roles.bin       роли, их права, логины и пароли (хеши), текущая роль
  state.json      что ochan помнит между запусками: история оболочки, выбор логотипа
  modules/        модули команд и языков (*.hcplugin), пакеты алиасов
  aliases/        пользовательские алиасы (*.ochan)
  scenarios/      сохранённые сценарии (ochan srs)
  history/        журнал операций — по нему работает rollback
  requests/       заявки на согласование
  decisions/      журнал решений по формальному промпту — для колец
  audit.log       журнал аудита с цепочкой хешей
  inventory.yaml  инвентарь — источник local, если файл есть
  inventory.seen.json  хосты, которые уже видели (ochan inventory ack, watch)
  policies/       политики ochan watch; отозванные и заменённые — в old/
  reports/        отчёты команды diff
  snapshots/      снапшоты расхождений
  logs/           журнал работы ochan и его архивы
  tls/            сертификат и ключ серверного режима (ochan tls init)
  ha.json, ha.token  пара серверов: роль узла, эпоха, контур, общий секрет (ochan ha init)
  agents.json     реестр агентов на сервере
  mail/           почта: письма агентов друг другу и людям (ochan mail)
  llm/            журнал генераций своей модели (llm.mode: embedded)
  free.json       выдачи free модели на узле HA-AI (ochan agents free)
  incidents/      инциденты HA-AI; incidents.secret — секрет вебхука мониторинга
  triggers.json   окна триггеров; triggers/ — секреты их вебхуков
  registry/cache/ клоны git-реестров пакетов
```

Каталоги создаются с правами 0700, файлы с секретами — 0600. Путь до
конфига переопределяется флагом `--config` или переменной
`OCTOCHAN_CONFIG` — так удобно держать несколько окружений.

## Пути

Где что лежит и откуда взят каждый путь, показывает `ochan paths`:

```
$ OCTOCHAN_MODULES=/opt/ochan/modules ochan paths
Рабочий каталог      /home/ops/.octochan
                       по умолчанию; меняется: OCTOCHAN_HOME, ochan.home рядом с программой (ochan setup)
Конфиг               /home/ops/.octochan/config.yaml
                       по умолчанию; меняется: --config, OCTOCHAN_CONFIG
Модули               /opt/ochan/modules
                       окружение OCTOCHAN_MODULES
Журналы              /home/ops/.octochan/logs
                       по умолчанию; меняется: OCTOCHAN_LOGS, paths.logs
…
```

| Что | Чем меняется |
|---|---|
| Рабочий каталог целиком | указатель `ochan.home` рядом с программой (`ochan setup`), `OCTOCHAN_HOME` — она сильнее |
| Конфиг | `--config`, `OCTOCHAN_CONFIG` |
| Модули и пакеты алиасов | `OCTOCHAN_MODULES`, `paths.modules` |
| Журналы ochan | `OCTOCHAN_LOGS`, `paths.logs` (прежний ключ — `defaults.log_path`) |
| Отчёты `diff` | `OCTOCHAN_REPORTS`, `paths.reports` |
| Клоны git-реестров | `OCTOCHAN_REGISTRY_CACHE`, `paths.registry_cache` |
| Сертификат и ключ сервера, секрет пары | `tls.cert`, `tls.key`, `ha.token_file` |
| Системная политика ролей | только при сборке: `make install SYSTEM_ROLES=…` |

```yaml
# config.yaml — то же настройками; окружение сильнее
paths:
  modules: /opt/ochan/modules
  logs: /var/log/ochan
```

Настройки `paths.*` и указатель пишет и установка: `ochan setup --modules
/opt/ochan/modules` — то же, что строка выше.

- **Рабочий каталог — одно целое.** Роли, журнал аудита, заявки, история,
  решения, политики, алиасы, сценарии, инциденты, почта и токены
  переносятся только вместе с ним: его зеркалит резервный узел
  [пары](server.md), и его закрывает от сценариев и ролей защита рабочего
  каталога. Вынеси заявки отдельно — пара перестала бы их копировать.
- **Каталоги узла выносятся отдельно** — в пару они не копируются. Модули
  выносят туда, где политика хоста разрешает запуск: в домашнем каталоге,
  смонтированном с `noexec`, плагин не запускается (`operation not
  permitted`). Перенос решает это, не обходя политику: каталог для
  исполняемых файлов выбирает администратор, а не ochan.
- **Путь — полный** (`~` раскрывается). Относительный зависел бы от
  каталога, из которого запущен ochan, — это отказ при запуске.
- **Вынесенный каталог должен быть вашим.** Он сам и каждый каталог над
  ним принадлежат вам или root и закрыты для записи группе и остальным
  (каталог выше с липким битом, как `/tmp`, годится) — как sshd требует
  от ключей. Иначе другой пользователь машины подложил бы в модули свой
  плагин, а ochan его запустил бы. На Windows права каталога ochan не
  проверяет.
- **Защита не снимается переносом.** Сценарий не читает и не пишет
  вынесенные каталоги, роль с [областью](roles.md#область) не получает их
  аргументом, песочница нейросети их не накрывает — так же, как рабочий
  каталог.
- **Системная политика ролей** (`/etc/octochan/roles.yaml`) окружением не
  переносится намеренно: её пишет root, и пользователь, указав другой
  файл, обошёл бы её. Путь задаёт сборка.

Сервер MCP и общий оркестратор передают своё окружение дочерним `ochan`,
поэтому пути у них те же; нейросеть и удалённый клиент переменные окружения
задать не могут.

## Конфиг

`config.yaml` разбит на разделы; полный список ключей с умолчаниями — в
[справочнике настроек](../reference/config.md). Чаще всего правят:

```yaml
lang: ru                   # язык справки и сообщений: ru, eng (en) или язык модуля

defaults:
  max_parallel_tasks: 5    # одновременных итераций parallel for
  allow_unverified_modules: false

executors:
  rlm:                     # модуль RLM, если он стоит
    api_url: https://rlm.example.internal/api/tasks.json

logs:
  max_size: 100MB          # журнал ochan уходит в архив с датой в имени
  min_level: warning       # ochan logs rank: что показывать по умолчанию

server:
  listen: 127.0.0.1:7443   # серверный режим
```

Адрес API не зашит в код: без него исполнитель модуля откажет с
объяснением. Всё остальное работает без него. Модуль RLM ставит `make rlm`
(на Windows — `scripts\install.ps1 -Rlm`), см. [«Модуль RLM»](scenarios.md#модуль-rlm).

## Секреты

Секреты в `config.yaml` не кладутся никогда: конфиг лежит на диске и
попадает в резервные копии.

| Что | Где |
|---|---|
| Токен исполнителя | `ochan auth --executor <имя>` (ввод скрыт, `~/.octochan/tokens/<имя>`, 0600) или `OCTOCHAN_TOKEN_<ИМЯ>` |
| Пароль почты | `OCTOCHAN_SMTP_PASSWORD` |
| Пароль PostgreSQL | `PGPASSWORD` или `~/.pgpass` — не в строке подключения |
| Пароли ролей | `ochan role … --npsw` спрашивает их; хранятся только хеши argon2id |
| Вход на сервер | спрашивается при подключении или `OCTOCHAN_REMOTE_LOGIN` / `OCTOCHAN_REMOTE_PASSWORD` |

Все переменные окружения — в [справочнике настроек](../reference/config.md#переменные-окружения).

## Командная строка, конвейеры и CI

Команды читают stdin, если вместо файла указан `-` или файл не указан вовсе:

```bash
cat prod.conf | ochan validate
ochan print prod.conf | ochan diff - test.conf
```

Полезный вывод идёт в stdout, предупреждения и ошибки — в stderr, поэтому
конвейеры не ломаются. Ненулевой код возврата означает ошибку: отказ в
правах, неверный аргумент, сбой проверки, `fail()` в сценарии.

Различие конфигураций ошибкой не считается: `ochan diff` нашёл различия —
он сделал свою работу и вернул 0. Чтобы CI падал на дрейфе, нужен сценарий
с `fail()` — см. рецепт [«Дрейф конфигурации в CI»](../cookbook/ci-drift.md).

## Интерактивная оболочка

`ochan` без аргументов на терминале открывает оболочку (`ochan shell` —
то же самое). Строка — команда ochan или инструкция языка алиасов: язык
в оболочке тот же, что в файле, как у bash. Автодополнение и история — у
обеих:

```
ochan[master]> diff prod.conf test.conf          # команда
ochan[master]> n = len(split(ochan("agents"), "\n"))
ochan[master]> if n > 3 {
...                print("агентов: " + str(n))
...            }
ochan[master]> alias twice(x: int) { return x * 2 }
ochan[master]> twice(21)
42
ochan[master]> !!reset                           # забыть переменные и алиасы оболочки
ochan[master]> !!history
ochan[master]> exit
```

- Слово, которое и команда, и имя в языке, — команда, если за ним не идёт
  `(` или `=`: `diff a.conf b.conf` — команда, `diff("a.conf", "b.conf")`
  — вызов. Ключевое слово языка (`if`, `for`, `alias`) — инструкция, если
  строка разбирается языком: `if x > 1 { … }` — инструкция,
  `if config.conf port == 8080 "ок"` — команда `if`.
- Незакрытый блок `{ … }` продолжается на следующих строках (приглашение
  `...`). Переменные и объявленные алиасы живут до выхода или `!!reset`.
- Инструкция в консоли выполняет то же, что сценарий, поэтому право на неё
  — как у `eval` (группа `apply`): роли только для чтения доступны команды,
  но не язык. Команды из инструкции — `ochan()` — каждая по своему праву
  ([«Язык алиасов»](language.md#команды-ochan)).

В приглашении видна текущая роль. История команд переживает перезапуск
(стрелка вверх, `!!history`); пароли в ссылках записываются как `***`, а
строка, начатая с пробела, не запоминается вовсе. Модули, изменившиеся на
диске, оболочка перезагружает сама.

Логотип при входе: `ochan shell --no-logo` — без него, `ochan shell
--logo` — с ним, даже при `shell.logo: false`. Выбор запоминается: в
следующих сессиях `ochan` без флага входит так же, пока выбор не сменят
другим флагом.

Команды `if` и `else` работают только в оболочке: результат предыдущего
`if` живёт в памяти процесса.

### Без терминала: конвейер и CI

Без терминала — в конвейере, в задании CI, в контейнере, с вводом из файла
— `ochan shell` читает stdin построчно и выполняет те же строки: команды и
инструкции языка, с переменными между строками и блоками в несколько строк.

```bash
echo 'logs rank --min warning' | ochan shell
ochan shell --stop-on-error < проверки.txt
```

```
# проверки.txt
ping
n = len(split(ochan("agents"), "\n"))
if n < 3 {
    fail("агентов меньше трёх: " + str(n))
}
```

- Пустые строки и строки с `#` пропускаются, `exit` кончает ввод. Логотипа,
  приглашения и истории нет.
- Вывод команд — в stdout, ошибки — в stderr. Код возврата — 1, если хоть
  одна строка кончилась ошибкой; с `--stop-on-error` оболочка
  останавливается на первой.
- stdin командам недоступен: из него читаются сами команды. Команде,
  которой нужен ввод, передают файл.
- `ochan` без аргументов и без терминала по-прежнему печатает справку:
  выполнять строки из stdin — явная команда `ochan shell`.

Раньше оболочка без терминала падала: go-prompt открывал `/dev/tty` и
паниковал (`no such device or address`).
