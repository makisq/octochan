# План, заявки и откат

Во многих компаниях изменение нельзя выполнить просто потому, что оно
правильное: сначала нужна заявка, согласование и бумага. ochan проводит
всю цепочку и на каждом шаге показывает, что именно происходит.

## План

```
ochan plan prod.conf changes.conf      что изменит patch
ochan plan restart.yaml                какие задачи создаст сценарий исполнителя
ochan plan сценарий.ochan              что запишет сценарий на языке алиасов
```

План ничего не меняет. Для правки конфига это параметры, которые изменятся;
для YAML-сценария — задачи, которые были бы созданы (изменяющие запросы
запрещены на уровне клиента); для сценария на языке алиасов — его
выполнение в режиме плана (см. [«Язык алиасов»](language.md#план-сценария)).

## Заявка

```
ochan request prod.conf changes.conf               правка конфига
ochan request restart.yaml --doc заявка.docx       сценарий исполнителя + документ
ochan request сценарий.ochan                       сценарий на языке алиасов
ochan requests                                     очередь
ochan requests 3ff2                                карточка: план, текст, решение
ochan approve 3ff2 --comment "окно с 02:00"        согласовать
ochan reject 3ff2 --reason "нет окна"              отказать (причина обязательна)
ochan apply --request 3ff2                         выполнить согласованное
```

Идентификатор можно сокращать до начала, если оно однозначно.

**Заявка хранит то, что согласуют, а не путь к нему.** Между согласованием
и выполнением файл на диске могли поправить — и выполнилось бы не то, на
что сказали «да». `apply --request` берёт текст из заявки.

**Решение принимается один раз.** Согласованную нельзя отклонить, а
отклонённую — согласовать: пересмотр — новая заявка. Иначе журнал
перестаёт отвечать на вопрос, что именно было одобрено.

```
ошибка: заявка 3ff2670fdd уже согласована — решение принимается один раз
ошибка: заявка 3ff2670fdd не согласована (ждёт решения): выполнять нельзя
```

### Заявка на правку конфига

`ochan request prod.conf changes.conf` фиксирует план правки и полный путь
файла. `apply --request` применяет ровно изменения плана — не перечитанный
файл правок — к тому файлу, где их согласовали, откуда бы ни запускали.
Перед этим файл сверяется с тем, что было при согласовании:

```
ошибка: /srv/pg/prod.conf изменился после согласования заявки 2fb5c48ac0: правка легла бы не на то, что согласовали; оформите новую заявку.
  max_connections: при согласовании 100, сейчас 150
```

Прежнее содержимое попадает в журнал, и `ochan rollback` его возвращает.
Файл пишется заново, как и `patch`: комментарии и порядок строк
conf-файла не сохраняются. Правку живого источника (`postgres://…`) ochan
не записывает — её выполняют на сервере, например `ALTER SYSTEM`.

### Заявка на сценарий на языке алиасов

В заявку попадают текст сценария, план, каталог, от которого отсчитываются
относительные пути, песочница, суммы файлов библиотеки, алиасы из которых
сценарий вызывает, и версии их пакетов. Если сценарий написан по
формальному промпту — ещё промпт, отчёт модели и соблюдённые жёсткие
правила (см. [«Нейросети и формальный промпт»](ai.md)). В карточке и в
документе есть и план, и текст сценария: согласуют не только план, но и
то, что его породило.

Перед выполнением план строится заново и сверяется с согласованным. Если
поправили файл, из которого сценарий строит конфиг, или алиас библиотеки,
выполнение отменяется с объяснением:

```
ошибка: план сценария изменился после согласования заявки 3ff2670fdd: выполнилось бы не то, что согласовали; оформите новую заявку.
Что изменилось:
  /srv/pg/prod.conf: будет записано не то содержимое, что согласовали (поменялись данные, из которых сценарий его строит)
```

Песочница, в которой строили план, действует и при выполнении: её границы
хранятся в заявке, а не берутся из флагов того, кто выполняет.

## Журнал и откат

Каждая операция попадает в журнал `~/.octochan/history`:

```
ochan history              список от новых к старым
ochan history df30         подробности: изменения и файлы до операции
ochan rollback df30        вернуть файлы к состоянию до операции
```

```
+ 2026-10-23 10:47:40  58c33d2838  сценарий  откат операции df3033a89b, файлов: 4
- 2026-10-23 10:47:35  df3033a89b  сценарий  сценарий rollout.ochan, изменений: 10
  2026-10-23 10:47:07  b7cd19aed9  правка файла  out.conf  изменено параметров: 1
  2026-10-23 10:47:07  3df8bb3cdb  сравнение  test.conf  расхождений: 2

+ обратимо, - уже отменено
```

Что откатывается:

| Операция | Откат |
|---|---|
| сценарий на языке алиасов по заявке | каждый записанный файл получает прежнее содержимое, созданный — удаляется; прерванный ошибкой сценарий откатывается так же |
| правка конфига по заявке | файл возвращается к прежнему |
| `patch` поверх существующего файла | файл возвращается к прежнему |
| задачи во внешней системе (`apply` YAML-сценария) | **необратимы**: перезапуск уже произошёл; `rollback` откажет и скажет об этом прямо |

Прежнее содержимое хранится целиком, а не как обратный diff: откат по diff
ломается, если файл успели поправить руками. Журнал пишется с правами 0600;
на сценарий хранится не больше 16 МиБ прежнего содержимого — сверх этого
выполнение предупреждает, что откат недоступен.

**Чужую правку откат не стирает.** Если файл поменяли после операции, откат
отказывает целиком и называет такие файлы; `--force` откатывает всё равно.
Сам откат тоже записывается и тоже обратим: `ochan rollback <откат>` вернёт
результат операции.

## Документ

`--doc заявка.docx` у `request` и `requests <id>` выгружает заявку в
обычный Word-файл: шапка, таблица полей, таблица изменений, текст сценария,
формальный промпт и отчёт модели, если они есть. Формат пишется напрямую
(`archive/zip` + `encoding/xml`), без внешних библиотек и без Word.

## Почта

```yaml
defaults:
  smtp_host: smtp.example.internal
  smtp_port: 587
  smtp_from: octochan@example.internal
  smtp_to: [dba@example.internal, duty@example.internal]
  smtp_user: octochan
  smtp_starttls: true       # требовать шифрование, рекомендуется
  notify_always: false      # true — слать без флага --notify
```

```
export OCTOCHAN_SMTP_PASSWORD=...     # пароль — только через окружение
ochan approve 3ff2 --notify
```

Соединение шифруется всегда, когда сервер это умеет; `smtp_starttls: true`
делает шифрование обязательным — без него письмо не уйдёт. Ненастроенная
почта — не ошибка: письмо некуда слать, и команда делает своё дело молча.
Сбой отправки при настроенной почте показывается, но работу не прерывает:
изменение уже сделано, и откатывать его из-за письма неправильно.
