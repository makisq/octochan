# План, заявки и откат

Во многих компаниях изменение нельзя выполнить просто потому, что оно
правильное: сначала нужна заявка, согласование и бумага. ochan проводит
всю цепочку и на каждом шаге показывает, что именно происходит.

## План

```
ochan plan prod.conf changes.conf      что изменит patch
ochan plan restart.yaml                какие задачи создаст сценарий исполнителя
ochan plan сценарий.ochan              что запишет сценарий на языке алиасов
```

План ничего не меняет. Для правки конфига это параметры, которые изменятся;
для YAML-сценария — задачи, которые были бы созданы (изменяющие запросы
запрещены на уровне клиента); для сценария на языке алиасов — его
выполнение в режиме плана (см. [«Язык алиасов»](language.md#план-сценария)).

## Заявка

```
ochan request prod.conf changes.conf               правка конфига
ochan request restart.yaml --doc заявка.docx       сценарий исполнителя + документ
ochan request сценарий.ochan                       сценарий на языке алиасов
ochan requests                                     очередь
ochan requests 3ff2                                карточка: план, текст, решение
ochan approve 3ff2 --comment "окно с 02:00"        согласовать
ochan reject 3ff2 --reason "нет окна"              отказать (причина обязательна)
ochan apply --request 3ff2                         выполнить согласованное
ochan compensate 3ff2                              оформить обратное действие во внешней системе
ochan request deploy.yaml --after 3ff2             выполнить только после 3ff2
ochan requests --ready                             что можно выполнять сейчас
ochan request raise.yaml --incident 88fb           заявка по инциденту — его шаг
ochan requests --after release#1234                заявки, оформленные в окне триггера
ochan '!!rin' @pgconf                              заявка на установку пакета из реестра
```

Идентификатор можно сокращать до начала, если оно однозначно.

**Заявка хранит то, что согласуют, а не путь к нему.** Между согласованием
и выполнением файл на диске могли поправить — и выполнилось бы не то, на
что сказали «да». `apply --request` берёт текст из заявки.

**Решение принимается один раз.** Согласованную нельзя отклонить, а
отклонённую — согласовать: пересмотр — новая заявка. Иначе журнал
перестаёт отвечать на вопрос, что именно было одобрено.

```
ошибка: заявка 3ff2670fdd уже согласована — решение принимается один раз
ошибка: заявка 3ff2670fdd не согласована (ждёт решения): выполнять нельзя
```

### Состояния

| Состояние | Что значит | Дальше |
|---|---|---|
| ждёт решения | оформлена, решения нет | `approve` или `reject` |
| согласована | можно выполнять | `apply --request` |
| отклонена | конечное | новая заявка |
| выполняется | выполнение началось | выполнена или упала |
| выполнена | конечное | `rollback`, `compensate` |
| упала | конечное: выполнение началось и не закончилось | оформить заново; сделанное до сбоя — `rollback` или `compensate` |

**«Выполняется»** ставится до первого действия под замком заявки: второй
`apply --request` той же заявки, запущенный рядом, откажет, а не выполнит
её ещё раз. Если процесс, который её выполнял, пропал, не записав итога,
исход неизвестен: следующий `apply --request` на той же машине объявит
заявку упавшей. Процесс на другой машине живым не проверить — там ждут
итога, а на паре серверов это решает переключение: пометка доходит до
резерва раньше действия, и `ha promote` объявляет такие заявки упавшими
([«Пара серверов»](server.md#пара-серверов-primary-и-standby)).

### Кто и как согласует

- **Свою заявку роль не согласует** (кроме master): иначе право `request`
  и `approve` у одной роли превращало бы согласование в формальность.
- **Заявку нейросети** (роль `llm`) и **план со слабой поддержкой** —
  каждый шаг прошёл кольца формального промпта, а вместе план держится
  ниже порога — согласуют, только посмотрев план: `approve` показывает
  его, называет самые слабые правила и просит ввести номер заявки; не на
  терминале — `--yes` ([«Кольца»](ai.md#кольца-well_true-и-well_false)).
- **Отказ** требует причины, а у заявки по формальному промпту — ещё и её
  вида: `--reason-kind plan` (по умолчанию) — ошибка плана, `timing`,
  `scope`, `other` — причина не в плане, и журнал решений правилам её не
  засчитывает.
- **Политика** — заранее данное согласование: заявки, которые оформил
  `ochan watch` и которые укладываются в её границы, она согласует сама. В
  карточке видно: «политика new-servers (зарегистрировал …)»
  ([«Слежение»](scenarios.md#слежение-ochan-watch-и-политика)).
- **free** — на узле контура HA-AI так же согласуется заявка модели: master
  передал ей политику, роль и срок. В карточке — «free: агент db7,
  политика fix-db (включил …) — без человека»
  ([«HA-AI, free и инциденты»](ha-ai.md)).

### Заявка на правку конфига

`ochan request prod.conf changes.conf` фиксирует план правки и полный путь
файла. `apply --request` применяет ровно изменения плана — не перечитанный
файл правок — к тому файлу, где их согласовали, откуда бы ни запускали.
Перед этим файл сверяется с тем, что было при согласовании:

```
ошибка: /srv/pg/prod.conf изменился после согласования заявки 2fb5c48ac0: правка легла бы не на то, что согласовали; оформите новую заявку.
  max_connections: при согласовании 100, сейчас 150
```

Прежнее содержимое попадает в журнал, и `ochan rollback` его возвращает.
Файл пишется заново, как и `patch`: комментарии и порядок строк
conf-файла не сохраняются. Правку живого источника (`postgres://…`) ochan
не записывает — её выполняют на сервере, например `ALTER SYSTEM`.

### Заявка на сценарий исполнителя

`ochan request restart.yaml role=standalone` фиксирует текст сценария,
параметры командной строки и план исполнителя. Исполнитель получает план,
на который сказали «да», и обязан применить ровно его: не пересчитывать
задачу и не делать ничего сверх плана. Перед выполнением ochan просит у
исполнителя план заново и сверяет с согласованным — поменялись сценарий,
параметры или сама внешняя система, и выполнения нет:

```
ошибка: план изменился после согласования заявки 2fb5c48ac0: выполнилось бы не то, на что сказали «да»; оформите новую заявку.
  пропало: задача CI1: limit = 300 (система v1)
  появилось: задача CI1: limit = 300 (система v2)
```

Без заявки `ochan apply restart.yaml` тоже идёт через план: исполнитель
строит его, ochan показывает и передаёт исполнителю ровно его. Исполнитель
модуля, собранного до ochan 0.2.0, плана не получает — им ochan не
выполняет и просит пересобрать модуль.

### Заявка на сценарий на языке алиасов

В заявку попадают текст сценария, план, каталог, от которого отсчитываются
относительные пути, песочница, суммы файлов библиотеки, алиасы из которых
сценарий вызывает, и версии их пакетов. Если сценарий написан по
формальному промпту — ещё промпт, отчёт модели и соблюдённые жёсткие
правила (см. [«Нейросети и формальный промпт»](ai.md)). В карточке и в
документе есть и план, и текст сценария: согласуют не только план, но и
то, что его породило.

Перед выполнением план строится заново и сверяется с согласованным. Если
поправили файл, из которого сценарий строит конфиг, или алиас библиотеки,
выполнение отменяется с объяснением:

```
ошибка: план сценария изменился после согласования заявки 3ff2670fdd: выполнилось бы не то, что согласовали; оформите новую заявку.
Что изменилось:
  /srv/pg/prod.conf: будет записано не то содержимое, что согласовали (поменялись данные, из которых сценарий его строит)
```

Песочница, в которой строили план, действует и при выполнении: её границы
хранятся в заявке, а не берутся из флагов того, кто выполняет.

## Порядок между заявками

`--after <id>` — заявка выполнится только после указанных: сначала схема
базы, потом приложение.

```
$ ochan request db.conf step1.conf
Заявка 371c921959 создана (ждёт решения)
$ ochan request app.conf app2.conf --after 371c
Заявка 380539c2ee создана (ждёт решения)
Выполнится после: 371c921959

$ ochan approve 371c && ochan approve 3805
$ ochan requests
2026-10-27 10:23  380539c2ee  ожидает (зависит от 371c921959)  /srv/app.conf  правка app.conf, параметров: 1
2026-10-27 10:23  371c921959  согласована   /srv/db.conf  правка db.conf, параметров: 1

$ ochan apply --request 3805
ошибка: заявка 380539c2ee ожидает: зависит от 371c921959 (согласована) — сначала ochan apply --request 371c921959
$ ochan apply --request 371c
Заявка 371c921959 выполнена: /srv/db.conf, изменено параметров: 1
$ ochan requests --ready
2026-10-27 10:23  380539c2ee  согласована   /srv/app.conf  правка app.conf, параметров: 1
```

Ядро держит только порядок. Повтор, расписание и продолжение с места —
дело модуля рабочего процесса: он берёт заявки из `ochan requests --ready`
и выполняет их в своём темпе. Цикла быть не может: `--after` называет
только уже существующие заявки.

**Сбой: A выполнена, B ждала A и упала.**

- **A остаётся.** Сбой B её не откатывает: A согласовали и выполнили
  отдельно, её результат верен сам по себе. Вернуть её — отдельное решение:
  `ochan rollback` или `ochan compensate`.
- **B не повторяют, а пересобирают.** Она упала посреди выполнения, и
  согласованный план уже не описывает систему. Состояние «упала» —
  конечное; новую B оформляют с `--after A` и согласуют заново.
- **Заявки после B не выполнятся**: они строились в расчёте на B. Список
  показывает их «не выполнится (B упала)», согласовать их нельзя.

Это сказано и в самом сбое:

```
Создано:
  - job-CI2
Заявка 5e0d… упала.
  До сбоя сделано: job-CI2.
  Заявки, после которых она шла, остаются выполненными — её сбой их не откатывает: 371c921959.
  Заявку не повторяют: оформите её заново (ochan request b.yaml --after 371c921959) и согласуйте.
  Вернуть сделанное до сбоя: ochan compensate 5e0d….
  Не выполнятся, пока их не оформят заново после новой: 7b21….
ошибка: система отказала на второй задаче
```

Упавшей считается заявка, выполнение которой началось. Если исполнитель
отказал до первого обращения к системе (модуль собран до 0.2.0, запросы
разошлись с планом), заявка остаётся согласованной: «Выполнение не
начиналось». Расхождение плана и невыполненные зависимости проверяются до
выполнения и тоже ничего не меняют.

Сделанное до сбоя остаётся в заявке и в журнале: файлы сценария
откатывает `ochan rollback`, задачи во внешней системе — `ochan
compensate` упавшей заявки. Откат A, после которой выполнены другие,
предупреждает: их он не трогает.

Нейросеть ставит порядок так же — полем `after` у `request_config`,
`request_scenario` и `request_script`.

## Журнал и откат

Каждая операция попадает в журнал `~/.octochan/history`:

```
ochan history              список от новых к старым
ochan history df30         подробности: изменения и файлы до операции
ochan rollback df30        вернуть файлы к состоянию до операции
```

```
+ 2026-10-23 10:47:40  58c33d2838  сценарий  откат операции df3033a89b, файлов: 4
- 2026-10-23 10:47:35  df3033a89b  сценарий  сценарий rollout.ochan, изменений: 10
  2026-10-23 10:47:07  b7cd19aed9  правка файла  out.conf  изменено параметров: 1
  2026-10-23 10:47:07  3df8bb3cdb  сравнение  test.conf  расхождений: 2

+ обратимо, - уже отменено
```

Что откатывается:

| Операция | Откат |
|---|---|
| сценарий на языке алиасов по заявке | каждый записанный файл получает прежнее содержимое, созданный — удаляется; прерванный ошибкой сценарий откатывается так же |
| правка конфига по заявке | файл возвращается к прежнему |
| `patch` поверх существующего файла | файл возвращается к прежнему |
| задачи во внешней системе (`apply` YAML-сценария) | `rollback` их не откатывает: прежнего состояния внешней системы у ochan нет. Обратное действие — `ochan compensate` (ниже) |

Прежнее содержимое хранится целиком, а не как обратный diff: откат по diff
ломается, если файл успели поправить руками. Журнал пишется с правами 0600;
на сценарий хранится не больше 16 МиБ прежнего содержимого — сверх этого
выполнение предупреждает, что откат недоступен.

**Чужую правку откат не стирает.** Если файл поменяли после операции, откат
отказывает целиком и называет такие файлы; `--force` откатывает всё равно.
Сам откат тоже записывается и тоже обратим: `ochan rollback <откат>` вернёт
результат операции.

## Обратное действие во внешней системе

`rollback` точный: прежнее содержимое файлов ochan записал сам. Во
внешней системе прежнего состояния у него нет, и обратное действие —
отдельная операция, вторая согласованная:

```
ochan compensate 7a8f          исполнитель строит план обратного действия, ochan оформляет заявку
ochan approve <id>             её согласуют, как любую другую
ochan apply --request <id>     выполняют: план снова строится и сверяется с согласованным
```

- Обратное действие строит исполнитель (`scenario.Compensator`): он знает,
  что сделала задача и можно ли это вернуть. В его план входят следы
  выполнения заявки — номера задач.
- **Если обратного действия нет — честный отказ.** Исполнитель его не умеет
  (как RLM) или задача уже отработала так, что вернуть нечего:

  ```
  ошибка: исполнитель RLM не умеет обратного действия: вернуть сделанное по заявке 7a8f… можно только средствами самой системы — ochan этого не обещает
  ошибка: обратного действия для заявки 7a8f… нет: задачи job-CI1 уже отработали, прежнее значение неизвестно
  ```

- Обратное действие у заявки одно, и только у выполненной или упавшей на
  полпути; у правки файлов его нет — там `rollback`.
- В карточке видно, кто чьё обратное действие: «Обратное действие: заявка
  …» у исходной и «Обратное действие заявки …» у второй.

## Документ

`--doc заявка.docx` у `request` и `requests <id>` выгружает заявку в
обычный Word-файл: шапка, таблица полей, таблица изменений, текст сценария,
формальный промпт и отчёт модели, если они есть. Формат пишется напрямую
(`archive/zip` + `encoding/xml`), без внешних библиотек и без Word.

## Почта

```yaml
defaults:
  smtp_host: smtp.example.internal
  smtp_port: 587
  smtp_from: octochan@example.internal
  smtp_to: [dba@example.internal, duty@example.internal]
  smtp_user: octochan
  smtp_starttls: true       # требовать шифрование, рекомендуется
  notify_always: false      # true — слать без флага --notify
```

```
export OCTOCHAN_SMTP_PASSWORD=...     # пароль — только через окружение
ochan approve 3ff2 --notify
```

Соединение шифруется всегда, когда сервер это умеет; `smtp_starttls: true`
делает шифрование обязательным — без него письмо не уйдёт. Ненастроенная
почта — не ошибка: письмо некуда слать, и команда делает своё дело молча.
Сбой отправки при настроенной почте показывается, но работу не прерывает:
изменение уже сделано, и откатывать его из-за письма неправильно.
