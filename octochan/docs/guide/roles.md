# Роли и права

Каждая команда проверяет права текущей роли — и в командной строке, и в
оболочке, и на сервере. После установки есть две роли:

| Роль | Права | |
|---|---|---|
| `master` | `all` — всё | первая и высшая; на своём компьютере ты master |
| `llm` | `read`, `plan`, `request` | для нейросетей: читать, планировать, оформлять заявки |

Остальные роли создаёт `master`. Право — группа, `all` или имя отдельной
команды (вложенная пишется через точку: `role.create`):

| Группа | Команды |
|---|---|
| `read` | aliases, check, diff, else, find, fp, history, if, lang, logs, modules, print, requests, sandbox, services, stats, status, validate |
| `plan` | plan |
| `request` | request |
| `approve` | approve, reject |
| `apply` | apply, eval, patch, rollback, run, srs, tee |
| `install` | !install, inspect |
| `auth` | auth, timer |
| `admin` | role create, role delete, role deny, role grant, role limit, role revoke, role scope, role undeny, role update |
| `audit` | audit, audit verify |
| `server` | serve, tls init |
| `remote` | connect, remote |

`help`, `shell`, `role`, `role list`, `role show`, `set role` и `back role`
доступны любой роли: без них нельзя узнать, кто ты, и вернуться обратно. Право на
каждую команду — в [справочнике команд](../reference/commands.md).

## Управление ролями

```
ochan role create slave --allow read,plan
ochan role create Dan --allow read,plan,request,approve --nlogin dan --npsw
ochan role grant slave approve
ochan role revoke slave approve
ochan role update master --npsw
ochan role update slave --nlogin dan --npsw --rename worker
ochan role delete worker
ochan role list
ochan role show slave
```

```
* master           all                              встроенная
  llm              read, plan, request              встроенная
  ci               read, plan, request
  Dan              read, plan, request, approve     логин, пароль
```

Неизвестное право — ошибка, а не пустое место: опечатка не выдаст роли
ничего молча. Права модулей команд тоже можно выдавать — по имени команды.

## Запреты

Запрет перекрывает право, в том числе `all`: «всё, кроме сервера и
управления ролями» пишется так, а не перечислением всего остального.

```
$ ochan role create ops --allow all --deny serve,admin
$ OCTOCHAN_ROLE=ops ochan role create x --allow read
ошибка: команда role create роли ops запрещена
$ ochan role undeny ops admin
```

Запрет команды открывает и её подкоманды: `deny role` закрывает
`role create`, но не `role`, `role show` и `set role` — без них не узнать
свою роль и не вернуться.

## Область

Область — каталоги, вне которых роль не работает.

```
$ ochan role scope dan /srv/configs/team-a
$ cd /srv/configs/team-a
$ OCTOCHAN_ROLE=dan ochan diff a.conf ../team-b/a.conf
ошибка: ../team-b/a.conf вне области роли dan (/srv/configs/team-a)
```

Внутри области должны лежать текущий каталог, каждый аргумент и каждое
значение строкового флага, понятые как путь (символические ссылки
раскрываются), каталоги песочницы, файлы заявок, которые роль согласует или
выполняет, и файлы, которые она откатывает. Сценарии такой роли всегда идут
в песочнице — без `--sandbox` она ставится сама, с текущим каталогом; `eval`
ей недоступен: он выполняет язык без песочницы. Заявку на сценарий без
песочницы и правку живого источника роль с областью не согласует и не
выполнит. Снять — `ochan role scope dan --clear`.

На [сервере](server.md) роль без своей области ограничена каталогом
сервера.

## Пределы

Предел — сколько раз за окно времени роль может выполнить команды права:

```
$ ochan role limit dan apply=10/1h approve=20/1d
$ ochan role limit llm request=30/1h
```

Окно — от `1m` до `31d`. Считается по [журналу аудита](#журнал-аудита),
по всем сессиям роли вместе, под его замком: два процесса не пройдут оба по
последней единице предела. Отказ тоже пишется в журнал:

```
ошибка: предел роли dan исчерпан: apply=10/1h; следующая попытка через 23m14s
```

Предел того же права заменяет прежний, `--clear` снимает все. У `llm` по
умолчанию предел `request=30/1h`.

## Согласование

Свою заявку роль не согласует: право `request` и `approve` у одной роли
иначе превращало бы согласование в формальность.

```
$ OCTOCHAN_ROLE=dan ochan approve 2fb5
ошибка: заявку роли dan согласует другая роль: свою заявку не согласуют
```

Исключение — master: на своей машине человек один. В заявке видно, кто и в
какой роли её оформил и согласовал.

Заявку роли `llm` согласуют, только посмотрев план: `approve` показывает
его и на терминале просит ввести номер заявки; не на терминале —
`--yes`. Вредная инструкция, подсунутая модели, рассчитывает как раз на
то, что человек согласует не глядя.

## Журнал аудита

Каждая команда, вход на сервер и смена роли пишутся в
`~/.octochan/audit.log` — разрешённые и отвергнутые, с причиной отказа и
адресом клиента сервера:

```
$ ochan audit --role dan --denied
- 2026-10-23 12:57:03  dan        root             diff a.conf ../team-b/a.conf
    ../team-b/a.conf вне области роли dan (/srv/configs/team-a)

+ разрешено, - отказано
$ ochan audit verify
Журнал аудита цел: записей 214, с 2026-10-20 09:12:44 по 2026-10-23 12:57:03
Хеш последней записи: 3f9a1c0b2e7d…
```

Записи связаны цепочкой хешей; как её проверять и зачем уносить хеш с
машины — в [«Безопасности»](security.md#журнал-аудита). Без журнала роль,
кроме master, не работает: master получает предупреждение, остальные —
отказ.

## Переключение

```
$ ochan set role slave
Роль: slave
$ ochan apply --request 3ff2
ошибка: роль slave не может выполнять apply: нужно право apply
$ ochan back role
Роль: master
```

`back role` возвращает к роли, которая была текущей до последнего
переключения; два возврата подряд приводят туда же, откуда начали:

```
ochan set role slave     # master -> slave
ochan back role          # slave  -> master
ochan back role          # master -> slave
ochan back role master   # к конкретной роли из истории
```

Логин и пароль `back role` не спрашивает: в роль уже входили. Поэтому,
зайдя мастером и переключившись проверить роль слейва, к master
возвращаешься без пароля. Если у роли сменили логин или пароль, она уходит
из истории, и вернуться в неё можно только через `set role` со входом.

Текущая роль и история хранятся в `roles.bin` и переживают перезапуск;
в приглашении оболочки видна роль: `ochan[slave]>`.

## Логин и пароль

Если у роли задан логин или пароль, `set role` их спрашивает. Пароль
вводится без эха; не на терминале — одной строкой из stdin:

```
printf 'dan\nпароль\n' | ochan set role Dan
```

Задаётся и меняется через `--npsw`, логин — через `--nlogin`, снимаются
через `--drop-psw` и `--drop-login`.

Хранилище — двоичный `~/.octochan/roles.bin` с правами 0600 и контрольной
суммой. Логин и пароль в нём — только соль и хеш argon2id. Испорченный
файл — ошибка, а не тихий откат к master без паролей.

## Роль из окружения

```
OCTOCHAN_ROLE=ci ochan validate prod.conf
```

Так удобно запускать ochan в CI и из других программ. Окружением задаётся
только роль **без** логина и пароля — иначе `OCTOCHAN_ROLE=master` обходил
бы пароль master:

```
ошибка: OCTOCHAN_ROLE=Dan: роль защищена логином или паролем, задать её окружением нельзя; войдите командой set role Dan
```

## Роль llm

`ochan-mcp` запускает `ochan` с `OCTOCHAN_ROLE=llm`: что бы ни было
текущей ролью пользователя, нейросеть работает в своей. Это второй рубеж
за закрытой таблицей инструментов сервера MCP: даже при ошибке в таблице
`ochan` откажет в выполнении сам.

Потолок `llm` — `read`, `plan`, `request`. Выдать ей `apply`, `approve`,
`admin` и прочее нельзя и master: нейросеть предлагает, решает человек.
Сверх потолка — предел заявок и подтверждение при согласовании (см.
выше); область и запреты задаются ей, как любой другой роли.

## Чем роли являются и чем нет

Локально роли — защита от ошибки и граница для нейросети, а не от
владельца компьютера: кто может удалить `~/.octochan`, тот вернёт роли к
исходным. Границей против других людей они становятся в
[серверном режиме](server.md): хранилище ролей лежит у сервера, а
подключаются к нему по сети.

Рабочий каталог ochan закрыт для всех ролей, кроме master: ни аргумент
команды, ни песочница сценария, ни встроенная функция в него не
дотянутся. Иначе роль с правом `apply` прочитала бы `roles.bin` с ключом
подписи допусков сервера и стала бы master. У master нет ни запретов, ни
области, ни пределов: одна ошибка заперла бы владельца без способа
вернуться.
