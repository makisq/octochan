# Серверный режим

Общий оркестратор — ochan на сервере или соседней машине, к которому
подключаются по сети в одной из его ролей. Роли и пароли хранит сервер и
проверяет их сам: у подключившегося хранилища нет, обойти вход ему нечем.

## Запуск сервера

```
ochan tls init --host orchestrator.example --host 10.0.0.5
ochan serve --listen 0.0.0.0:7443
```

```
Сертификат: ~/.octochan/tls/server.crt
Ключ:       ~/.octochan/tls/server.key (права 0600)
Имена:      localhost, 127.0.0.1, ::1, orchestrator.example, 10.0.0.5
Отпечаток:  68:D3:5F:C5:9E:AA:D0:41:…
Клиентам: скопировать сертификат и указать его в tls.ca их config.yaml

Сервер слушает https://0.0.0.0:7443
Каталог:   /srv/octochan
Сертификат: 68:D3:5F:C5:9E:AA:D0:41:…
```

`tls init` создаёт самоподписанный сертификат ECDSA P-256 и ключ.
Клиентам этот же сертификат указывается как `tls.ca`: он сам себе
удостоверяющий центр. Сверьте отпечаток, когда передаёте его.

Команды клиента выполняются на сервере над его файлами в каталоге
`server.dir` (по умолчанию — где запущен `serve`). Каждая — отдельным
процессом ochan в роли сессии, с теми же правами, что в командной строке.
Не выполняются `shell`, `serve`, `connect`, `remote` и флаг `--config` —
чужой конфиг мог бы увести токен API на чужой адрес.

## Подключение

На клиенте — сертификат сервера в `tls.ca`:

```yaml
tls:
  ca: /home/dan/.octochan/orchestrator.crt
```

```
ochan connect orchestrator.example:7443 --role Dan
```

```
Логин: dan
Пароль: (ввод скрыт)
Подключено к orchestrator.example:7443, роль Dan
ochan@orchestrator.example:7443[Dan]> diff prod.conf test.conf
ochan@orchestrator.example:7443[Dan]> set role slave
Роль: slave
ochan@orchestrator.example:7443[slave]> back role
Роль: Dan
ochan@orchestrator.example:7443[Dan]> exit
```

Если у роли нет логина и пароля, вход происходит сразу. Внутри сессии
`role` показывает роль и историю, `set role` переключает её со входом,
`back role` возвращает по кольцу, как и локально. У каждой сессии своя
роль и своя история: общее хранилище сервера они не трогают.

Одна команда без сессии:

```
ochan remote orchestrator.example:7443 diff prod.conf test.conf
cat новый.conf | ochan remote --role Dan orchestrator.example:7443 validate -
```

Флаги `remote` пишутся до адреса: всё после него — команда для сервера.
Аргумент `-` передаёт серверу stdin. Логин и пароль без вопросов — из
`OCTOCHAN_REMOTE_LOGIN` и `OCTOCHAN_REMOTE_PASSWORD`. Новый пароль для
`role create|update --npsw` спрашивает клиент и передаёт серверу на stdin.

## Настройки

```yaml
ssl: true                 # шифрование соединения вкл/выкл
tls:
  min_version: "1.2"      # 1.2 или 1.3; SSL 3.0, TLS 1.0 и 1.1 небезопасны
  cert: ~/.octochan/tls/server.crt   # сервер
  key: ~/.octochan/tls/server.key    # сервер
  ca: ""                  # клиент: чем проверять сервер; пусто — системные
  server_name: ""         # клиент: имя в сертификате, если не совпадает с адресом
server:
  listen: 127.0.0.1:7443
  dir: ""                 # каталог, над файлами которого работают команды
  session_timeout: 30m    # сессия без запросов
  command_timeout: 10m    # одна команда
```

SSL — старое имя TLS: «SSL-подключение» здесь и есть TLS. Без `ssl`
сервер слушает и клиент подключается только к этой же машине, иначе
пароли шли бы по сети открытым текстом; `--allow-plaintext` снимает
запрет. Проверку сертификата отключить нельзя: без неё пароль ушёл бы
любому, кто встал посередине.

## Защита входа

- Пароль проверяет сервер, по хешу argon2id; одновременно — не больше
  четырёх проверок, чтобы параллельные входы не съели память.
- Пять неудачных входов подряд блокируют пару «адрес, роль» на минуту.
- На несуществующую роль сервер отвечает так же, как на роль с паролем:
  перебирать имена ролей по ответам нельзя.
- Сессия живёт 30 минут без запросов и 12 часов всего. В памяти сервера
  лежит хеш токена, а не сам токен.
- Сменили логин или пароль роли — все её сессии закрываются, а `back role`
  в неё без нового входа не пустит. Удалили роль — её сессии тоже.
- Роль дочернему процессу передаётся допуском сервера: роль, срок и
  подпись ключом, который меняется при каждом запуске `serve`. Окружением
  без допуска роль с паролем не задать.
- Каждый вход, отказ и команда пишутся в журнал сервера (stderr `serve`) и
  в [журнал аудита](roles.md#журнал-аудита) с адресом клиента — там же
  неудачные входы и смены ролей.

Права `server` и `remote` не входят в потолок роли `llm`: нейросеть,
подключившись к серверу, где у master нет пароля, стала бы master.

## Чужие роли на сервере

На общем сервере роль — граница между людьми, поэтому клиенту доступно
меньше, чем той же роли на своей машине:

- **Каталог сервера.** Роль без своей [области](roles.md#область)
  ограничена каталогом сервера (`server.dir`): ни аргумент команды, ни
  флаг, ни песочница сценария за него не выходят. Клиенту с `apply` иначе
  был бы доступен любой файл машины.

  ```
  $ ochan remote print /etc/passwd
  ошибка: /etc/passwd вне области роли dan (/srv/configs)
  ```

- **Сценарии** клиентов всегда идут в песочнице, с ограничениями ядра.
- **Рабочий каталог ochan** сервера закрыт: в нём хранилище ролей с ключом
  подписи допусков.
- **Запреты, пределы и разделение обязанностей** —
  [как у любой роли](roles.md#запреты): `ochan role limit dan apply=10/1h`
  считает выполнения всех сессий роли вместе.

Права на машине сервера проверяет сам сервер, а затем — ещё раз —
дочерний процесс ochan, которому сервер передал роль допуском.

## Запуск как служба

`serve` — обычный процесс переднего плана; под systemd он запускается как
любая служба:

```ini
# /etc/systemd/system/octochan.service
[Unit]
Description=octochan shared orchestrator
After=network-online.target

[Service]
User=octochan
WorkingDirectory=/srv/octochan
ExecStart=/usr/local/bin/ochan serve --listen 0.0.0.0:7443
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Пользователь службы — владелец `~/.octochan` с ролями и сертификатом.

## Пара серверов: primary и standby

Два узла `ochan serve`: **primary** пишет, **standby** держит копию его
состояния — заявки, журнал операций, решения, политики, роли с паролями и
ключом допусков, журнал аудита, инвентарь, реестр агентов, библиотеку
алиасов. Не копируются настройки узла (`config.yaml`, `tls/`, `ha.json`,
`ha.token`), токены исполнителей и модули: их ставят на оба узла.

**Консенсуса нет — и не обещается.** Кто владеет заявкой — отвечает
primary: только он создаёт, согласует и выполняет её. Переключение —
решение человека.

```yaml
# a: ~/.octochan/config.yaml            # b: то же, адреса наоборот
ha:
  peer: b.example:7443
  self: a.example:7443
```

```
a$ ochan ha init --node a --role primary
Общий секрет пары: /home/octochan/.octochan/ha.token (права 0600) — скопируйте его на второй узел
Узел a: primary, эпоха 1
b$ ochan ha init --node b --role standby      # после того как ha.token скопирован
a$ ochan serve --listen 0.0.0.0:7443
b$ ochan serve --listen 0.0.0.0:7443

$ ochan ha status a.example:7443,b.example:7443
a.example:7443           a — primary, эпоха 1
b.example:7443           b — standby, эпоха 1, копия от 2026-10-29 10:42:13 (2s назад)
```

- **Копия.** Раз в `ha.replicate_every` standby забирает у primary опись
  файлов и те, что изменились; узлы подтверждают друг другу, что они пара,
  общим секретом. Без ssl узлы на разных машинах друг к другу не ходят:
  копия содержит хеши паролей.
- **Standby только читает.** Команды чтения (`requests`, `history`,
  `status`…) он выполняет по копии; на запись отвечает отказом с адресом
  primary:

  ```
  ошибка: узел b — standby (эпоха 1): здесь только чтение; запись — на primary a.example:7443
  ```

- **Клиент знает оба адреса** и сам находит primary:
  `ochan connect a.example:7443,b.example:7443`. Primary не нашёлся, а
  standby на связи — клиент подключается к нему для чтения и предупреждает
  об этом: журнал и заявки можно смотреть, пока человек решает, кого
  повысить. После переключения он
  входит на новый primary теми же логином и паролем и говорит об этом
  (`primary пары сменился: …`). С `--balance` (или `remote.balance_reads`)
  чтение идёт по очереди на все узлы. Повторяет клиент только то, что
  точно не выполнялось: отказ standby или узел, до которого не
  достучаться. Если связь оборвалась посреди команды, исход неизвестен, и
  клиент так и говорит, а не повторяет запись.

### Переключение

```
b$ ochan ha promote
Второй узел a.example:7443 не отвечает: …
Узел b — primary, эпоха 2
Заявка 0badc0de00 упала: исход неизвестен: заявка выполнялась (узел a (эпоха 1), a-host, процесс 4121, с …), когда узел a перестал быть primary
```

- **Эпоха — забор.** `promote` делает эпоху узла на единицу больше
  известной. Работающий `serve` подхватывает её сам. Бывший primary,
  вернувшись и увидев большую эпоху, отступает сам: становится standby, а
  своё состояние — с тем, что успел записать после разрыва, — не сливает и
  не стирает, а откладывает целиком в `~/.octochan/ha/diverged-e1-…`;
  `ochan ha status` показывает, где. Решать, что с этим делать, —
  человеку.
- **Два primary одной эпохи** — конфликт: оба закрывают запись, пока
  человек не повысит одного.
- **Выполнение не удваивается.** Перед выполнением заявка помечается
  «выполняется», и primary ждёт, пока пометка дойдёт до standby (барьер).
  `promote` находит заявки, которые выполнялись на прежнем primary, и
  объявляет их исход неизвестным — они упали и второй раз не
  выполняются ([«Порядок между заявками»](requests.md#порядок-между-заявками)).
  Если резерв не подтвердил пометку, выполнение идёт с предупреждением;
  с `ha.require_standby: true` — не начинается.
- **Чего пара не делает.** Не переключается сама: автоматическое
  переключение без консенсуса при разрыве сети дало бы два primary.
  Если бывший primary жив и отрезан сетью, до восстановления связи он
  принимает запись — остановите его или отрежьте от клиентов, прежде чем
  повышать резерв. Файлы, которые команды правят в `server.dir`, пара не
  копирует: держите их на общем хранилище или работайте через
  исполнителей.

Права: `ha` и `ha status` — чтение, `ha init` и `ha promote` — `server`.
Пошагово, с выводами — рецепт [«Пара серверов и агенты»](../cookbook/ha-pair.md).

## Агенты

Агент — машина, которая сама сообщает серверу о себе: имя, группы,
переменные; адрес сервер берёт из соединения.

```
db7$ OCTOCHAN_REMOTE_PASSWORD=… ochan agent run --server a.example:7443,b.example:7443 \
       --name db7 --group db,db_new --var svm_ci=CI007 --every 1m
10:42:13  Агент db7 зарегистрирован (10.0.0.7)
10:43:13  Агент db7 на связи (10.0.0.7)

$ ochan agents
db7              на связи   10.0.0.7               db, db_new           12s назад, роль agent
```

- На сервере для агентов — роль с правом `agent`: оно открывает только
  `agents beat`. Имя агента принадлежит роли, в которой он пришёл первым:
  другая роль его не займёт.
- Реестр — **источник инвентаря**: `agents://` — все, `agents://online` —
  только те, что сообщали о себе за три своих промежутка (не меньше трёх
  минут). У хоста есть переменные `agent_address`, `agent_online`,
  `agent_last_seen`.

  ```yaml
  inventory:
    sources:
      agents: agents://online
  ```

  Цели сценариев берутся из реестра, а `ochan watch --source agents
  --policy new-servers` видит новый агент как новый хост и действует по
  [политике](scenarios.md#слежение-ochan-watch-и-политика).
- Реестр копируется на standby, и агент со списком адресов переживает
  переключение пары. `ochan agents forget db7` (право `approve`) убирает
  запись.
