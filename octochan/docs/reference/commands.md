# Справочник команд

Все команды ochan с флагами и правом, которое их открывает (см. [роли](../guide/roles.md)).
Справка по команде — `ochan help <команда>` или `ochan <команда> --help`; версия — `ochan --version`.

## Общие флаги

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--config` | string | — | путь до конфига (по умолчанию ~/.octochan/config.yaml) |
| `--verbose` | bool | — | дублировать журнал в stderr |

## ochan !!install

Установить модуль или пакет алиасов.

```
ochan !!install <модуль.hcplugin | пакет | файл.ochan>
```

Одна команда ставит всё, чем расширяется ochan, в ~/.octochan/modules:

  модуль.hcplugin  модуль gRPC: команды, языки и исполнители сценариев —
                   что он объявит. Фиксируется его контрольная сумма, и
                   подменённый после установки файл не загрузится
  пакет            каталог с алиасами (*.ochan) и package.yaml — скилл для
                   сценариев и формального промпта. Модули .hcplugin из
                   каталога ставятся вместе с ним: скилл и его исполнитель
  файл.ochan       однофайловый пакет алиасов

Пакет проверяется до установки: с ошибкой он не ставится и библиотеку не
ломает. Исполнитель модуля выбирается по полю service сценария, как
встроенный; его токен — ochan auth --executor <имя>.

С --remove удаляет модуль (имя файла) или пакет (имя пакета).

Право: `install`.

Примеры:

```
ochan '!!install' ssh-runner.hcplugin
ochan '!!install' ./pgconf
ochan '!!install' --remove pgconf
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--remove` | bool | — | удалить модуль или пакет алиасов |

## ochan !!registry

Реестры пакетов: источники, ключи подписи, публикация, отзыв.

```
ochan !!registry
```

Без подкоманды — источники registry.sources по приоритету и ключи
registry.keys. Свой реестр — каталог: keygen создаёт ключ подписи, publish
кладёт пакет и подписывает индекс, revoke отзывает версию. Каталог
отдают по HTTP или коммитят в git.

Право: `install`.

Примеры:

```
ochan '!!registry'
ochan '!!registry' keygen corp-release
ochan '!!registry' publish ./pgconf --registry /srv/registry --key corp-release.key
ochan '!!registry' revoke @pgconf v1.3.0 --registry /srv/registry --key corp-release.key --reason "CVE-2026-1234"
```

Подкоманды: [`keygen`](#ochan-registry-keygen), [`publish`](#ochan-registry-publish), [`revoke`](#ochan-registry-revoke).

## ochan !!rin

Поставить пакет алиасов из реестра — с планом и согласованием.

```
ochan !!rin <@пакет> [версия]
```

Ищет пакет в registry.sources по приоритету, строит план установки —
источник, что и куда разместит, режимы, зависимости, подпись индекса,
sha256 архива — и оформляет заявку. После ochan approve <id> пакет
ставит ochan apply --request <id>: ровно тот архив, сумму которого
согласовали. Отозванная автором версия не ставится.

--plan — только показать план; --approve — поставить сразу, если роль
может согласовывать.

Право: `install`.

Примеры:

```
ochan '!!rin' @pgconf --plan
ochan '!!rin' @pgconf v1.4.0
ochan '!!rin' @pgconf --approve
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--approve` | bool | — | поставить сразу, без заявки: роли нужно право approve |
| `--plan` | bool | — | только показать план установки |

## ochan !!search

Найти пакет алиасов в реестрах.

```
ochan !!search <слово>
```

Ищет по имени и описанию пакета во всех источниках registry.sources —
и только в них. Источники одного приоритета — одним блоком.

Право: `read`.

Примеры:

```
ochan '!!search' pgconf
```

## ochan agent run

Сообщать серверу о себе раз в --every.

```
ochan agent run --server <host:port[,host:port]> --name <имя> [--group g] [--var k=v]
```

Входит на сервер в роли --role (по умолчанию agent; ей нужно право agent),
раз в --every выполняет там ochan agents beat с именем, группами и
переменными этой машины. Логин и пароль — из OCTOCHAN_REMOTE_LOGIN и
OCTOCHAN_REMOTE_PASSWORD: спросить некого. Пара серверов — адреса через
запятую: агент переживает её переключение. --once — один раз, для cron.

Право: `remote`.

Примеры:

```
ochan agent run --server a.example:7443,b.example:7443 --name db7 --group db,db_new \
  --var svm_ci=CI007 --every 1m
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-plaintext` | bool | — | разрешить подключение без ssl к другой машине |
| `--every` | duration | `1m0s` | как часто сообщать о себе |
| `--free-for` | string | — | free: срок, например 4h |
| `--free-policy` | string | — | free: политика — что выполнять без человека |
| `--free-role` | string | — | free: чьи права на выполнение модель берёт |
| `--group` | stringSlice | — | группы агента |
| `--isolation` | string | `natural` | natural — модель только предлагает; free — выполняет по политике (только master, только HA-AI) |
| `--name` | string | — | имя агента — имя хоста в инвентаре |
| `--once` | bool | — | сообщить один раз и выйти |
| `--role` | string | `agent` | роль агента на сервере |
| `--server` | string | — | адрес сервера; пара — через запятую |
| `--var` | stringArray | — | переменная агента ключ=значение |

Реестр агентов: машины, которые сами сообщают серверу о себе.

```
ochan agents
```

Агент — машина с ochan agent run: раз в --every он сообщает серверу имя,
группы и переменные, а сервер запоминает и его адрес. Реестр — источник
инвентаря agents:// (agents://online — только на связи): цели сценариев
берутся из него, а ochan watch --source agents видит новый агент как
новый хост и действует по политике.

Право: `read`.

Подкоманды: [`beat`](#ochan-agents-beat), [`forget`](#ochan-agents-forget), [`free`](#ochan-agents-free).

## ochan agents beat

Сообщить серверу о себе — это вызывает ochan agent run.

```

```

Обновляет запись агента в реестре: группы, переменные, адрес, время.
Имя принадлежит роли, в которой агент сообщил о себе первый раз: другая
роль его не займёт. Право — agent.

Право: `agent`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--every` | duration | `1m0s` | как часто агент сообщает о себе |
| `--group` | stringSlice | — | группы агента |
| `--name` | string | — | имя агента — имя хоста в инвентаре |
| `--var` | stringArray | — | переменная агента ключ=значение |

## ochan agents free

Включить free агенту: модель выполняет без человека по политике.

```
ochan agents free <агент> --role <роль> --for <срок> --policy <политика>
```

Только master и только на primary контура HA-AI (ochan ha contour ai).
Заявка модели (роль llm), которая укладывается в политику, согласуется ею и
выполняется сразу — от имени --role, с её правами и пределами. Вне
политики — обычная заявка: ждёт master. free гаснет по --for, с отзывом
или сроком политики и с --revoke. Песочница, кольца, арбитр и сверка плана
действуют как всегда: free меняет только то, кто сказал «да».

Право: `admin`.

Примеры:

```
ochan agents free db7 --role deployer --for 4h --policy new-servers
ochan agents free db7 --revoke
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--for` | string | — | срок: 30m, 4h, 1d |
| `--policy` | string | — | политика: что выполнять без человека |
| `--revoke` | bool | — | отозвать free агента |
| `--role` | string | — | чьи права на выполнение модель берёт |

## ochan apply

Выполнить сценарий.

```
ochan apply <сценарий|-> [key=value ...] | apply --request <id>
```

Способ выполнения выбирается по полю service самого сценария:
каждый сервис зарегистрирован своим исполнителем. Флага для выбора
внешней системы нет — она такой же исполнитель, как и любой другой.

Исполнитель получает план и применяет ровно его. С --request — план,
на который сказали «да»: перед выполнением ochan строит план заново и
сверяет с согласованным; разошлись — выполнения нет.

Чтобы применить конфиг к файлу, используйте patch.

Право: `apply`.

Примеры:

```
ochan apply scenario.yaml role=standalone
cat scenario.yaml | ochan apply -
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--limit` | stringArray | — | только цели, подходящие под селектор: group=db_new, host=db*; можно указать несколько раз |
| `--notify` | bool | — | отправить уведомление по почте |
| `--request` | string | — | выполнить согласованную заявку |
| `-w`, `--wait` | bool | — | дождаться завершения |

## ochan back role

Вернуться к прошлой роли.

```
ochan back role [роль]
```

Без имени — к роли, которая была текущей до последнего переключения.

Примеры:

```

```

## ochan compensate

Оформить обратное действие выполненной заявки — второй согласованной операцией.

```
ochan compensate <id>
```

rollback откатывает файлы точно: прежнее содержимое ochan записал сам.
Во внешней системе прежнего состояния у ochan нет, и обратное действие —
отдельная операция: исполнитель строит её план, ochan оформляет заявку,
её согласуют и выполняют как любую другую (ochan approve, ochan apply
--request). Обратное действие у заявки одно.

Если его нет — исполнитель не умеет обратного действия или задача уже
отработала так, что вернуть нечего, — это отказ с причиной, а не
видимость отката.

Право: `request`.

Примеры:

```
ochan compensate 7a8f
ochan approve <id обратного действия>
ochan apply --request <id обратного действия>
```

## ochan connect

Подключиться к общему оркестратору.

```
ochan connect <host:port[,host:port]>
```

Открывает сессию на сервере в роли --role (по умолчанию master). Если у роли
есть логин или пароль, их спросят. Внутри сессии: команды ochan выполняются
на сервере, role показывает роль сессии, set role и back role переключают её,
exit завершает сессию.

Пара серверов — адреса через запятую: запись идёт на primary, после
переключения пары — на новый; с --balance чтение идёт по очереди на все
узлы на связи.

Без вопросов — из OCTOCHAN_REMOTE_LOGIN и OCTOCHAN_REMOTE_PASSWORD.

Право: `remote`.

Примеры:

```
ochan connect orchestrator.example:7443 --role Dan
ochan connect a.example:7443,b.example:7443 --balance
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-plaintext` | bool | — | разрешить подключение без ssl к другой машине |
| `--balance` | bool | — | чтение — по очереди на все узлы пары на связи |
| `--role` | string | `master` | роль на сервере |

## ochan diff

Сравнить две конфигурации или два файла.

```
ochan diff <источник1> <источник2>
```

Сравнение у ochan одно. Конфиги и живые источники — по смыслу: 8GB и
8192MB равны, порядок параметров неважен. Всё остальное — журналы,
скрипты, любой текст — построчно, в формате diff -u: разбор конфига
пропустил бы строки журнала, и два разных журнала вышли бы
одинаковыми. Конфигом считается текст, где почти каждая строка —
[секция] или «имя = значение»; --lines и --config выбирают явно.

Источником может быть файл, "-" для stdin или живой сервер,
например postgres://user@host:5432/postgres.

Для живого PostgreSQL читается pg_settings, а не postgresql.conf:
поверх файла действуют ALTER SYSTEM, include и параметры командной
строки, поэтому файл не отражает того, как сервер работает на самом деле.

Право: `read`.

Примеры:

```
ochan diff prod.conf test.conf
ochan diff эталон.conf postgres://dba@db1:5432/postgres
cat prod.conf | ochan diff - test.conf
ochan diff app.log app.log.1              # не конфиг — построчно
ochan diff --lines -U 0 nginx.conf nginx.conf.bak
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--all` | bool | — | для живых источников включать параметры со значением по умолчанию |
| `--config` | bool | — | сравнить по смыслу, как конфиги, даже если текст на них не похож |
| `-f`, `--fast` | bool | — | только вывод в консоль, без отчёта и снапшота |
| `-l`, `--lines` | bool | — | сравнить построчно, как diff -u, даже конфиги |
| `--no-snapshot` | bool | — | не создавать снапшот |
| `-U`, `--unified` | int | `3` | строк контекста вокруг изменения при построчном сравнении |

## ochan fp

Формальный промпт: проверка и протокол.

```
ochan fp
```

Формальный промпт — язык, на котором оператор описывает задачу модели.
Проверки выполняются до модели и детерминированы: текст принадлежит языку,
слова однозначны, знания хватает, жёсткие правила совместны.

Подкоманды: [`alphabet`](#ochan-fp-alphabet), [`check`](#ochan-fp-check), [`journal`](#ochan-fp-journal), [`protocol`](#ochan-fp-protocol), [`words`](#ochan-fp-words).

## ochan fp alphabet

Алфавит языка: из чего складывается текст своей модели.

```
ochan fp alphabet
```

Слова и знаки, из которых складывается текст формального промпта:
ключевые слова и типы отношений, слова словаря (базового, словарей
оператора и скиллов), их смыслы-классы, служебные слова, единицы,
операции скиллов и знаки грамматики. Из алфавита строится словарь своей
модели (ochan llm init): токена вне алфавита у неё нет.

По строке на запись: вид и текст через табуляцию. Имена частных случаев в
языке открыты: в словаре модели они — переменные, а цифры и разметку строки
словарь добавляет сам.

Право: `read`.

## ochan fp check

Проверить формальный промпт.

```
ochan fp check <файл.fp | ->
```

Отказы — по обозначениям манифеста:
  ⊥syn       текст не принадлежит языку
  ⊥ambig     слово может означать несколько классов, и место его не выбирает
  ⊥undef     не хватает отношения, класса, операции или скилла
  ⊥conflict  противоречие: правила, приоритеты, повтор, отчёт против промпта

Скиллы из import ищутся среди пакетов алиасов ochan. С --standalone
скилл даёт ровно то, что объявлено в его provides:.

Настройки — в config.yaml: fp.max_meanings, fp.consistency, fp.quiet.

Право: `read`.

Примеры:

```
ochan fp check задача.fp
cat задача.fp | ochan fp check --name задача.fp -
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--model` | bool | — | текст модели: только язык, строже — без комментариев и символов вне ASCII, как ответ встроенной модели |
| `--name` | string | — | имя промпта, поданного на stdin |
| `--standalone` | bool | — | не сверять скиллы с библиотекой: скилл даёт то, что объявлено в provides: |

## ochan fp journal

Журнал решений: надёжность правил и калибровка.

```
ochan fp journal
```

Кольца берут надёжность правил из журнала решений. Правило — операция
скилла или write и save; его надёжность — 95-процентный интервал
бета-распределения по планам, где оно использовалось: верный план прошёл
арбитра, и оператор его согласовал, не отклонил и не откатил. Без журнала
действует условный счёт: prior.<алиас> в манифесте пакета или
fp.rings.prior.

Нарушение запрета промпта — ошибка модели и промпта, а не скилла: оно
не снижает надёжность правил и считается отдельно, по ролям и промптам.

Калибровка сравнивает поддержку плана с долей верных планов: если при
поддержке 0,7–0,8 верных около 75 %, шкала честная.

Право: `read`.

Подкоманды: [`amend`](#ochan-fp-journal-amend), [`export`](#ochan-fp-journal-export).

## ochan fp journal amend

Поздняя поправка исхода плана: инцидент после согласования, ошибочный отказ.

```
ochan fp journal amend <запись|заявка> (--wrong | --right) --reason <причина>
```

Согласованный план привёл к инциденту — его правила не должны считаться
надёжнее: --wrong. Отказ оказался ошибкой оператора — --right. Запись
журнала не переписывается: поправка ложится сверху, с тем, кто и почему
её сделал, и действует последняя. Право — approve: это решение оператора.

Аргумент — номер записи журнала решений или номер заявки на план.

Право: `approve`.

Примеры:

```
ochan fp journal amend 7a8f --wrong --reason "INC-123: соединения кончились через час"
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--reason` | string | — | почему: инцидент, ошибка оператора |
| `--right` | bool | — | план был верен |
| `--wrong` | bool | — | план был неверен |

## ochan fp journal export

Журнал решений в JSON — параметры колец архитектурной модели.

```
ochan fp journal export
```

Надёжность правил по журналу (счёт с весом давности), условный счёт
автора, порог well_True и исходы выборов архитектурной модели с
признаками правила выбора. Из них модель пересчитывает свои кольца —
rings.json рядом с весами (ochan llm fit). Исходы слепые к оценкам
(раздел 7.3): отказ кольца 2 исходом не считается.

Право: `read`.

## ochan fp protocol

Показать протокол — то, что модель читает первым.

```
ochan fp protocol
```

Протокол зависит от режима модели: llm.mode в config.yaml, а без него —
fp.mode. protocol и embedded — задачи только формальным промптом, текст вне
языка — отказ ⊥syn. natural — модель принимает задачи на естественном
языке; согласование заявок и пределы роли остаются, а жёстких правил, по
которым проверить план, нет.

Право: `read`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--mode` | string | — | показать протокол режима formal или natural, а не того, что в настройках |

## ochan fp words

Словарь языка: слова, их смыслы и откуда они.

```
ochan fp words [слово...]
```

Слово со смыслом в формальном промпте — только из словаря. Словарь
складывается из базового, словарей оператора (fp.lexicons) и словарей

больше потолка fp.max_meanings, в язык не входит.

словами — их статьи во всех словарях.

Право: `read`.

Примеры:

```

ochan fp words --skill pgconf
ochan fp words rock limit
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--skill` | string | — | словарь этого скилла (пакета алиасов) |

## ochan ha

Пара серверов primary/standby: настройка, состояние, переключение.

```
ochan ha
```

Два узла ochan serve: primary пишет, standby держит копию его состояния
(заявки, журнал, роли, аудит, политики, реестр агентов) и отвечает на
чтение. Консенсуса нет: переключение — ochan ha promote на standby,
решение человека. Эпоха — забор: узел, увидевший primary с эпохой больше
своей, перестаёт быть primary сам и откладывает то, что записал после
разрыва, в ha/diverged-….

Настройки — config.yaml: ha.peer (адрес второго узла), ha.self (адрес
этого узла для клиентов), ha.token_file, ha.replicate_every,
ha.require_standby.

Примеры:

```
ochan ha init --node a --role primary
ochan ha init --node b --role standby
ochan ha status
ochan ha status a.example:7443,b.example:7443
ochan ha promote
```

Подкоманды: [`contour`](#ochan-ha-contour), [`init`](#ochan-ha-init), [`promote`](#ochan-ha-promote), [`status`](#ochan-ha-status).

## ochan incident

Инциденты HA-AI: модель чинит до срока, не успела — эскалация инженерам.

```

```

модель чинит сама. Её заметки, заявки (request --incident) и их выполнение —
шаги инцидента. Решила — incident resolve. Не успела или признала, что не
справится (incident escalate), — инцидент эскалируется: инженерной группе

Право: `read`.

```

## ochan incident learn

Обучение по инцидентам: какие повторяются и созрели для модели.

```
ochan incident learn [--export файл]
```

Одиночный инцидент — шум, учить на нём модель — значит запоминать
случайность. Команда группирует инциденты по структуре записи на ℒ —
без частных имён: разные хосты и числа дают одну структуру — и решает,
какой кластер созрел. Порог — как у вакуума в PostgreSQL: кластер
созрел, когда его вес больше incidents.learn.threshold +
incidents.learn.scale_factor × вес всех инцидентов; вес инцидента падает
вдвое за incidents.learn.half_life. Похожесть — incidents.learn.similarity.

--export пишет созревшие кластеры в JSON Lines — материал для обучения
своей модели. Инциденты на естественном языке структуры не дают и в
обучении не участвуют.

Право: `read`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--export` | string | — | записать созревшие кластеры в файл (JSON Lines) |

## ochan llm corpus

Корпус для обучения своей модели: пары задача → ответ логики ochan.

```
ochan llm corpus --out корпус.jsonl [--model каталог] [--count 5000]
```

Пара — задача на ℒ (цель, классы, отношения, приоритеты, жёсткие
правила, обобщения со стрелками, неточные предпосылки, скиллы) и ответ —
та же программа, закрытая там, где задача оставила открытым. Ответ выводит
логика ochan — та же, что у модели при ответе. Задача без предпосылки
(⊥undef) — близнец решаемой, её ответ — без решений (H3). Каждую пару
принимает разбор ochan; непрошедшие отбрасываются.

С --model у пары — токены словарём модели (ids, start): по ним учит
ochan llm train. Строка JSON на пару; split — train или test,
задача и её близнец — в одной части.

Право: `install`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--count` | int | `5000` | сколько пар |
| `--h3` | float64 | `0.5` | доля задач с решениями, у которых есть близнец без предпосылки |
| `--model` | string | — | каталог своей модели; без флага — llm.model |
| `--out` | string | — | файл корпуса (JSON Lines) |
| `--seed` | int64 | `7` | начало случайной последовательности: тот же seed — тот же корпус |
| `--tasks` | string | — | каталог: отложенные задачи файлами .fp — для замера |
| `--tasks-count` | int | `40` | сколько отложенных задач в --tasks |
| `--test` | float64 | `0.1` | доля отложенных пар |

## ochan llm generate

Локальная модель пишет ответ на языке: своя — сама, чужую ведёт декодер ochan.

```
ochan llm generate [--prompt задача.fp] [--out файл]
```

Модель получает протокол и задачу (--prompt — формальный промпт оператора)
и пишет ответ. Сначала ochan сверяет протокол движка (/v1/info): без
подтверждённого протокола генерации нет.

Своя модель ℒ — архитектурная: логика и кольца в её коде, ответ на задачу
она пишет целиком сама, а ochan проверяет его снаружи и пишет в журнал
решений. Настройки декодера llm.decoder.* к ней не применяются.

Чужой движок ведёт декодер ochan: на каждом шаге ochan берёт у движка
распределение следующего токена, токен ниже порога llm.decoder.tau не
берётся (кольцо 0), комментарий и символы вне ASCII — тоже. Собранная
строка — утверждение — проверяется по языку; не в языке — откат к её
началу, и путь, который увёл из языка, запрещён. Ответ — только принятые
утверждения, и целиком он проходит проверку языка; иначе ответа нет.

Задачу не на языке и задачу без предпосылки (⊥undef: требование,
операция, скилл, обобщение, которых нет) модель не получает: ochan сам
возвращает перечень недостающего — догадывать его модели нечем.

Ответ — в stdout (или --out), сводка колец — в stderr: ответ можно сразу
отправить, например ochan mail send --to operators -.

Право: `plan`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--out` | string | — | записать ответ в файл, а не в stdout |
| `--prompt` | string | — | задача — формальный промпт оператора (файл или - для stdin) |

доставляются вместе с ochan (они встроены в бинарник). Учить язык с нуля
на каждой машине незачем: модель отвечает сразу — без Python, видеокарты
и сети. Каталог — llm.model. Своё у каждой установки — параметры колец:
надёжность правил по её журналу и инцидентам (llm fit, llm learn).
Веса — int8: ochan llm train --init дообучает сеть и с них; --full
распаковывает их в float32 — такие читает и torch.

Без --pretrained — новая модель под обучение с нуля. Её словарь — алфавит
ℒ (ochan fp alphabet: слова словаря, их смыслы, ключевые и служебные
слова, единицы, знаки, операции скиллов) с цифрами, разметкой строки и
переменными для имён частных случаев. Конфигурация — архитектура Llama
размера --size. Веса сети обучает ochan llm train по корпусу ochan llm
corpus; каталог с весами — llm.model.

--random-weights — случайные веса: модель отвечает сразу, потому что ответ
пишет её логика, а сеть только выбирает порядок среди допустимых. Это
проверка контура до обучения, а не обученная модель.

Право: `install`.

Примеры:

```
ochan llm init --pretrained --out ~/models/own
ochan llm init --out ~/models/new --size small
ochan llm corpus --model ~/models/new --count 60000 --out corpus.jsonl
ochan llm train --model ~/models/new --corpus corpus.jsonl
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--context` | int | `1024` | контекст: сколько токенов видит модель |
| `--full` | bool | — | с --pretrained: распаковать веса в float32 — их читает и torch |
| `--out` | string | — | каталог новой модели |
| `--pretrained` | bool | — | стартовая модель: обученные веса и словарь, встроенные в ochan |
| `--random-weights` | bool | — | случайные веса: проверить контур до обучения |
| `--size` | string | `small` | размер сети: tiny, small или base |

## ochan llm learn

Своя модель учится на повторяющихся инцидентах; версии параметров и откат.

```
ochan llm learn [--model каталог] [--clusters файл] | --versions | --rollback [N] | --package каталог --version V
```

Созревшие кластеры инцидентов (ochan incident learn) становятся знанием
модели: обобщение — факты структуры, которые есть больше чем у половины
инцидентов кластера; правила плана, которым модель решает задачу
инцидента, получают его исход — решила сама или отдала инженерам. Задачу
той же структуры модель узнаёт сама: надёжность правил на ней — по этим
исходам, а плохо решённая структура — вопрос оператору. Кластеры
пересчитываются целиком; каждая запись — новая версия rings.json.

Инциденты — этой машины; --clusters — выгрузка ochan incident learn
--export другой. --pairs — пары для дообучения сети (llm train --init):
задачи, которые модель решила сама, с примесью базового корпуса --replay.
--package — знания модели пакетом реестра для других машин: обобщения и
надёжность правил на них, без номеров инцидентов.

Право: `install`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--clusters` | string | — | выгрузка ochan incident learn --export; без флага — инциденты этой машины |
| `--description` | string | — | описание пакета знаний одной строкой |
| `--model` | string | — | каталог своей модели; без флага — llm.model |
| `--package` | string | — | пакет знаний из кластеров модели; имя пакета — имя каталога |
| `--pairs` | string | — | записать пары для дообучения сети (ochan llm train --init) |
| `--replay` | string | — | базовый корпус для примеси к парам |
| `--replay-share` | float64 | `0.9` | доля базового корпуса среди пар обучения |
| `--rollback` | string | — | откатить параметры к версии N; без N — к предыдущей |
| `--versions` | bool | — | версии параметров модели |

## ochan llm quantize

Квантовать свою модель: int8 или int4 по группам строки.

```
ochan llm quantize --bits 8|4 --out каталог [--model каталог] [--group N] [--check корпус.jsonl]

Веса матриц — симметрично по группам строки: int8 (группа — вся строка)

масштаб группы — fp16, нормировки остаются fp32. Каталог --out — снова
модель: словарь, конфигурация и параметры колец переходят с весами.

--check — сверка с исходной на отложенных парах корпуса (с токенами,
ochan llm corpus --model): доля позиций ответа с тем же самым вероятным
токеном и потери на ответе у обеих.

Право: `install`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--bits` | int | `8` | 4 или 8 |
| `--check` | string | — | корпус с токенами: сверка с исходной на отложенных парах |
| `--group` | int | `0` | размер группы; 0 — вся строка (у int4 — 32) |
| `--model` | string | — | каталог своей модели; без флага — llm.model |
| `--out` | string | — | каталог квантованной модели |
| `--pairs` | int | `100` | сколько отложенных пар сверять |

## ochan llm run

Цикл агента своей модели: ответ становится заявкой, шагом инцидента или письмом.

```
ochan llm run [--agent имя] [--once] | --prompt задача.fp [--scenario сценарий.yaml]
```

Своя модель ℒ отвечает только формальным промптом; в действия её ответ
переводит ochan — командами от роли llm и агента, с их правами и журналом.

Задачи: письма в ящике агента (--agent или OCTOCHAN_AGENT) и открытые
инциденты на его хосте; с --prompt — одна задача из файла. Задача не на
языке, без предпосылки (⊥undef), отказ модели, вопрос оператору, ответ,
который ochan не принял, — инцидент эскалируется инженерам, на письмо
уходит причина формальным промптом. Ответ принят — заметка к инциденту
или ответ на письмо.

Заявку из решения делает сценарий исполнителя, который приложил оператор
(incident open --scenario, поле scenario вебхука, здесь --scenario): места
${Класс.атрибут} получают решённые значения ответа. Под free агента заявка
в пределах политики выполняется без человека — тогда инцидент решён; иначе
ждёт согласования. Без сценария решение уходит людям: заявку оформит
человек.

Без --once цикл ходит каждые --every, пока его не остановят; на standby он
ждёт. Своя модель (llm.model) загружается в процесс один раз на весь цикл.

Право: `read`.

Примеры:

```
ochan llm run --agent db7
ochan llm run --agent db7 --once
ochan llm run --prompt задача.fp --scenario raise.yaml
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--agent` | string | — | агент: его ящик и инциденты на его хосте; без флага — OCTOCHAN_AGENT |
| `--every` | duration | `30s` | как часто смотреть письма и инциденты |
| `--once` | bool | — | один проход и выход |
| `--prompt` | string | — | одна задача из файла (- — stdin) |
| `--scenario` | string | — | сценарий исполнителя с местами ${Класс.атрибут} для задачи --prompt |

## ochan llm serve

Выставить свою модель по протоколу движка v1 — для ochan на других машинах.

```
ochan llm serve [--allow-remote]
```

Загружает свою модель llm.model в процесс и отвечает по протоколу движка v1
на адресе llm.endpoint: /v1/info, /v1/generate, /v1/next, /v1/score. Ochan
на другой машине говорит с ней по этому адресу — llm.endpoint без
llm.model. На этой машине сервер не нужен: команды ochan загружают модель
сами.

Аутентификации и TLS у сервера нет: он слушает только локальный адрес;
не локальный — с --allow-remote и только за прокси с TLS и
аутентификацией. Остановить — Ctrl+C.

Право: `read`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-remote` | bool | — | слушать не локальный адрес — только за прокси с TLS и аутентификацией |

## ochan llm train

Обучить веса сети своей модели: градиентный спуск на процессоре.

```
ochan llm train --corpus корпус.jsonl [--model каталог] [--init каталог] [--epochs 8] [--lr 1e-3] [--resume]
```

Градиентный спуск по токенам корпуса (ochan llm corpus --model): потери —
по всей паре <bos> задача <answer> ответ <eos>, батч — по числу токенов
(--batch-tokens, пары близкой длины вместе), AdamW, обрезка нормы
градиента, разгон и косинусный спад скорости. Считает процессор, всеми
ядрами: Python и видеокарта не нужны. Веса пишутся в каталог модели
(model.safetensors) — это и есть llm.model.

--init — дообучение: веса и словарь готовой модели, полной или
квантованной (стартовая — ochan llm init --pretrained), например на парах
кластеров инцидентов с примесью базового корпуса (ochan llm learn
--pairs). Новые веса пишутся в --model — новый каталог; прежний остаётся
для отката, параметры колец и их версии переходят с весами.

Каждые --save-every шагов и при прерывании (Ctrl+C) каталог — рабочая
модель и состояние обучения: --resume продолжает с него с теми же
параметрами и корпусом, и результат тот же, что без прерывания.

Дообучение на сотнях пар — минуты. Обучение с нуля на десятках тысяч пар
на процессоре — дни: тот же счёт на видеокарте делает
llama/train_own.py, каталог модели и корпус у них общие.

Право: `install`.

Примеры:

```
ochan llm train --init ~/models/own --model ~/models/own-2 --corpus pairs.jsonl --epochs 1 --lr 1e-4
ochan llm train --model ~/models/new --corpus corpus.jsonl
ochan llm train --model ~/models/new --corpus corpus.jsonl --resume
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--batch-tokens` | int | `32768` | токенов в батче с выравниванием по самой длинной паре |
| `--corpus` | string | — | корпус с токенами: ochan llm corpus --model или llm learn --pairs |
| `--epochs` | float64 | `8` | проходов по корпусу |
| `--eval-pairs` | int | `200` | сколько отложенных пар мерить; 0 — все |
| `--init` | string | — | дообучение: начать с весов этой модели; --model — новый каталог |
| `--lr` | float64 | `0.001` | скорость обучения; для дообучения — меньше (1e-4) |
| `--model` | string | — | каталог модели, куда пишутся веса; без флага — llm.model |
| `--resume` | bool | — | продолжить с сохранения в --model |
| `--save-every` | int | `500` | шагов между сохранениями |
| `--seed` | int64 | `7` | начало случайной последовательности: тот же seed — те же веса |

## ochan logs rank

Ранжировать строки журнала по уровням важности.

```
ochan logs rank <журнал | ->
```

Уровень строки задают правила logs.rules — регулярные выражения по порядку:
первое совпадение решает. Уровни — logs.levels, от наименее важного, как
log_min_messages у PostgreSQL: --min warning оставляет warning и всё важнее.
Строка без совпадений получает logs.default_level.

С --summary — сводка: число строк по уровням и самые частые сообщения.
Группа (?P<msg>…) в правиле выделяет суть сообщения; без неё одинаковыми
считаются строки, которые различаются только числами.

Право: `read`.

Примеры:

```
ochan logs rank /var/log/postgresql/postgresql.log --min error
journalctl -u nginx | ochan logs rank - --summary --top 5
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--min` | string | — | показывать строки этого уровня и важнее (по умолчанию logs.min_level) |
| `--summary` | bool | — | сводка: строки по уровням и частые сообщения |
| `--top` | int | `10` | сколько частых сообщений показать в сводке (0 — все) |

## ochan mail send

Написать агенту или людям.

ochan mail send --to <агент|группа|адрес> [--subject тема] <текст | файл | ->

## ochan net http

Жив ли HTTP: код, время, размер и сертификат.

```
ochan net http <адрес>
```

Код ответа, время, размер тела и, у https, срок сертификата. Код 400 и
выше — ошибка; --expect — ровно этот код. --body печатает тело (не больше
1 МиБ) — например, JSON проверки здоровья для сценария. Сертификат
проверяется всегда; свой центр сертификации — --ca.

Право: `net`.

Примеры:

```
ochan net http https://grafana.example.com/api/health
ochan net http http://db7:8008/primary --expect 200
ochan net http https://vault.internal/v1/sys/health --ca corp-ca.pem --body
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--body` | bool | — | напечатать тело ответа (не больше 1 МиБ) |
| `--ca` | string | — | свой центр сертификации (PEM) вдобавок к системным |
| `--expect` | int | `0` | ожидаемый код ответа; 0 — любой ниже 400 |
| `-H`, `--header` | stringArray | — | заголовок запроса «Имя: значение» |
| `-X`, `--method` | string | `GET` | метод запроса |

## ochan net tls

Сертификат TLS: кто выдал, кому и сколько ему осталось.

```
ochan net tls <хост[:порт]>
```

Порт по умолчанию — 443. Сертификат проверяется по системным корням и
--ca; не прошёл проверку — сведения о нём всё равно печатаются, а команда
— ошибка. Истёк или осталось меньше --warn (по умолчанию 30d) — ошибка:
так ochan net tls годится для проверки по расписанию.

Право: `net`.

Примеры:

```
ochan net tls grafana.example.com
ochan net tls db7:5433 --name db7.internal --ca corp-ca.pem --warn 14d
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--ca` | string | — | свой центр сертификации (PEM) вдобавок к системным |
| `--name` | string | — | имя сервера для SNI и проверки; по умолчанию — хост |

## ochan paths

Где лежит то, чем пользуется ochan, и чем меняется каждый путь.

```
ochan paths
```

Рабочий каталог (по умолчанию ~/.octochan) переносится целиком: в нём
роли, журнал аудита, заявки, история, решения, политики, алиасы,
инциденты, почта и токены. Это одно целое: его зеркалит резервный узел
пары и закрывает от сценариев и ролей защита рабочего каталога. Где он —
говорит указатель ochan.home рядом с программой (его пишет ochan setup;
путь в нём может быть от папки программы) или переменная OCTOCHAN_HOME —
она сильнее указателя.

Каталоги узла выносятся отдельно — переменной окружения или настройкой
paths.* в config.yaml (окружение сильнее): модули (OCTOCHAN_MODULES,
paths.modules), журналы (OCTOCHAN_LOGS, paths.logs), отчёты
(OCTOCHAN_REPORTS, paths.reports), кеш реестров (OCTOCHAN_REGISTRY_CACHE,
paths.registry_cache). Модули выносят туда, где политика хоста разрешает
запуск: в домашнем каталоге с noexec плагин не запускается (operation not
permitted), и перенос решает это, не обходя политику.

Путь — полный. Вынесенный каталог и каждый каталог над ним должны
принадлежать вам или root и быть закрыты для записи группе и остальным:
иначе другой пользователь машины подложил бы в модули свой плагин. Защита
рабочего каталога действует и на вынесенные.

Право: `read`.

## ochan plan

Показать, что произойдёт, ничего не делая.

```
ochan plan <сценарий> | plan <база> <изменения> | plan --script <файл.ochan | ->
```

С одним аргументом планирует сценарий: какие операции были бы
выполнены и над чем. С двумя — показывает, какие параметры изменит
patch.

Способ выполнения сценария выбирается по его полю service, флага
для этого нет. Изменяющие запросы в режиме плана запрещены на уровне
клиента, поэтому команда не может ничего создать даже по ошибке.

Файл .ochan (или --script) — сценарий на языке алиасов. Он проверяется
целиком и выполняется в режиме плана: write и save ничего не пишут,
а печатается, какие файлы и параметры они изменили бы. Чтение файлов
и живых источников при этом настоящее — без него планировать нечего.

Право: `plan`.

Примеры:

```
ochan plan restart.yaml
ochan plan prod.conf changes.conf
ochan plan эталон.conf postgres://dba@db1:5432/postgres
ochan plan сценарий.ochan
ochan plan --script --sandbox --root ./configs - < сценарий.ochan
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-env` | stringArray | — | разрешить в песочнице переменную окружения; можно указать несколько раз |
| `--allow-exec` | stringSlice | — | разрешить exec() сценария запускать эти программы (kubectl,terraform) — только в песочнице ядра; оболочки и интерпретаторы не разрешаются |
| `--allow-live` | stringArray | — | разрешить в песочнице живые источники этой схемы, например postgres |
| `--allow-net` | stringArray | — | разрешить в песочнице fetch и curl к этому хосту (host или host:port); можно указать несколько раз |
| `--bundle` | bool | — | stdin — JSON {"script": …, "prompt": …, "report": …}; так их передаёт ochan-mcp |
| `--limit` | stringArray | — | только цели (хосты инвентаря), подходящие под селектор: group=db_new, host=db*; можно указать несколько раз |
| `--name` | string | — | имя сценария, поданного на stdin |
| `--prompt` | string | — | формальный промпт: его жёсткие правила проверяются по плану сценария |
| `--report` | string | — | отчёт модели (раздел report:), проверяется вместе с промптом |
| `--root` | stringArray | — | разрешённый каталог песочницы; можно указать несколько раз (по умолчанию — текущий) |
| `--sandbox` | bool | — | песочница: файлы только внутри --root, окружение, живые источники и сеть — только разрешённые |
| `--script` | bool | — | сценарий на языке алиасов (для файла .ochan подразумевается) |
| `--trust` | stringSlice | — | правила (пакет.алиас, write, save), которым оператор доверяет без журнала: их утверждения проходят кольцо 2 |

## ochan request

Создать заявку на изменение из плана.

```
ochan request <сценарий> | request <база> <изменения> | request --script <файл.ochan | ->
```

Заявка фиксирует план и ждёт решения. Выполнить её можно только
после согласования: ochan apply --request <id>.

Заявка отвечает не на вопрос «кому в принципе можно», а на вопрос
«на это конкретное изменение сказали да» — именно это нужно аудиту.

Файл .ochan (или --script) — сценарий на языке алиасов: он проверяется,
план строится выполнением в режиме плана, а в заявку попадают его текст,
каталог и песочница. При выполнении план строится заново и должен совпасть.

--after <id> — порядок: заявка выполнится только после указанных. Если
она упадёт, те, после которых она шла, остаются выполненными — сбой их
не откатывает; упавшую не повторяют, а оформляют заново, и заявки после
неё — тоже. Повтор и расписание — дело модуля рабочего процесса.

Право: `request`.

Примеры:

```

ochan request prod.conf changes.conf
ochan request deploy.yaml --after 1c4a
ochan request сценарий.ochan
ochan request --script --sandbox --root ./configs - < сценарий.ochan

```

--nlogin задаёт новый логин, --npsw спрашивает новый пароль (ввод скрыт;
не на терминале — одна строка из stdin). --drop-login и --drop-psw снимают
логин и пароль: в роль снова можно входить без них.

После смены логина или пароля роль уходит из истории переключений:
back role в неё больше не пустит без входа.

Право: `admin`.

Примеры:

```
ochan role update master --npsw
ochan role update slave --nlogin dan --npsw
ochan role update slave --rename worker
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--drop-login` | bool | — | снять логин |
| `--drop-psw` | bool | — | снять пароль |
| `--nlogin` | string | — | задать логин роли |
| `--npsw` | bool | — | задать пароль роли (спросит, ввод скрыт) |
| `--rename` | string | — | новое имя роли |

## ochan rollback

Отменить изменение файлов из истории.

```
ochan rollback <id>
```

Возвращает файлы к состоянию до операции.

Откатить можно правку файла и сценарий, выполненный по заявке: каждый
записанный им файл возвращается к прежнему содержимому, а созданный —
удаляется. Если файл поменяли после операции, откат отказывает и
называет его: без --force чужая правка не стирается.

Задачи, созданные во внешней системе, необратимы: перезапуск уже
произошёл, и отменять в октохане нечего — для таких записей команда
откажет и скажет об этом прямо.

Право: `apply`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--force` | bool | — | откатить повторно или поверх файлов, изменившихся после операции |
| `--not-plan` | bool | — | откат не из-за плана: правилам плана по формальному промпту не засчитывать |

## ochan run

Выполнить сценарий или алиас.

```
ochan run <файл.ochan | алиас | -> [аргументы...]
```

Если первый аргумент — существующий файл или «-» (stdin), выполняется он.
Иначе имя трактуется как алиас, а остальные аргументы — как его параметры.
Числа распознаются автоматически, всё остальное передаётся строкой.

Что сценарий изменил бы, не выполняя его: ochan plan файл.ochan.

Право: `apply`.

Примеры:

```

ochan run --sandbox --root ./configs сценарий.ochan
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-env` | stringArray | — | разрешить в песочнице переменную окружения; можно указать несколько раз |
| `--allow-exec` | stringSlice | — | разрешить exec() сценария запускать эти программы (kubectl,terraform) — только в песочнице ядра; оболочки и интерпретаторы не разрешаются |
| `--allow-live` | stringArray | — | разрешить в песочнице живые источники этой схемы, например postgres |
| `--allow-net` | stringArray | — | разрешить в песочнице fetch и curl к этому хосту (host или host:port); можно указать несколько раз |
| `--limit` | stringArray | — | только цели (хосты инвентаря), подходящие под селектор: group=db_new, host=db*; можно указать несколько раз |
| `--name` | string | — | имя сценария, поданного на stdin |
| `--root` | stringArray | — | разрешённый каталог песочницы; можно указать несколько раз (по умолчанию — текущий) |
| `--sandbox` | bool | — | песочница: файлы только внутри --root, окружение, живые источники и сеть — только разрешённые |

## ochan sandbox

Показать, какую изоляцию даёт песочница на этой системе.

```
ochan sandbox
```

Сценарий с --sandbox выполняется отдельным процессом. На Linux его
ограничивает ядро: Landlock пускает только в разрешённые каталоги,
seccomp запрещает запуск программ, отладку чужих процессов, монтирование
и сокеты, своё сетевое пространство оставляет без сети. На других ОС
файлы и сеть держит только песочница языка.

С sandbox.strict: true в config.yaml сценарий не выполняется, если
изоляция неполная.

С --allow-exec проба ставит песочницу с запуском этих программ: так
видно, даст ли ядро такую изоляцию, до того как на неё рассчитывать.

Право: `read`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-exec` | stringSlice | — | проверить песочницу с запуском этих программ |

## ochan serve

Запустить общий оркестратор: подключение по сети в одной из ролей.

```
ochan serve
```

Сервер держит роли у себя: логин и пароль проверяет он, и подключившийся
не может их обойти. Команды клиента выполняются на сервере, в роли сессии,
над файлами сервера в каталоге server.dir.

Настройки — в config.yaml: ssl (шифрование вкл/выкл), tls.min_version,
tls.cert, tls.key, server.listen, server.dir, server.session_timeout,
server.command_timeout. Сертификат создаёт ochan tls init.

Без ssl сервер слушает только эту машину: иначе пароли ролей шли бы по
сети открытым текстом. --allow-plaintext снимает запрет.

Право: `server`.

Примеры:

```
ochan tls init --host orchestrator.example
ochan serve --listen 0.0.0.0:7443
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-plaintext` | bool | — | разрешить работу без ssl на сетевом адресе |
| `--dir` | string | — | каталог, над файлами которого работают команды (по умолчанию server.dir или текущий) |
| `--listen` | string | — | адрес сервера (по умолчанию server.listen) |

## ochan setup

Установить ochan: всё в одну папку или каждый путь отдельно.

```
ochan setup [--here[=папка]] | [--bin папка] [--home папка] [--modules папка] [--logs папка] [--reports папка] [--registry-cache папка]
```

Без флагов спрашивает, как ставить:

  1 — быстрая: всё в одной папке — программы ochan и ochan-mcp, рабочий
      каталог (.octochan) и модули. Для машин, где работать и запускать
      программы разрешено только в одной папке.
  2 — ручная: каждый путь задаёте сами; Enter — путь по умолчанию.

Ответы читаются из stdin построчно — их можно подать и конвейером. То же
флагами, без вопросов: --here — быстрая установка в текущую папку
(--here=папка — в другую); --bin, --home, --modules, --logs, --reports,
--registry-cache — ручная, незаданное остаётся по умолчанию.

Рабочий каталог не в ~/.octochan записывается указателем ochan.home рядом
с программой: ochan находит его сам, переменные окружения не нужны (при
быстрой установке путь в указателе относительный — папку можно переносить
целиком). Вынесенные каталоги узла записываются в config.yaml (paths.*).
Что получилось — ochan paths.

--desktop — ещё и значок: запись в меню приложений и ярлык на рабочем
столе, ochan находится поиском системы и открывается в своей оболочке
(Linux и Windows). --desktop=only — только значок для уже установленной
программы, --desktop=remove — убрать его.

Команда не требует ни рабочего каталога, ни ролей: её запускают там, где
ochan ещё не установлен.

Право: `install`.

Примеры:

```
ochan setup
ochan setup --here --desktop
ochan setup --bin ~/tools --home /srv/ochan --modules /opt/ochan/modules
printf '1\n' | ochan setup
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--bin` | string | — | каталог программ ochan и ochan-mcp |
| `--desktop` | string | — | значок в меню приложений и на рабочем столе; only — только значок, remove — убрать |
| `--here` | string | — | быстрая установка: всё в одной папке (без значения — в текущей) |
| `--home` | string | — | рабочий каталог: роли, заявки, журнал аудита, конфиг |
| `--logs` | string | — | каталог журналов; по умолчанию — в рабочем каталоге |
| `--module` | stringArray | — | после установки поставить модуль из файла (можно несколько раз) |
| `--modules` | string | — | каталог модулей — там, где разрешён запуск программ; по умолчанию — в рабочем каталоге |
| `--registry-cache` | string | — | кеш реестров пакетов; по умолчанию — в рабочем каталоге |
| `--reports` | string | — | каталог отчётов; по умолчанию — в рабочем каталоге |
| `-y`, `--yes` | bool | — | не спрашивать подтверждения |

## ochan shell

Запустить оболочку: интерактивную на терминале, построчную без него.

```
ochan shell
```

На терминале — интерактивная оболочка с автодополнением и историей.

Без терминала — в конвейере, в задании CI, с вводом из файла — оболочка
читает stdin построчно и выполняет те же строки: команды ochan и
инструкции языка алиасов, с переменными между строками и блоками
{ … } в несколько строк. Пустые строки и строки с # пропускаются, exit
кончает ввод. Ошибки идут в stderr, вывод команд — в stdout; код
возврата — 1, если хоть одна строка кончилась ошибкой. С
--stop-on-error оболочка останавливается на первой. В историю такие
строки не пишутся, а stdin командам недоступен: из него читаются сами
команды.

Право: `свободная — доступна любой роли`.

Примеры:

```
ochan shell
echo 'logs rank --min warning' | ochan shell
ochan shell --stop-on-error < проверки.txt
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--logo` | bool | — | показывать логотип при входе — и в следующих сессиях, даже если shell.logo: false |
| `--no-logo` | bool | — | не показывать логотип при входе — и в следующих сессиях |
| `--stop-on-error` | bool | — | без терминала: остановиться на первой строке с ошибкой |

## ochan text

Поиск по шаблону (grep), поля строк (awk, cut) и последние строки (tail)

## ochan text fields

Поля строк: что делают awk '{print $1}' и cut.

```
ochan text fields [файл...] [-f 1,3-4] [-d разделитель]
```

Строка делится на поля пробелами и табуляциями, как у awk, или
разделителем -d, как у cut. -f — номера полей с 1: 1,3-4, 2- (со второго
до конца); без -f — все. --match — только строки, подходящие под
шаблон, как /шаблон/ у awk. Поля выводятся через -s: по умолчанию тот же
разделитель, а без -d — пробел.

Право: `read`.

Примеры:

```
ochan text fields -f 1,4 access.log
ochan text fields -d : -f 1,7 /etc/passwd
ochan text fields --match ERROR -f 2- app.log
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `-d`, `--delimiter` | string | — | разделитель полей; без него — пробелы и табуляции |
| `-f`, `--fields` | string | — | номера полей с 1: 1,3-4 или 2- |
| `--match` | string | — | только строки, подходящие под шаблон |
| `-s`, `--output` | string | ` ` | разделитель полей в выводе |

## ochan text grep

Строки, подходящие под шаблон.

```
ochan text grep <шаблон> [файл...]
```

Шаблон — регулярное выражение RE2: без возвратов, поэтому время поиска
не взрывается на любом шаблоне. Файлов несколько — перед строкой имя
файла; шаблон файлов (*.log) раскрывается. Совпадений нет — пустой вывод,
а не ошибка: в сценарии это пустая строка.

Право: `read`.

Примеры:

```
ochan text grep -i 'error|fatal' /var/log/postgresql/*.log
ochan text grep -c timeout app.log
ochan logs rank --min warning | ochan text grep -n replica
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `-c`, `--count` | bool | — | только число совпадений |
| `-F`, `--fixed` | bool | — | шаблон — строка, а не регулярное выражение |
| `-i`, `--ignore-case` | bool | — | без учёта регистра |
| `-v`, `--invert` | bool | — | строки, которые не подходят |
| `-n`, `--line-number` | bool | — | номер строки перед ней |
| `-m`, `--max` | int | `0` | не больше стольких строк; 0 — все |

## ochan trigger

## ochan watch

Следить за инвентарём: новый хост — план, заявка, а по политике — выполнение.

```
ochan watch --source <источник> (--policy <имя|файл> | --scenario <сценарий>)
```

Проход: читает источник инвентаря, находит новые хосты (которых ещё не
видели), для каждого строит план сценария, суженного до этого хоста, и
оформляет заявку. Обработанный хост отмечается увиденным.

Проверять и планировать по расписанию ochan может сам; выполнять — только
по зарегистрированной политике (ochan policy add). Заявка, которая в неё
укладывается — метки хоста, параметры сценария, сервис, план без
прерывания обслуживания, предел роли на apply, — согласуется политикой и
выполняется. Всё остальное остаётся заявкой и ждёт человека; причина
печатается. Отозванная или истёкшая политика выключает выполнение со
следующего прохода.

Без --every — один проход: для cron. С --every — проходы до остановки.

Право: `request`.

Примеры:

```
ochan watch --source cmdb --policy new-servers
ochan watch --source cmdb --policy new-servers.yaml --every 10m
ochan watch --source cmdb --scenario tune.yaml
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--every` | duration | `0s` | повторять проход с этим промежутком (от 1m); без него — один проход |
| `--policy` | string | — | политика: имя или её файл — выполнять то, что в неё укладывается |
| `--scenario` | string | — | сценарий без политики: только заявки |
| `--source` | string | — | источник инвентаря (имя из inventory.sources или local) |
