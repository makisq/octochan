## ochan !install

Установить модуль или пакет алиасов.

```
ochan !install <модуль.hcplugin | пакет | файл.ochan>
```

Одна команда ставит всё, чем расширяется ochan, в ~/.octochan/modules:

  модуль.hcplugin  модуль gRPC: команды, языки и исполнители сценариев —
                   что он объявит. Фиксируется его контрольная сумма, и
                   подменённый после установки файл не загрузится
  пакет            каталог с алиасами (*.ochan) и package.yaml — скилл для
                   сценариев и формального промпта. Модули .hcplugin из
                   каталога ставятся вместе с ним: скилл и его исполнитель
  файл.ochan       однофайловый пакет алиасов

Пакет проверяется до установки: с ошибкой он не ставится и библиотеку не
ломает. Исполнитель модуля выбирается по полю service сценария, как
встроенный; его токен — ochan auth --executor <имя>.

С --remove удаляет модуль (имя файла) или пакет (имя пакета).

Право: `install`.

Примеры:

```
ochan '!install' ssh-runner.hcplugin
ochan '!install' ./pgconf
ochan '!install' --remove pgconf
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--remove` | bool | — | удалить модуль или пакет алиасов |

## ochan agent run

Сообщать серверу о себе раз в --every.

```
ochan agent run --server <host:port[,host:port]> --name <имя> [--group g] [--var k=v]
```

Входит на сервер в роли --role (по умолчанию agent; ей нужно право agent),
раз в --every выполняет там ochan agents beat с именем, группами и
переменными этой машины. Логин и пароль — из OCTOCHAN_REMOTE_LOGIN и
OCTOCHAN_REMOTE_PASSWORD: спросить некого. Пара серверов — адреса через
запятую: агент переживает её переключение. --once — один раз, для cron.

Право: `remote`.

Примеры:

```
ochan agent run --server a.example:7443,b.example:7443 --name db7 --group db,db_new \
  --var svm_ci=CI007 --every 1m
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-plaintext` | bool | — | разрешить подключение без ssl к другой машине |
| `--every` | duration | `1m0s` | как часто сообщать о себе |
| `--group` | stringSlice | — | группы агента |
| `--name` | string | — | имя агента — имя хоста в инвентаре |
| `--once` | bool | — | сообщить один раз и выйти |
| `--role` | string | `agent` | роль агента на сервере |
| `--server` | string | — | адрес сервера; пара — через запятую |
| `--var` | stringArray | — | переменная агента ключ=значение |

## ochan agents

Реестр агентов: машины, которые сами сообщают серверу о себе.

```
ochan agents
```

Агент — машина с ochan agent run: раз в --every он сообщает серверу имя,
группы и переменные, а сервер запоминает и его адрес. Реестр — источник
инвентаря agents:// (agents://online — только на связи): цели сценариев
берутся из него, а ochan watch --source agents видит новый агент как
новый хост и действует по политике.

Право: `read`.

Подкоманды: [`beat`](#ochan-agents-beat), [`forget`](#ochan-agents-forget).

## ochan agents beat

Имя принадлежит роли, в которой агент сообщил о себе первый раз: другая
роль его не займёт. Право — agent.

Право: `agent`.

## ochan apply

Выполнить сценарий.

```
ochan apply <сценарий|-> [key=value ...] | apply --request <id>
```

Способ выполнения выбирается по полю service самого сценария:
каждый сервис зарегистрирован своим исполнителем. Флага для выбора
внешней системы нет — она такой же исполнитель, как и любой другой.

Исполнитель получает план и применяет ровно его. С --request — план,
на который сказали «да»: перед выполнением ochan строит план заново и
сверяет с согласованным; разошлись — выполнения нет.

Чтобы применить конфиг к файлу, используйте patch.

Право: `apply`.

Примеры:

```
ochan apply scenario.yaml role=standalone
cat scenario.yaml | ochan apply -
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--limit` | stringArray | — | только цели, подходящие под селектор: group=db_new, host=db*; можно указать несколько раз |
| `--notify` | bool | — | отправить уведомление по почте |
| `--request` | string | — | выполнить согласованную заявку |
| `-w`, `--wait` | bool | — | дождаться завершения |

## ochan audit

Журнал аудита: кто, что и когда пытался выполнить.

```
ochan audit
```

Каждая команда, вход на сервер и смена роли пишутся в журнал
~/.octochan/audit.log — и разрешённые, и отвергнутые, с причиной отказа.
Записи связаны цепочкой хешей: правку, вставку или удаление записи
находит ochan audit verify.

Право: `audit`.

Примеры:

```
ochan audit
ochan audit --role dan --denied
ochan audit verify --head 3f9a1c0b2e7d
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--denied` | bool | — | только отказы |
| `-n`, `--n` | int | `20` | сколько записей показать (0 — все) |
| `--role` | string | — | только записи этой роли |

Подкоманды: [`verify`](#ochan-audit-verify).

## ochan audit verify

Проверить цепочку хешей журнала аудита.

```
ochan audit verify
```

Проверяет каждую запись: её хеш, ссылку на предыдущую и номер. Правка,
вставка или удаление записи рвут цепочку — проверка назовёт строку.

Обрезанный хвост цепочку не рвёт. Поэтому хеш последней записи стоит
время от времени сохранять вне этой машины: --head с ним проверит, что
эта запись в журнале есть.

Право: `audit`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--head` | string | — | хеш записи, сохранённый вне машины: она должна быть в журнале |

## ochan auth

Установить токен исполнителя сценариев.

```
ochan auth [token]
```

Токен исполнителя — RLM, SSH, API своей системы — хранится в
~/.octochan/tokens/<имя> с правами 0600; вместо файла — переменная
окружения OCTOCHAN_TOKEN_<ИМЯ>. Ядро передаёт токен исполнителю при
каждом вызове; в config.yaml токены не попадают.

Без --executor — единственный подключённый исполнитель.

Право: `auth`.

Примеры:

```
ochan auth --executor rlm
ochan auth
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--executor` | string | — | исполнитель, чей это токен: rlm, ssh…; без флага — единственный подключённый |

## ochan back role

Вернуться к прошлой роли.

```
ochan back role [роль]
```

Без имени — к роли, которая была текущей до последнего переключения.
Два back role подряд возвращают туда же, откуда начали: set role slave,
back role — master, back role — снова slave. С именем — к этой роли, если
она есть в истории. Логин и пароль не спрашиваются: в роль уже входили.

Право: `свободная — доступна любой роли`.

Примеры:

```
ochan back role
ochan back role master
ochan back role Dan
```

## ochan check

Проверить сценарий языка алиасов, ничего не выполняя.

```
ochan check [файл.ochan | -]...
```

Обходит все ветки и все алиасы и находит то, что видно без запуска:
неизвестные имена и функции, неверное число аргументов, break и return
не на своём месте, явно неверные типы. Файлы не читаются, источники
не опрашиваются: проверяется только текст.

Без аргументов проверяет библиотеку — все установленные алиасы.

Право: `read`.

Примеры:

```
ochan check сценарий.ochan
cat сценарий.ochan | ochan check -
ochan check
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--name` | string | — | имя сценария, поданного на stdin |

## ochan compensate

Оформить обратное действие выполненной заявки — второй согласованной операцией.

```
ochan compensate <id>
```

rollback откатывает файлы точно: прежнее содержимое ochan записал сам.
Во внешней системе прежнего состояния у ochan нет, и обратное действие —
отдельная операция: исполнитель строит её план, ochan оформляет заявку,
её согласуют и выполняют как любую другую (ochan approve, ochan apply
--request). Обратное действие у заявки одно.

Если его нет — исполнитель не умеет обратного действия или задача уже
отработала так, что вернуть нечего, — это отказ с причиной, а не
видимость отката.

Право: `request`.

Примеры:

```
ochan compensate 7a8f
ochan approve <id обратного действия>
ochan apply --request <id обратного действия>
```

## ochan connect

Подключиться к общему оркестратору.

```
ochan connect <host:port[,host:port]>
```

Открывает сессию на сервере в роли --role (по умолчанию master). Если у роли
есть логин или пароль, их спросят. Внутри сессии: команды ochan выполняются
на сервере, role показывает роль сессии, set role и back role переключают её,
exit завершает сессию.

Пара серверов — адреса через запятую: запись идёт на primary, после
переключения пары — на новый; с --balance чтение идёт по очереди на все
узлы на связи.

Без вопросов — из OCTOCHAN_REMOTE_LOGIN и OCTOCHAN_REMOTE_PASSWORD.

Право: `remote`.

Примеры:

```
ochan connect orchestrator.example:7443 --role Dan
ochan connect a.example:7443,b.example:7443 --balance
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-plaintext` | bool | — | разрешить подключение без ssl к другой машине |
| `--balance` | bool | — | чтение — по очереди на все узлы пары на связи |
| `--role` | string | `master` | роль на сервере |

## ochan diff

Сравнить две конфигурации.

```
ochan diff <источник1> <источник2>
```

Источником может быть файл, "-" для stdin или живой сервер,
например postgres://user@host:5432/postgres.

поверх файла действуют ALTER SYSTEM, include и параметры командной
строки, поэтому файл не отражает того, как сервер работает на самом деле.

Право: `read`.

Примеры:

```
ochan diff prod.conf test.conf
ochan diff эталон.conf postgres://dba@db1:5432/postgres
cat prod.conf | ochan diff - test.conf
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--all` | bool | — | для живых источников включать параметры со значением по умолчанию |
| `-f`, `--fast` | bool | — | только вывод в консоль, без отчёта и снапшота |
| `--no-snapshot` | bool | — | не создавать снапшот |

## ochan fp check

Проверить формальный промпт.

```
ochan fp check <файл.fp | ->
```

Отказы — по обозначениям манифеста:
  ⊥syn       текст не принадлежит языку
  ⊥ambig     слово может означать несколько классов, и место его не выбирает
  ⊥undef     не хватает отношения, класса, операции или скилла
  ⊥conflict  противоречие: правила, приоритеты, повтор, отчёт против промпта

Скиллы из import ищутся среди пакетов алиасов ochan. С --standalone
скилл даёт ровно то, что объявлено в его provides:.

Настройки — в config.yaml: fp.max_meanings, fp.consistency, fp.quiet.

Право: `read`.

Примеры:

```

```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--name` | string | — | имя промпта, поданного на stdin |
| `--standalone` | bool | — | не сверять скиллы с библиотекой: скилл даёт то, что объявлено в provides: |

## ochan fp journal

Журнал решений: надёжность правил и калибровка.

```
ochan fp journal
```

Кольца берут надёжность правил из журнала решений. Правило — операция
скилла или write и save; его надёжность — 95-процентный интервал
бета-распределения по планам, где оно использовалось: верный план прошёл
арбитра, и оператор его согласовал, не отклонил и не откатил. Без журнала
действует условный счёт: prior.<алиас> в манифесте пакета или
fp.rings.prior.

Нарушение запрета промпта — ошибка модели и промпта, а не скилла: оно
не снижает надёжность правил и считается отдельно, по ролям и промптам.

Калибровка сравнивает поддержку плана с долей верных планов: если при
поддержке 0,7–0,8 верных около 75 %, шкала честная.

Право: `read`.

## ochan fp protocol

Показать протокол — то, что модель читает первым.

```

```

Протокол зависит от fp.mode в config.yaml. formal — задачи только
формальным промптом, текст вне языка — отказ ⊥syn. natural — модель
принимает задачи на естественном языке; согласование заявок и пределы
роли остаются, а жёстких правил, по которым проверить план, нет.

Право: `read`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--mode` | string | — | показать протокол режима formal или natural, а не того, что в fp.mode |

## ochan fp words

| `--skill` | string | — | словарь этого скилла (пакета алиасов) |

## ochan ha

Пара серверов primary/standby: настройка, состояние, переключение.

```
ochan ha
```

Два узла ochan serve: primary пишет, standby держит копию его состояния
(заявки, журнал, роли, аудит, политики, реестр агентов) и отвечает на
чтение. Консенсуса нет: переключение — ochan ha promote на standby,
решение человека. Эпоха — забор: узел, увидевший primary с эпохой больше
своей, перестаёт быть primary сам и откладывает то, что записал после
разрыва, в ha/diverged-….

Настройки — config.yaml: ha.peer (адрес второго узла), ha.self (адрес
этого узла для клиентов), ha.token_file, ha.replicate_every,
ha.require_standby.

Примеры:

```
ochan ha init --node a --role primary
ochan ha init --node b --role standby
ochan ha status
ochan ha status a.example:7443,b.example:7443
ochan ha promote
```

Подкоманды: [`init`](#ochan-ha-init), [`promote`](#ochan-ha-promote), [`status`](#ochan-ha-status).

## ochan ha init

Сделать этот узел узлом пары.

```

```

Записывает ha.json узла: имя и роль. Первый узел — primary, второй —
standby. Общий секрет пары (ha.token_file) создаётся, если его нет:
скопируйте его на второй узел так же бережно, как ключ TLS.

Право: `read`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--node` | string | — | имя узла |
| `--role` | string | — | primary или standby |

## ochan ha promote

Сделать этот узел primary: переключение пары.

```
ochan ha promote
```

Эпоха узла становится на единицу больше известной. Работающий ochan serve
подхватывает её сам; бывший primary, увидев большую эпоху, отступает и
откладывает то, что успел записать после разрыва.

Консенсуса нет: решение — ваше. Если бывший primary жив и отрезан сетью,
до восстановления связи он будет принимать запись — остановите его или
отрежьте от клиентов, прежде чем повышать резерв.

Заявки, которые числились выполняемыми на бывшем primary, становятся
упавшими с неизвестным исходом: второй раз они не выполняются.

Право: `read`.

## ochan logs rank

Ранжировать строки журнала по уровням важности.

```

```

Уровень строки задают правила logs.rules — регулярные выражения по порядку:

|---|---|---|---|
| `--min` | string | — | показывать строки этого уровня и важнее (по умолчанию logs.min_level) |
| `--summary` | bool | — | сводка: строки по уровням и частые сообщения |
| `--top` | int | `10` | сколько частых сообщений показать в сводке (0 — все) |

## ochan plan

Показать, что произойдёт, ничего не делая.

```
ochan plan <сценарий> | plan <база> <изменения> | plan --script <файл.ochan | ->
```

С одним аргументом планирует сценарий: какие операции были бы
выполнены и над чем. С двумя — показывает, какие параметры изменит
patch.

Способ выполнения сценария выбирается по его полю service, флага
для этого нет. Изменяющие запросы в режиме плана запрещены на уровне
клиента, поэтому команда не может ничего создать даже по ошибке.

Файл .ochan (или --script) — сценарий на языке алиасов. Он проверяется
целиком и выполняется в режиме плана: write и save ничего не пишут,
а печатается, какие файлы и параметры они изменили бы. Чтение файлов
и живых источников при этом настоящее — без него планировать нечего.

Право: `plan`.

Примеры:

```
ochan plan restart.yaml
ochan plan prod.conf changes.conf
ochan plan эталон.conf postgres://dba@db1:5432/postgres
ochan plan сценарий.ochan
ochan plan --script --sandbox --root ./configs - < сценарий.ochan
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-env` | stringArray | — | разрешить в песочнице переменную окружения; можно указать несколько раз |
| `--allow-exec` | stringSlice | — | разрешить exec() сценария запускать эти программы (kubectl,terraform) — только в песочнице ядра; оболочки и интерпретаторы не разрешаются |
| `--allow-live` | stringArray | — | разрешить в песочнице живые источники этой схемы, например postgres |
| `--allow-net` | stringArray | — | разрешить в песочнице fetch и curl к этому хосту (host или host:port); можно указать несколько раз |
| `--bundle` | bool | — | stdin — JSON {"script": …, "prompt": …, "report": …}; так их передаёт ochan-mcp |
| `--limit` | stringArray | — | только цели (хосты инвентаря), подходящие под селектор: group=db_new, host=db*; можно указать несколько раз |
| `--name` | string | — | имя сценария, поданного на stdin |
| `--prompt` | string | — | формальный промпт: его жёсткие правила проверяются по плану сценария |
| `--report` | string | — | отчёт модели (раздел report:), проверяется вместе с промптом |
| `--root` | stringArray | — | разрешённый каталог песочницы; можно указать несколько раз (по умолчанию — текущий) |
| `--sandbox` | bool | — | песочница: файлы только внутри --root, окружение, живые источники и сеть — только разрешённые |
| `--script` | bool | — | сценарий на языке алиасов (для файла .ochan подразумевается) |
| `--trust` | stringSlice | — | правила (пакет.алиас, write, save), которым оператор доверяет без журнала: их утверждения проходят кольцо 2 |

## ochan policy

```

```

Политика — заранее данное согласование с границами: сценарий, белый список
меток целей (селекторы инвентаря), белый список параметров сценария с
допустимыми значениями и срок. ochan watch выполняет сам только то, что
в неё укладывается; всё остальное — заявки, а не изменения.

Без подкоманды — список политик, и отозванных тоже.

Право: `read`.

Примеры:

```
ochan policy

ochan policy show new-servers
ochan policy revoke new-servers --reason "миграция закончилась"
```

Подкоманды: [`add`](#ochan-policy-add), [`revoke`](#ochan-policy-revoke), [`show`](#ochan-policy-show).

## ochan policy add

Зарегистрировать политику: заранее данное согласование.

```
ochan policy add <файл>
```

Политику регистрируют с правом approve: по ней ochan watch согласует
заявки сам. Файл:

  name: new-servers

  targets: [group=db_new]    # белый список меток целей

Действующую политику с тем же именем не заменяют: сначала её отзывают.

Право: `approve`.

```
ochan policy revoke <имя>
```

## ochan request

Создать заявку на изменение из плана.

```
ochan request <сценарий> | request <база> <изменения> | request --script <файл.ochan | ->
```

Заявка фиксирует план и ждёт решения. Выполнить её можно только
после согласования: ochan apply --request <id>.

Заявка отвечает не на вопрос «кому в принципе можно», а на вопрос
«на это конкретное изменение сказали да» — именно это нужно аудиту.

Файл .ochan (или --script) — сценарий на языке алиасов: он проверяется,
план строится выполнением в режиме плана, а в заявку попадают его текст,
каталог и песочница. При выполнении план строится заново и должен совпасть.

--after <id> — порядок: заявка выполнится только после указанных. Если
она упадёт, те, после которых она шла, остаются выполненными — сбой их
не откатывает; упавшую не повторяют, а оформляют заново, и заявки после
неё — тоже. Повтор и расписание — дело модуля рабочего процесса.

Право: `request`.

Примеры:

```
ochan request restart.yaml --doc заявка.docx
ochan request prod.conf changes.conf
ochan request deploy.yaml --after 1c4a
ochan request сценарий.ochan
ochan request --script --sandbox --root ./configs - < сценарий.ochan
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--after` | stringSlice | — | выполнять только после этих заявок |
| `--allow-env` | stringArray | — | разрешить в песочнице переменную окружения; можно указать несколько раз |
| `--allow-exec` | stringSlice | — | разрешить exec() сценария запускать эти программы (kubectl,terraform) — только в песочнице ядра; оболочки и интерпретаторы не разрешаются |
| `--allow-live` | stringArray | — | разрешить в песочнице живые источники этой схемы, например postgres |
| `--allow-net` | stringArray | — | разрешить в песочнице fetch и curl к этому хосту (host или host:port); можно указать несколько раз |
| `--bundle` | bool | — | stdin — JSON {"script": …, "prompt": …, "report": …}; так их передаёт ochan-mcp |
| `--doc` | string | — | выгрузить заявку в файл .docx |
| `--limit` | stringArray | — | только цели (хосты инвентаря), подходящие под селектор: group=db_new, host=db*; можно указать несколько раз |
| `--name` | string | — | имя сценария, поданного на stdin |
| `--prompt` | string | — | формальный промпт: его жёсткие правила проверяются по плану сценария |
| `--report` | string | — | отчёт модели (раздел report:), проверяется вместе с промптом |
| `--root` | stringArray | — | разрешённый каталог песочницы; можно указать несколько раз (по умолчанию — текущий) |
| `--sandbox` | bool | — | песочница: файлы только внутри --root, окружение, живые источники и сеть — только разрешённые |
| `--script` | bool | — | сценарий на языке алиасов (для файла .ochan подразумевается) |
| `--trust` | stringSlice | — | правила (пакет.алиас, write, save), которым оператор доверяет без журнала: их утверждения проходят кольцо 2 |

## ochan rollback

Отменить изменение файлов из истории.

```

```

## ochan sandbox

Показать, какую изоляцию даёт песочница на этой системе.

```
ochan sandbox
```

Сценарий с --sandbox выполняется отдельным процессом. На Linux его
ограничивает ядро: Landlock пускает только в разрешённые каталоги,
seccomp запрещает запуск программ, отладку чужих процессов, монтирование
и сокеты, своё сетевое пространство оставляет без сети. На других ОС
файлы и сеть держит только песочница языка.

С sandbox.strict: true в config.yaml сценарий не выполняется, если
изоляция неполная.

С --allow-exec проба ставит песочницу с запуском этих программ: так
видно, даст ли ядро такую изоляцию, до того как на неё рассчитывать.

Право: `read`.

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-exec` | stringSlice | — | проверить песочницу с запуском этих программ |

## ochan serve

Запустить общий оркестратор: подключение по сети в одной из ролей.

```
ochan serve
```

Сервер держит роли у себя: логин и пароль проверяет он, и подключившийся
не может их обойти. Команды клиента выполняются на сервере, в роли сессии,
над файлами сервера в каталоге server.dir.

Настройки — в config.yaml: ssl (шифрование вкл/выкл), tls.min_version,
tls.cert, tls.key, server.listen, server.dir, server.session_timeout,
server.command_timeout. Сертификат создаёт ochan tls init.

Без ssl сервер слушает только эту машину: иначе пароли ролей шли бы по
сети открытым текстом. --allow-plaintext снимает запрет.

Право: `server`.

Примеры:

```
ochan tls init --host orchestrator.example
ochan serve --listen 0.0.0.0:7443
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--allow-plaintext` | bool | — | разрешить работу без ssl на сетевом адресе |
| `--dir` | string | — | каталог, над файлами которого работают команды (по умолчанию server.dir или текущий) |
| `--listen` | string | — | адрес сервера (по умолчанию server.listen) |

Показывает состояние того, что создал исполнитель сценариев: задачи RLM,
задания на машине — чего угодно, у чего есть статус. Ссылку печатает
apply: «Создано: …».

Исполнитель выбирается флагом: --executor rlm или коротко --rlm (флаг
есть у каждого исполнителя, который умеет показывать статус). Если такой
исполнитель один, флаг не нужен. Исполнители приходят модулями: статус
показывает тот, кто реализует scenario.StatusReporter.

Право: `read`.

Примеры:

```
ochan status 4f1c2a
ochan status 4f1c2a 9b7e01 --rlm
ochan status job-17 --executor linux
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--executor` | string | — | исполнитель, у которого спросить статус: rlm, linux… |

## ochan tls init

Создать самоподписанный сертификат сервера.

```
ochan tls init
```

Создаёт ключ ECDSA P-256 и сертификат в tls.key и tls.cert. Клиентам
этот же сертификат указывается как tls.ca: самоподписанный сертификат
сервера — сам себе удостоверяющий центр. Сверьте отпечаток при передаче.

Право: `server`.

Примеры:

```

```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--days` | int | `365` | срок действия сертификата в днях |
| `--force` | bool | — | перезаписать существующие сертификат и ключ |
| `--host` | stringArray | — | имя или адрес сервера в сертификате; можно указать несколько раз |

## ochan watch

Следить за инвентарём: новый хост — план, заявка, а по политике — выполнение.

```
ochan watch --source <источник> (--policy <имя|файл> | --scenario <сценарий>)
```

Проход: читает источник инвентаря, находит новые хосты (которых ещё не
видели), для каждого строит план сценария, суженного до этого хоста, и
оформляет заявку. Обработанный хост отмечается увиденным.

Проверять и планировать по расписанию ochan может сам; выполнять — только
по зарегистрированной политике (ochan policy add). Заявка, которая в неё
укладывается — метки хоста, параметры сценария, сервис, план без
прерывания обслуживания, предел роли на apply, — согласуется политикой и
выполняется. Всё остальное остаётся заявкой и ждёт человека; причина
печатается. Отозванная или истёкшая политика выключает выполнение со
следующего прохода.

Без --every — один проход: для cron. С --every — проходы до остановки.

Право: `request`.

Примеры:

```
ochan watch --source cmdb --policy new-servers
ochan watch --source cmdb --policy new-servers.yaml --every 10m
ochan watch --source cmdb --scenario tune.yaml
```

| Флаг | Тип | По умолчанию | Описание |
|---|---|---|---|
| `--every` | duration | `0s` | повторять проход с этим промежутком (от 1m); без него — один проход |
| `--policy` | string | — | политика: имя или её файл — выполнять то, что в неё укладывается |
| `--scenario` | string | — | сценарий без политики: только заявки |
| `--source` | string | — | источник инвентаря (имя из inventory.sources или local) |
