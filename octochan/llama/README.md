# Лама в ФПм-вид

Своя модель ochan (`llm.mode: embedded`) знает только формальный промпт.
Здесь — два пути к ней и замер каждого шага. Первый — дообучить готовую
модель архитектуры Llama: адаптер к протоколу движка v1, обрезка выходного
словаря до алфавита ℒ, LoRA. Второй — своя модель ℒ с нуля: архитектура
Llama, веса и словарь только ℒ. Доступ к Llama 3.2 Meta владельцу не дала,
поэтому основная линия — вторая. План целиком —
[docs/plans/llama-fpm.md](../docs/plans/llama-fpm.md).

| Файл | Что делает |
|---|---|
| `adapter.py` | сервер протокола движка v1: распределение следующего токена до выборки, кеш KV по общему префиксу; `raw` — сырой вывод без колец |
| `fpm.py` | модель в ФПм-виде: базовая модель и выходной слой, обрезанный до алфавита (`fpm.json`, `lm_head.safetensors`) |
| `prune.py` | шаг 2: обрезка выходного словаря до алфавита ℒ (`ochan fp alphabet`) |
| `corpus.py` | шаг 3: синтетический корпус пар «задача → ответ» на ℒ; ответ выводится из задачи (`solve`), каждую пару проверяет разбор ochan |
| `fpcheck/` | пакетная проверка текстов разбором ochan (JSONL на входе и выходе) для `corpus.py` |
| `train.py` | шаг 3: LoRA и выходной слой на корпусе ℒ; сохранения и продолжение после сброса видеокарты |
| `measure.py` | замер: сырой вывод против встроенного режима ochan по набору задач; язык, согласованность отчёта, точное совпадение с `solve`, H3 |
| `fpmtok.py` | словарь своей модели: алфавит ℒ, цифры, разметка строки; имена частных случаев — переменные |
| `own.py` | своя модель ℒ: архитектура Llama с нуля; движок протокола v1 для неё (адаптер узнаёт каталог сам) |
| `train_own.py` | обучение своей модели с нуля на корпусе ℒ |
| `quantize.py` | шаг 4: int8 и int4 своей модели, сверка с исходной |
| `tasks/` | задачи эксплуатации на ℒ; каждая проходит `ochan fp check` |

## Окружение

Модели, venv и кеши — не на системном диске:

```
py -3.12 -m venv G:\fpm-llm\venv
set PIP_CACHE_DIR=G:\fpm-llm\cache\pip
set HF_HOME=G:\fpm-llm\cache\hf
G:\fpm-llm\venv\Scripts\python -m pip install torch --index-url https://download.pytorch.org/whl/cu128
G:\fpm-llm\venv\Scripts\python -m pip install transformers safetensors accelerate peft huggingface_hub
```

Проверено: Windows 10, RTX 5070 12 ГБ (sm_120), torch 2.11.0+cu128,
transformers 5.22.1, peft 0.21.2. Для RTX 50xx нужна сборка CUDA 12.8 и
новее. Llama 3.2 у Meta — по лицензии: её принимает аккаунт Hugging Face
владельца, токен — переменная `HF_TOKEN`.

## Запуск

```
ochan fp alphabet > alphabet.tsv
python prune.py --model HuggingFaceTB/SmolLM2-135M-Instruct --alphabet alphabet.tsv --corpus "tasks/*.fp" --out G:/fpm-llm/models/smollm2-135m-fpm
python adapter.py serve --model G:/fpm-llm/models/smollm2-135m-fpm --listen 127.0.0.1:8091
```

```yaml
# config.yaml ochan
llm:
  mode: embedded
  engine: transformers
  endpoint: http://127.0.0.1:8091
  rings:
    tau: 0.42
```

```
ochan llm generate --prompt tasks/pg_memory.fp
python measure.py --model G:/fpm-llm/models/smollm2-135m-fpm --ochan ochan --endpoint http://127.0.0.1:8091 --home G:/fpm-llm/runs/home --out run.jsonl "tasks/*.fp"
```

`measure.py` запускает ochan в отдельном доме: журнал и роли пользователя
замер не трогает.

Обучение (шаг 3):

```
go build -o fpcheck.exe ./llama/fpcheck
ochan fp protocol --mode formal > protocol.txt
python corpus.py --lexicon ../fp/lexicon.yaml --fpcheck fpcheck.exe --count 4000 --out corpus.jsonl --tasks G:/fpm-llm/runs/tasks-test
python prune.py --model HuggingFaceTB/SmolLM2-135M-Instruct --alphabet alphabet.tsv --corpus "tasks/*.fp" corpus.jsonl --out G:/fpm-llm/models/smollm2-135m-fpm
python train.py --model G:/fpm-llm/models/smollm2-135m-fpm --protocol protocol.txt --corpus corpus.jsonl --out G:/fpm-llm/models/smollm2-135m-fpm-lora --checkpointing --resume
python adapter.py serve --model G:/fpm-llm/models/smollm2-135m-fpm-lora --listen 127.0.0.1:8092
```

Своя модель ℒ с нуля (шаг 3б) и её квантование (шаг 4):

```
ochan fp alphabet > alphabet.tsv
python corpus.py --lexicon ../fp/lexicon.yaml --fpcheck fpcheck.exe --count 60000 --seed 11 --out corpus-own.jsonl --tasks G:/fpm-llm/runs/tasks-gen --tasks-count 60
python train_own.py --alphabet alphabet.tsv --corpus corpus-own.jsonl --out G:/fpm-llm/models/own-small --epochs 10
python quantize.py --model G:/fpm-llm/models/own-small --bits 4 --out G:/fpm-llm/models/own-small-int4 --check corpus-own.jsonl
python adapter.py serve --model G:/fpm-llm/models/own-small-int4 --listen 127.0.0.1:8093
```

Пара корпуса длиной ~4 500 токенов, почти всё — протокол. Без
`--checkpointing` активации SmolLM2 занимают 18 ГБ и выходят за 12 ГБ
видеокарты; с ним — 4,3 ГБ. Под Windows драйвер иногда сбрасывает
видеокарту (событие `nvlddmkm` 153, TDR), процесс теряет CUDA: с
`--resume` повторный запуск продолжает с последнего сохранения
(`--save-every`, по умолчанию 50 шагов).

## Замеры

Модель для отладки — SmolLM2-135M-Instruct (архитектура Llama, Apache 2.0),
пока нет доступа к Llama 3.2 1B. Набор — 8 задач из `tasks/`. Числа — из
прогонов `measure.py` 31.10.2026.

**Шаг 1. Базовая модель через адаптер.**

| τ | raw в ℒ | embedded с ответом | откатов | утверждений вне ℒ | отклонено кольцом 0 | позиций без токена |
|---|---|---|---|---|---|---|
| 0,42 | 0/8 | 0/8 | 0 | 0 | 15 | 8 |
| 0,1 | 0/8 | 0/8 | 49 | 8 | 19 186 | 48 |

Сырой вывод — английская проза («The language does not have a `Backup`
class…»), а на задаче с русским комментарием модель повторяет его по-русски.
Во встроенном режиме при τ = 0,42 ответа нет ни разу: уже первый токен
утверждения не дотягивает до порога (самый вероятный — «To», p ≈ 0,17).
При τ = 0,1 кольца работают — откаты, утверждения вне ℒ, снятые позиции, —
но ни одно утверждение языка модель не собирает.

**Шаг 2. Словарь вывода = алфавит ℒ.** `ochan fp alphabet` — 425 записей
(слова, смыслы-классы, служебные слова, ключевые слова, единицы, знаки).
Вместе с их сочетаниями из корпуса, буквами и цифрами: словарь вывода
49 152 → 1 250 токенов, выходной слой 28,3 → 0,72 млн параметров, токенов
вне ℒ на выходе — 0. Входной словарь целый: модель читает протокол и задачу
как есть.

| τ | raw в ℒ | embedded с ответом | откатов | утверждений вне ℒ | отклонено кольцом 0 | позиций без токена |
|---|---|---|---|---|---|---|
| 0,42 | 0/8 | 0/8 | 0 | 0 | 16 | 8 |
| 0,1 | 0/8 | 0/8 | 14 | 9 | 55 254 | 10 |

Обрезка убирает чужие символы и языки — кириллицы, эмодзи, «Sure!» у модели
больше нет, — но не английский синтаксис. Сырой вывод по-прежнему проза:
«A user can set the default value of the "Backup" relation…» — она
складывается из слов самого алфавита (a, the, of, set, value, relation).
Словарь ℒ — подмножество английского, поэтому язык держат грамматика в
декодере ochan и обучение (шаг 3), а не словарь.

**Шаг 3. LoRA на корпусе ℒ.** Корпус — 4 000 синтетических пар «задача →
ответ» (`corpus.py`): классы, цепочка отношений, приоритеты, жёсткий запрет,
значения задачи в `cell c1`. Ответ выводится из задачи (`solve`): копия
задачи, затем решения — отношения `defines`, `limits`, `modifies` переносят
атрибут источника на цель, у которой его нет; если два источника дают цели
разные значения, решает `priority:` (с `alternatives:`), без приоритета
решения нет; затем `report:` — запись `q: атрибут` на каждое решение, с
основанием. Каждую пару принимает разбор ochan. Обучение — 3 600 пар,
отложено 400; 30 задач замера — первые из отложенных (`tasks-test`). LoRA
r = 16 и выходной слой, 5,6 млн параметров; одна эпоха, 450 шагов по 8 пар,
lr 2·10⁻⁴ — 3 ч на RTX 5070. Потери на отложенных парах: 0,498 → 0,013.

По дороге исправлено четыре вещи, каждая видна в замере:

- *Токены через перевод строки.* BPE пишет «\n  set» как «\n », « set», а
  декодер проверяет язык по строкам и режет токен на `\n`: модель, обученная
  на обычной токенизации, во встроенном режиме ломалась на первом
  утверждении. Ответ токенизируется построчно — при обучении и в адаптере, —
  в алфавите нет токенов с текстом после `\n` (1 250 → 1 242), а output
  адаптер кодирует путём, который модель сама написала.
- *Случайные решения.* В первом корпусе решение выбиралось случайно, и на
  развилке модель давала p ≈ 0,02 — кольцо 0 справедливо не пускало ни
  одного продолжения. Теперь решение — функция задачи.
- *Построчная проверка отчёта* (ochan, `fp`). Запись `q:` без `choice:` и
  `basis:` была отказом ⊥syn, даже когда они идут следующими строками:
  во встроенном режиме не писалась ни одна запись `report:`, и ответ
  складывался только у задач без решений. Теперь запись в конце текста —
  недописанная (Incomplete), как пустой раздел в конце; в готовом тексте —
  по-прежнему отказ.
- *Недетерминированный адаптер.* В bf16 логиты зависят от того, как вход
  поделён на куски: на test12 конец ответа получал p = 0,531 или 0,562 в
  зависимости от истории кеша — на развилке около 0,5 этого хватает, чтобы
  сырой вывод и встроенный режим расходились из-за шума, а не колец. Теперь
  промпт без последнего токена считается одним куском, ответ — по токену:
  распределение совпадает побитно при любой истории запросов.

Языка модель держится сама: на отложенных raw в ℒ 30/30, при τ = 0,1
декодеру нечего делать — ни отката, ни утверждения вне ℒ, ответ встроенного

Копия задачи верна в 28/30, ошибаются решения — лишнее решение по
отношению, которое атрибут не переносит (3 задачи), пропущенная цель или
решение (5), чужое имя отношения в `basis` (6), конфликт решён против
приоритета (3); в одной задаче бывает по нескольку. Форма при этом
держится: «сходится» 28/30 — отчёт согласован с решениями, ошибка в самом
выводе.

При τ = 0,42 кольцо 0 отказывает, где модель не уверена: на test02 в
`basis: priority(` лучший класс — 0,33, ответа нет; сырой вывод там угадал
неверно. На test17 развилка — ничья 0,495 / 0,495, и декодер с argmax
разбивают её по-разному.

Задачи `tasks/` — вне корпуса: в них обобщения, `import`, `requires:`,
частные случаи, `binds_to:`, которых синтетика не даёт. На `connections.fp`
модель зацикливается в строке `priority:`, на `navigation.fp` портит уже
`goal:`. «Точно» здесь меряется по `solve`, который знает только отношения и
приоритеты, — для этих задач значимы язык и согласованность. H3 (⊥undef на
недостающую предпосылку) корпус шага 3 не покрывал: в нём не было
`requires:`.

**Шаг 3б. Своя модель ℒ с нуля.** Доступ к Llama 3.2 Meta не дала, и
основная линия — модель, у которой и веса, и словарь только ℒ. Архитектура
Llama (`own.py`): ширина 384, 8 слоёв, 6 голов, MLP 1 024, вход и выход
связаны, контекст 1 024 — 14,5–14,8 млн параметров в зависимости от
словаря. Протокол модель не читает: пара — `<bos>` задача `<answer>` ответ
`<eos>`.

Обучение делится так, как его задумывал П3. Статистика — только по конечному
словарю: словарь модели — алфавит ℒ, цифры и разметка строки. Имена частных
случаев (значения слотов, имена стрелок, ячеек, версий) — переменные `<vK>`
по первому появлению: их модель не учит, а переносит, и ответ по построению
не меняется, когда меняется только имя (А.6, пункт а). Логика — в ответах:
их выводит `solve`, каждую пару принимает разбор ochan. Потери — по всей
паре: задачи (определения обобщений, отношения, правила) — тоже язык,
который модель учит.

Корпус расширен обобщениями и частными случаями. Обобщение — схема
отношения, частный случай — стрелка этой схемы: имя стрелки (`h121151`) —
ссылка, через которую ячейки правят частный случай, значение слота
(`plodu2222_ru`) — частное имя без определения. Новый вывод — по стрелке:
атрибут, заданный обобщению, переходит на каждую его стрелку, у которой он
не задан, — и только так: ни на обобщение, ни на соседние стрелки атрибут
стрелки не переходит. Близнецы H3 — стрелка к необъявленному обобщению с
похожим именем, незаполненный слот, операция обобщения не из скилла. 60 001
пара, все приняты ochan (генерация — 51 с): обучение 54 000, отложено 6 001;
без предпосылки 18 218, перенос 17 099, перенос и по стрелке 8 457, без
решений 8 216, конфликт 4 017, по стрелке 3 994. 60 задач замера
(`tasks-gen`) — первые из отложенных. Старый корпус `solve` выводит без
изменений (5 001 из 5 001).

Словарь — в двух вариантах, каждый — 10 эпох на RTX 5070:

| словарь | токенов | пара, токенов | обучение | потери на ответе (отложенные) |
|---|---|---|---|---|
| первый: пробел и `_` — отдельные токены | 764 | ~480 | 30 мин | 6,646 → 0,021 |

если верны все ~250 его токенов. Почти весь остаток потерь первой модели —

строго, теперь — по канонической записи. В `tasks/` две задачи до модели не
доходят: `connections.fp` и `navigation.fp` берут слова из словарей
скиллов, а заглушкам словари не ставятся (⊥syn); остальным модели не из
чего ответить — в корпусе нет ни их слов, ни их конструкций.

**Шаг 4. Квантование своей модели** (`quantize.py`), вторая модель. Сверка —
на 1 000 отложенных парах с подстановкой верного префикса; «точно» — сырой
вывод на 60 задачах со стрелками:

| веса | размер | тот же токен | потери на ответе | точно, без копии | точно, копия задана |
|---|---|---|---|---|---|
| fp32 | 56,5 МБ | — | 0,0302 | 13/60 | 23/60 |
| int8, по строке | 14,2 МБ | 99,98 % | 0,0302 | 13/60 | 23/60 |
| int4, группы по 32 | 8,0 МБ | 99,83 % | 0,0306 | 10/60 | 20/60 |

int8 даёт те же ответы, что fp32; int4 теряет 3 задачи из 60. Вывод
детерминирован: повтор fp32 под другой нагрузкой видеокарты — те же 60
ответов из 60 (fp32, распределение считается по токену).

Вывод шагов 3б и 4: статистика выучила язык и перенос имён, но логику —
перенос по отношениям, приоритеты, стрелки — она делает статистически и
ошибается именно в ней. Там, где детерминированную часть у неё забрали
(копия задачи), точность выросла с 13 до 23 из 60. Следующий шаг — логика
строит множество допустимых пакетов, а модель только выбирает среди них
([план](../docs/plans/llama-fpm.md)).
