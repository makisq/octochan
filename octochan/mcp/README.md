# ochan-mcp

Сервер [Model Context Protocol](https://modelcontextprotocol.io) для octochan.

Это **отдельный модуль**, а не часть ядра. У него свой `go.mod`, ни одной
внешней зависимости, и ядро о нём не знает: `ochan` без него работает так же,
как раньше. Внутри нет ни одной модели и нет кода конкретного поставщика —
MCP открытый протокол, и подключиться может любой клиент с любой моделью.

## Принцип

**Нейросеть предлагает, человек решает.** Через сервер можно читать
конфигурации, строить планы, писать сценарии на языке алиасов и создавать
заявки. Выполнить изменение нельзя: заявку согласует и выполняет человек.

```
модель  →  plan_config / plan_scenario  →  request_config / request_scenario
модель  →  check_prompt → check_script → plan_script → request_script
                                                        ↓
человек →  ochan approve <id>  →  ochan apply --request <id>  →  rollback / compensate
```

## Протокол

При подключении модель первым получает протокол формального промпта: сервер
берёт его у `ochan fp protocol` при запуске и отдаёт в `instructions`
ответа на `initialize`. Протокол говорит модели, кто она здесь (слой, а не
собеседник), на каком языке с ней говорят, какие бывают отказы и в каком
порядке работать. Для клиентов, которые `instructions` модели не
показывают, тот же текст отдаёт инструмент `protocol`.

Какой протокол, решает `fp.mode` в `config.yaml` ochan: `formal` —
задачи только формальным промптом, `natural` — модель принимает их на
естественном языке (жёстких правил промпта тогда нет; согласование заявок
и пределы роли остаются). Сервер читает протокол при запуске: после смены
`fp.mode` его перезапускают.

Язык формального промпта замкнут: слово со смыслом — только из словаря.
Словарь модель смотрит инструментом `vocabulary` (`ochan fp words`):
базовый, словари оператора и скиллов; отчёт модели тоже пишется словами
словаря.

Протокол, `instructions`, заголовки и описания инструментов и их
параметров написаны по-английски — всегда, независимо от языка оператора
(`lang`): модели понимают английский лучше, и формальный промпт пишется на
нём. Сообщения самого сервера — ошибки протокола и отказы до запуска
(«The call was rejected before it ran: …») — тоже по-английски. Тест
следит, чтобы в описаниях не появилась кириллица. Вывод инструментов
(находки проверки, план, заявка) — на языке оператора; коды отказов
`⊥syn`, `⊥ambig`, `⊥undef`, `⊥conflict` одинаковы везде.

Протокол живёт в `ochan`, рядом с проверкой языка, а не копией в сервере:
иначе модель читала бы одно, а проверка требовала бы другого. Если `ochan`
протокол не отдал, сервер работает, но пишет об этом в журнал и в
`instructions`.

Это свойство не держится на договорённости. Таблица инструментов проверяется
при запуске: команда, которой нет в закрытом списке, не пройдёт проверку,
и сервер не стартует.

Второй рубеж — роль. Сервер запускает `ochan` с `OCTOCHAN_ROLE=llm`, что бы
ни было текущей ролью пользователя и что бы ни стояло в окружении сервера.
У роли `llm` права `read`, `plan` и `request`, и выше этого потолка их не
поднять. Даже если в таблицу по ошибке попадёт выполняющая команда, `ochan`
откажет сам.

## Сборка

`make install` в каталоге `octochan` ставит `ochan-mcp` рядом с `ochan`
в `~/.local/bin` (на Windows — `scripts\install.ps1`), и оба вызываются по
имени. Сервер находит `ochan` рядом с собой или в `PATH`; иначе — флаг
`--ochan`. Собрать руками:

```bash
cd octochan/mcp
go build -o ochan-mcp .
```

## Запуск

Сервер говорит по stdio, его запускает клиент. Конфигурация в формате,
который понимает большинство клиентов:

```json
{
  "mcpServers": {
    "octochan": {
      "command": "C:/tools/ochan-mcp.exe",
      "args": ["--root", "D:/configs"]
    }
  }
}
```

| Флаг | По умолчанию | |
|---|---|---|
| `--root DIR` | текущий каталог | где разрешены файлы; можно указать несколько раз |
| `--allow-live postgres` | выключено | разрешить живые источники этой схемы |
| `--allow-env NAME` | ни одной | разрешить сценариям читать эту переменную окружения; можно указать несколько раз |
| `--allow-net HOST` | ни одного | разрешить сценариям `fetch` и `curl` к этому хосту (`хост` или `хост:порт`); можно указать несколько раз |
| `--ochan PATH` | рядом или из `PATH` | путь к `ochan` |
| `--timeout 2m` | 2 минуты | предел одного вызова |
| `--max-output N` | 100 000 байт | предел вывода, который получает модель |

Настройки `ochan` — адрес API, токен, почта — берутся из его обычного
конфига и окружения: сервер передаёт `ochan` своё окружение как есть.

Корень, который накрывает рабочий каталог ochan (`~/.octochan`), сервер не
примет и не стартует: там роли, ключ подписи допусков сервера и токены.
Запускайте его из каталога проекта или укажите `--root`.

## Удалённый доступ по HTTP

С `--listen` сервер говорит по Streamable HTTP (MCP 2025-03-26 и
2025-06-18) — так к нему подключаются модели, которые работают не на вашей
машине: коннектор MCP в Claude API, инструмент `mcp` в OpenAI Responses API,
ChatGPT, Claude.ai, Gemini CLI, Claude Code, Cursor, VS Code и любая
программа на MCP SDK. Инструменты, роль `llm` и границы — те же, что по
stdio: удалённая модель читает, планирует и оформляет заявки, а выполняет
их человек.

```bash
# на машине с конфигурациями, за прокси или туннелем с TLS
ochan-mcp --root /srv/configs --listen 127.0.0.1:8765

# или сразу с TLS на сетевом адресе
ochan-mcp --root /srv/configs --listen 0.0.0.0:8443 \
  --tls-cert /etc/ochan-mcp/fullchain.pem --tls-key /etc/ochan-mcp/privkey.pem
```

При первом запуске сервер создаёт токен доступа — 256 случайных бит в
`~/.config/ochan-mcp/token` (права 0600) — и пишет в журнал, где он лежит.
Токен можно задать и окружением `OCHAN_MCP_TOKEN` (не короче 32 знаков).
Клиент отправляет его заголовком:

```
POST https://mcp.example.com/mcp
Authorization: Bearer <токен>
```

Клиентам, которые не умеют задавать заголовки (коннекторы ChatGPT и
Claude.ai без OAuth), — адрес с токеном: `https://mcp.example.com/mcp/<токен>`.
Такой адрес — сам секрет: не публикуйте его и не пишите в журналы прокси.

| Флаг | По умолчанию | |
|---|---|---|
| `--listen ADDR` | выключено (stdio) | слушать адрес по HTTP |
| `--path /mcp` | `/mcp` | путь MCP |
| `--token-file FILE` | `~/.config/ochan-mcp/token` | файл токена; нет файла — создаётся |
| `--tls-cert`, `--tls-key` | — | сертификат и ключ TLS |
| `--allow-plaintext` | выключено | HTTP без TLS на сетевом адресе: TLS снимает прокси |
| `--allow-origin URL` | ни одного | разрешить запросы из браузера с этого Origin |
| `--session-idle 1h` | 1 час | сколько живёт сессия без запросов |

Что держит сервер:

- **Токен** — на каждом запросе, сравнение за постоянное время; путь с
  токеном в журнал не пишется.
- **TLS** обязателен на любом адресе, кроме loopback, — иначе сервер не
  стартует; минимум TLS 1.2. За прокси, который сам снимает TLS, — флаг
  `--allow-plaintext`.
- **Origin.** Запрос с заголовком `Origin` (из браузера) принимается только
  с адресов из `--allow-origin`: страница, перепривязавшая своё имя DNS на
  127.0.0.1, до сервера не дотянется. Тело — только `application/json`:
  «простой» запрос формы из браузера отвергается.
- **Сессии.** `Mcp-Session-Id` выдаётся при `initialize`; без него вызовы
  не принимаются (400), чужая или истёкшая сессия — 404, `DELETE` её
  закрывает. Отмена вызова (`notifications/cancelled`) действует только в
  своей сессии. Сессий не больше ста.
- **Версия протокола** из заголовка `MCP-Protocol-Version` проверяется:
  незнакомая — 400.
- **Журнал аудита.** `ochan` под сервером знает адрес клиента: в
  `ochan audit` вызовы удалённой модели видны как роль `llm` с адресом
  `mcp <IP>`.

Потока событий от сервера (`GET`) нет: уведомлений сервер не шлёт, `GET`
отвечает 405.

### Подключение клиентов

Готовые конфиги — в [clients/](clients/); адрес везде
`https://mcp.example.com/mcp`, токен — из `OCHAN_MCP_TOKEN`.

| Клиент | Как | Файл |
|---|---|---|
| Claude API (Messages) | `mcp_servers` + `mcp_toolset`, бета `mcp-client-2025-11-20`; токен — `authorization_token` | [claude-api.sh](clients/claude-api.sh) |
| Claude Code | `claude mcp add --transport http … --header "Authorization: Bearer …"` | [claude-code.sh](clients/claude-code.sh) |
| OpenAI Responses API | инструмент `{"type": "mcp", "server_url": …, "headers": …}` | [openai-responses.sh](clients/openai-responses.sh) |
| ChatGPT, Claude.ai | свой коннектор в настройках: адрес `https://mcp.example.com/mcp/<токен>`, без аутентификации — токен уже в адресе | — |
| Gemini CLI | `~/.gemini/settings.json`: `httpUrl` и `headers` | [gemini-settings.json](clients/gemini-settings.json) |
| Cursor | `~/.cursor/mcp.json`: `url` и `headers` | [cursor-mcp.json](clients/cursor-mcp.json) |
| VS Code | `.vscode/mcp.json`: `type: http`, токен спрашивается при подключении | [vscode-mcp.json](clients/vscode-mcp.json) |
| Своя программа | MCP SDK для Python 2.x | [python_client.py](clients/python_client.py) |
| Локальные модели (Ollama, LM Studio…) | через любой клиент выше; на той же машине проще stdio | — |

Модели поставщиков ходят к серверу из интернета: адрес должен быть
публичным и с настоящим сертификатом (Let's Encrypt, прокси или туннель),
самоподписанному они не поверят. Gemini CLI, Claude Code, Cursor и VS Code
работают на вашей машине — им хватит `127.0.0.1`.

Проверка руками:

```bash
TOKEN=$(cat ~/.config/ochan-mcp/token)
curl -si -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -X POST http://127.0.0.1:8765/mcp \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18"}}' \
  | grep -i mcp-session-id
```

## Инструменты

| Инструмент | Команда ochan | Что делает |
|---|---|---|
| `diff` | `diff --fast` | сравнить две конфигурации по смыслу |
| `validate` | `validate` | проверить конфигурацию |
| `find` | `find` | найти параметр |
| `stats` | `stats` | статистика конфигурации |
| `print` | `print` | показать файл |
| `plan_config` | `plan` | что изменит правка конфигурации |
| `plan_scenario` | `plan` | что выполнит сценарий |
| `services` | `services` | сервисы сценариев и их исполнители |
| `aliases` | `aliases` | алиасы и встроенные функции — библиотека навыков |
| `modules` | `modules` | установленные модули |
| `history` | `history` | журнал операций |
| `requests` | `requests` | заявки |
| `request_config` | `request` | заявка на правку конфигурации; `after` — выполнить только после другой заявки |
| `request_scenario` | `request` | заявка на выполнение сценария; `after` — так же |
| `task_status` | `status` | статус задачи у исполнителя; `executor` — какого, если их несколько |
| `rank_logs` | `logs rank` | строки журнала по уровням важности или сводка |
| `protocol` | `fp protocol` | протокол: как оператор ставит задачу (`fp.mode`), язык, отказы, порядок работы |
| `vocabulary` | `fp words` | словарь формального промпта: слова, их смыслы и откуда они; `skill` — словарь скилла, `word` — статьи слова |
| `check_prompt` | `fp check` | проверить формальный промпт: ⊥syn, ⊥ambig, ⊥undef, ⊥conflict |
| `check_script` | `check` | проверить сценарий на языке алиасов, ничего не выполняя |
| `plan_script` | `plan --script --bundle` | план сценария в песочнице; с промптом — проверка жёстких правил по плану |
| `request_script` | `request --script --bundle` | заявка на выполнение сценария с промптом и отчётом модели; `after` — так же |

**Чего нет и почему.** `apply`, `approve`, `reject`, `rollback`, `patch` —
выполнение и решения принадлежат человеку. `run` и `eval` — они выполняют
сценарий по-настоящему: `write` и `save` пишут файлы. Сценарии модель
проверяет, планирует и оформляет заявкой, а выполняет человек.
`!install` и `inspect` — запускают чужой исполняемый файл. `auth` — токен
не дело модели. Голый `logs` и `logs files` — журнал самого ochan: в нём
действия оператора. Разрешение даётся подкоманде, а не команде целиком:
таблица пропускает `logs rank`, `fp check` и `fp words`, но не `logs`.

## Сценарии на языке алиасов

Модель пишет сценарий, а не собирает команду: язык алиасов маленький
(24 ключевых слова, 88 встроенных функций), и список функций и алиасов
библиотеки отдаёт инструмент `aliases`. Порядок работы:

1. `check_script` — проверка без выполнения: синтаксис, неизвестные имена
   и функции, число аргументов, `break` и `return` не на своём месте, явно
   неверные типы. Ошибки находятся и в ветках, которые при выполнении не
   сработали бы, и сообщаются все сразу.
2. `plan_script` — сценарий проверяется и выполняется в режиме плана:
   `write` и `save` ничего не пишут, план показывает, какие файлы и
   параметры изменились бы.
3. `request_script` — то же, плюс заявка в состоянии «ждёт решения» с
   текстом сценария и планом. Перед выполнением план строится заново и
   должен совпасть с согласованным.

У `plan_script` и `request_script` есть необязательные `prompt` и
`report` — формальный промпт, по которому написан сценарий, и отчёт
модели. Они проверяются до плана, а дальше — по плану:

- жёсткие правила промпта;
- слоты обобщений: значение, которое сценарий подставляет в операцию
  обобщения, — из домена или диапазона слота (`100..500`);
- ячейки: значение, которое промпт задал, план обязан держать;
- отчёт против плана: значение, которое записывает план и которое решила
  модель (литерал или число в сценарии), обязано быть в отчёте
  (`q: prod_conf.max_connections`) и совпадать с планом; отчёт о том, чего
  план не пишет, — тоже отказ;
- кольца: шаги по мало проверенным правилам отвергаются, а план со
  слабой поддержкой в целом — «нужен оператор»: заявка создаётся, но
  согласуют её, только посмотрев план.

План, который не прошёл, отвергается, и заявка на него не создаётся.
Промпт, отчёт и соблюдённые правила попадают в заявку. Нарушения
запретов, слотов и расхождения отчёта записываются на модель и промпт, а
не на правила скиллов.

Тексты передаются `ochan` через stdin, а не аргументом: командную строку
видно в списке процессов. stdin один, поэтому `plan_script` и
`request_script` подают его JSON-объектом `{"script", "prompt", "report"}`
с флагом `--bundle`, даже если текст один. Таблица инструментов не
пропустит два текста на stdin без `--bundle` и ключ, которого `ochan` не
знает. Необязательное `name` подписывает сценарий в сообщениях об ошибках,
плане и заявке.

**Сценарий всегда выполняется в песочнице.** Чтение файлов в режиме плана
настоящее, поэтому без песочницы модель прочитала бы через план что угодно.
Сервер передаёт `ochan` свои ограничения флагами (`--sandbox --root=…
--allow-live=… --allow-env=… --allow-net=…`), и встроенные функции языка проверяют их
сами при каждом обращении:

- файлы — только внутри тех же каталогов, что и у остальных инструментов;
- переменные окружения — только из `--allow-env` сервера, по умолчанию ни
  одной: в окружении лежат токен API и пароли, а сервер передаёт `ochan`
  своё окружение как есть;
- живые источники — только схем из `--allow-live`;
- `fetch` и `curl` — только к хостам из `--allow-net`, по умолчанию ни к
  одному, и только чтение: `GET` и `HEAD`.

Это свойство тоже проверяется при запуске: инструмент, который принимает
сценарий и выполняет его не через `plan --script` или `request --script`
в песочнице, не пройдёт проверку таблицы, и сервер не стартует.

## Как устроена проверка

Модель не собирает командную строку сама. Каждый инструмент — это схема
со слотами, у каждого слота свой тип, а аргументы `ochan` строит таблица.
Всё, что не прошло проверку, отвергается **до запуска** с понятной причиной,
и модель может исправить вызов.

- **Пути** — только внутри `--root`. Символические ссылки раскрываются до
  проверки: ссылка внутри каталога, ведущая наружу, отвергается.
- **Документы** — только новые `.docx`; существующий файл не перезаписывается.
- **Живые источники** (`postgres://`) — выключены, пока не разрешены явно.
- **Значения** не становятся флагами: позиционные аргументы идут после `--`.
- **Лишние поля** в вызове — ошибка, а не повод их проигнорировать.
- **Переопределения сценария** сортируются: одинаковый вызов — одинаковая
  командная строка, одинаковый план, одинаковая заявка.
- **Пароли** в ссылках маскируются в журнале сервера.
- **Сценарий** — непустая строка без нулевых символов, не длиннее 256 КиБ.
  В журнал сервера пишется только его размер.

Журнал сервер пишет в stderr: каждый вызов, итоговая команда `ochan`, код
возврата и время.

## Ограничения

- Отмена вызова на Windows завершает `ochan` принудительно: послать
  прерывание другому процессу там нельзя, и если у `ochan` загружены модули
  команд, их процессы он погасить не успеет. На Linux и macOS `ochan`
  получает прерывание и завершается сам.
- По HTTP сервер отвечает JSON, а не потоком событий: прогресс долгого
  вызова клиент не видит, ответ приходит целиком.
- Вызовы, присланные одновременно, и выполняются одновременно. Если важен
  порядок — например, создать заявку и сразу её прочитать, — клиент должен
  дождаться первого ответа.

## Тесты

```bash
cd octochan/mcp
go test -race ./...
```

Вместо настоящего `ochan` тесты запускают сам тестовый бинарь: он печатает
полученные аргументы, и проверяется ровно та командная строка, которую
построил сервер.
