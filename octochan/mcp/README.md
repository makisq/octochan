# ochan-mcp

Сервер [Model Context Protocol](https://modelcontextprotocol.io) для octochan.

Это **отдельный модуль**, а не часть ядра. У него свой `go.mod`, ни одной
внешней зависимости, и ядро о нём не знает: `ochan` без него работает так же,
как раньше. Внутри нет ни одной модели и нет кода конкретного поставщика —
MCP открытый протокол, и подключиться может любой клиент с любой моделью.

## Принцип

**Нейросеть предлагает, человек решает.** Через сервер можно читать
конфигурации, строить планы, писать сценарии на языке алиасов и создавать
заявки. Выполнить изменение нельзя: заявку согласует и выполняет человек.

```
модель  →  plan_config / plan_scenario  →  request_config / request_scenario
модель  →  check_prompt → check_script → plan_script → request_script
                                                        ↓
человек →  ochan approve <id>  →  ochan apply --request <id>
```

## Протокол

При подключении модель первым получает протокол формального промпта: сервер
берёт его у `ochan fp protocol` при запуске и отдаёт в `instructions`
ответа на `initialize`. Протокол говорит модели, кто она здесь (слой, а не
собеседник), на каком языке с ней говорят, какие бывают отказы и в каком
порядке работать. Для клиентов, которые `instructions` модели не
показывают, тот же текст отдаёт инструмент `protocol`.

Протокол и `instructions` написаны по-английски — всегда, независимо от
языка оператора: модели понимают английский лучше, и формальный промпт
пишется на нём. Вывод инструментов (находки проверки, план, заявка) — на
языке оператора; коды отказов `⊥syn`, `⊥ambig`, `⊥undef`, `⊥conflict`
одинаковы везде.

Протокол живёт в `ochan`, рядом с проверкой языка, а не копией в сервере:
иначе модель читала бы одно, а проверка требовала бы другого. Если `ochan`
протокол не отдал, сервер работает, но пишет об этом в журнал и в
`instructions`.

Это свойство не держится на договорённости. Таблица инструментов проверяется
при запуске: команда, которой нет в закрытом списке, не пройдёт проверку,
и сервер не стартует.

Второй рубеж — роль. Сервер запускает `ochan` с `OCTOCHAN_ROLE=llm`, что бы
ни было текущей ролью пользователя и что бы ни стояло в окружении сервера.
У роли `llm` права `read`, `plan` и `request`, и выше этого потолка их не
поднять. Даже если в таблицу по ошибке попадёт выполняющая команда, `ochan`
откажет сам.

## Сборка

```bash
cd octochan/mcp
go build -o ochan-mcp .
```

Положите `ochan-mcp` рядом с `ochan` — сервер найдёт его сам. Иначе укажите
путь флагом `--ochan` или добавьте `ochan` в `PATH`.

## Запуск

Сервер говорит по stdio, его запускает клиент. Конфигурация в формате,
который понимает большинство клиентов:

```json
{
  "mcpServers": {
    "octochan": {
      "command": "C:/tools/ochan-mcp.exe",
      "args": ["--root", "D:/configs"]
    }
  }
}
```

| Флаг | По умолчанию | |
|---|---|---|
| `--root DIR` | текущий каталог | где разрешены файлы; можно указать несколько раз |
| `--allow-live postgres` | выключено | разрешить живые источники этой схемы |
| `--allow-env NAME` | ни одной | разрешить сценариям читать эту переменную окружения; можно указать несколько раз |
| `--ochan PATH` | рядом или из `PATH` | путь к `ochan` |
| `--timeout 2m` | 2 минуты | предел одного вызова |
| `--max-output N` | 100 000 байт | предел вывода, который получает модель |

Настройки `ochan` — адрес API, токен, почта — берутся из его обычного
конфига и окружения: сервер передаёт `ochan` своё окружение как есть.

## Инструменты

| Инструмент | Команда ochan | Что делает |
|---|---|---|
| `diff` | `diff --fast` | сравнить две конфигурации по смыслу |
| `validate` | `validate` | проверить конфигурацию |
| `find` | `find` | найти параметр |
| `stats` | `stats` | статистика конфигурации |
| `print` | `print` | показать файл |
| `plan_config` | `plan` | что изменит правка конфигурации |
| `plan_scenario` | `plan` | что выполнит сценарий |
| `services` | `services` | сервисы сценариев и их исполнители |
| `aliases` | `aliases` | алиасы и встроенные функции — библиотека навыков |
| `modules` | `modules` | установленные модули |
| `history` | `history` | журнал операций |
| `requests` | `requests` | заявки |
| `request_config` | `request` | заявка на правку конфигурации |
| `request_scenario` | `request` | заявка на выполнение сценария |
| `task_status` | `status` | статус задачи у исполнителя |
| `rank_logs` | `logs rank` | строки журнала по уровням важности или сводка |
| `protocol` | `fp protocol` | протокол формального промпта |
| `check_prompt` | `fp check` | проверить формальный промпт: ⊥syn, ⊥ambig, ⊥undef, ⊥conflict |
| `check_script` | `check` | проверить сценарий на языке алиасов, ничего не выполняя |
| `plan_script` | `plan --script --bundle` | план сценария в песочнице; с промптом — проверка жёстких правил по плану |
| `request_script` | `request --script --bundle` | заявка на выполнение сценария с промптом и отчётом модели |

**Чего нет и почему.** `apply`, `approve`, `reject`, `rollback`, `patch` —
выполнение и решения принадлежат человеку. `run` и `eval` — они выполняют
сценарий по-настоящему: `write` и `save` пишут файлы. Сценарии модель
проверяет, планирует и оформляет заявкой, а выполняет человек.
`!install` и `inspect` — запускают чужой исполняемый файл. `auth` — токен
не дело модели. Голый `logs` и `logs files` — журнал самого ochan: в нём
действия оператора. Разрешение даётся подкоманде, а не команде целиком:
таблица пропускает `logs rank` и `fp check`, но не `logs`.

## Сценарии на языке алиасов

Модель пишет сценарий, а не собирает команду: язык алиасов маленький
(18 ключевых слов, 30 встроенных функций), и список функций и алиасов
библиотеки отдаёт инструмент `aliases`. Порядок работы:

1. `check_script` — проверка без выполнения: синтаксис, неизвестные имена
   и функции, число аргументов, `break` и `return` не на своём месте, явно
   неверные типы. Ошибки находятся и в ветках, которые при выполнении не
   сработали бы, и сообщаются все сразу.
2. `plan_script` — сценарий проверяется и выполняется в режиме плана:
   `write` и `save` ничего не пишут, план показывает, какие файлы и
   параметры изменились бы.
3. `request_script` — то же, плюс заявка в состоянии «ждёт решения» с
   текстом сценария и планом. Перед выполнением план строится заново и
   должен совпасть с согласованным.

У `plan_script` и `request_script` есть необязательные `prompt` и
`report` — формальный промпт, по которому написан сценарий, и отчёт
модели. Они проверяются до плана, а жёсткие правила промпта — по плану:
план, который нарушает правило, отвергается, и заявка на него не
создаётся. Промпт, отчёт и соблюдённые правила попадают в заявку.

Тексты передаются `ochan` через stdin, а не аргументом: командную строку
видно в списке процессов. stdin один, поэтому `plan_script` и
`request_script` подают его JSON-объектом `{"script", "prompt", "report"}`
с флагом `--bundle`, даже если текст один. Таблица инструментов не
пропустит два текста на stdin без `--bundle` и ключ, которого `ochan` не
знает. Необязательное `name` подписывает сценарий в сообщениях об ошибках,
плане и заявке.

**Сценарий всегда выполняется в песочнице.** Чтение файлов в режиме плана
настоящее, поэтому без песочницы модель прочитала бы через план что угодно.
Сервер передаёт `ochan` свои ограничения флагами (`--sandbox --root=…
--allow-live=… --allow-env=…`), и встроенные функции языка проверяют их
сами при каждом обращении:

- файлы — только внутри тех же каталогов, что и у остальных инструментов;
- переменные окружения — только из `--allow-env` сервера, по умолчанию ни
  одной: в окружении лежат токен API и пароли, а сервер передаёт `ochan`
  своё окружение как есть;
- живые источники — только схем из `--allow-live`.

Это свойство тоже проверяется при запуске: инструмент, который принимает
сценарий и выполняет его не через `plan --script` или `request --script`
в песочнице, не пройдёт проверку таблицы, и сервер не стартует.

## Как устроена проверка

Модель не собирает командную строку сама. Каждый инструмент — это схема
со слотами, у каждого слота свой тип, а аргументы `ochan` строит таблица.
Всё, что не прошло проверку, отвергается **до запуска** с понятной причиной,
и модель может исправить вызов.

- **Пути** — только внутри `--root`. Символические ссылки раскрываются до
  проверки: ссылка внутри каталога, ведущая наружу, отвергается.
- **Документы** — только новые `.docx`; существующий файл не перезаписывается.
- **Живые источники** (`postgres://`) — выключены, пока не разрешены явно.
- **Значения** не становятся флагами: позиционные аргументы идут после `--`.
- **Лишние поля** в вызове — ошибка, а не повод их проигнорировать.
- **Переопределения сценария** сортируются: одинаковый вызов — одинаковая
  командная строка, одинаковый план, одинаковая заявка.
- **Пароли** в ссылках маскируются в журнале сервера.
- **Сценарий** — непустая строка без нулевых символов, не длиннее 256 КиБ.
  В журнал сервера пишется только его размер.

Журнал сервер пишет в stderr: каждый вызов, итоговая команда `ochan`, код
возврата и время.

## Ограничения

- Отмена вызова на Windows завершает `ochan` принудительно: послать
  прерывание другому процессу там нельзя, и если у `ochan` загружены модули
  команд, их процессы он погасить не успеет. На Linux и macOS `ochan`
  получает прерывание и завершается сам.
- Вызовы, присланные одновременно, и выполняются одновременно. Если важен
  порядок — например, создать заявку и сразу её прочитать, — клиент должен
  дождаться первого ответа.

## Тесты

```bash
cd octochan/mcp
go test -race ./...
```

Вместо настоящего `ochan` тесты запускают сам тестовый бинарь: он печатает
полученные аргументы, и проверяется ровно та командная строка, которую
построил сервер.
